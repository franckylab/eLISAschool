🔍 3. Analyse critique — Problèmes identifiés

🔴 P1 — Duplication des registres (CRITIQUE)

Le ModuleRegistryService (15 modules hardcodés) et le ModuleResolutionService (catalogue DB) peuvent retourner des résultats incohérents. Le middleware requireModuleActive() utilise configurationService.isModuleActive() qui ne consulte PAS le ModuleResolutionService.

🔴 P2 — Accès aux modules sans plan actif (CRITIQUE)

Un établissement sans AbonnementClient actif peut accéder aux modules avec actifParDefaut=true. Il n'y a aucun gating basé sur le statut de l'abonnement. Conséquence : un établissement qui n'a jamais souscrit ou dont l'abonnement a expiré utilise gratuitement des modules qui devraient être payants.

🟡 P3 — Les établissements voient la configuration de TOUS les modules

L'endpoint GET /configuration/modules-advanced/definitions retourne toutes les définitions sans filtrage par plan. L'établissement voit des modules auxquels il n'a pas droit (ex: comptabilite nécessite plan enterprise).

🟡 P4 — Pas de distinction "visible" vs "accessible"

Un module devrait être soit (a) visible mais verrouillé avec upsell, soit (b) complètement masqué. Actuellement, tous les modules sont visibles et toggle-able par l'établissement, même ceux nécessitant un plan supérieur.

🟡 P5 — Incohérence de cascade entre services

ModuleRegistryService.isModuleActif() : override tenant → featureFlag → défaut
ModuleResolutionService.resoudre() : catalogue → plan → groupe → supplément
ConfigurationService.isModuleActive() : sa propre cascade
Ces 3 chemins donnent des résultats différents pour le même module.

🟢 P6 — Points positifs de l'architecture actuelle

✓ Cache Redis + Pub/Sub cross-instance (TTL 60s unifié)
✓ Middleware RLS avec isolation multi-tenant stricte
✓ Modules critiques protégés (bypass middleware + service)
✓ Gestion des dépendances (auto-activation à l'activation)
✓ Audit trail via HistoriqueConfiguration
✓ Impact preview avant activation/désactivation

🌍 4. Meilleures pratiques SaaS (benchmarks)

4.1 Patterns industry — Feature Gating & Entitlements

📌 Pattern 1 : Entitlement-Based Access

Chaque plan définit des entitlements (droits d'accès). L'entitlement est lié au cycle de vie de l'abonnement : activation → renouvellement → expiration → révocation.

Utilisé par : Stripe Billing, Stigg, Schematic

📌 Pattern 2 : Feature Flags + Entitlements

Séparer le feature flag (déploiement technique, rollout %) de l'entitlement (droit contractuel). Le flag contrôle la disponibilité technique ; l'entitlement contrôle le droit d'accès.

Utilisé par : LaunchDarkly, Split.io

📌 Pattern 3 : Entitlements ≠ Feature Flags

Les feature flags sont volatils (modifiés à la volée). Les entitlements sont permanents et liés au contrat. Ne JAMAIS utiliser un flag pour contrôler un droit payant — risque de donner/retirer un accès par erreur.

Source : Schematic HQ, Stigg

📌 Pattern 4 : Graceful Degradation

Quand un abonnement expire : (1) données préservées en lecture seule, (2) module verrouillé avec message upsell, (3) période de grâce configurable, (4) archivage après N jours.

Utilisé par : WorkOS, HubSpot, Intercom

💡 5. Recommandations & plan d'action

R1 — Unifier la source de vérité (PRIORITÉ MAX — P0)

Supprimer le ModuleRegistryService (hardcoded). Le ModuleResolutionService (catalogue DB) devient la source unique de résolution. Le ConfigurationService.isModuleActive() doit déléguer au ModuleResolutionService.

Fichiers : module-registry.service.ts (supprimer), configuration.service.ts (déléguer), module-active.middleware.ts

R2 — Implémenter le gating par abonnement (P0)

Si AbonnementClient.statut !== ACTIF pour un établissement :

  • Seuls les modules CRITIQUE restent accessibles
  • Tous les autres modules sont verrouillés (lecture seule si données existantes)
  • Le frontend affiche un bandeau "Abonnement requis" avec CTA facturation
R3 — Filtrer la visibilité par plan (P1)

L'endpoint GET /configuration/modules-advanced/status retourne pour chaque module :

  • estAccessible : le module est actif ET le plan le permet
  • estVisible : le module est visible dans le catalogue (pas masqué)
  • raisonBlocage : "Plan Pro requis" / "Abonnement expiré" / "Module désactivé"
R4 — Implémenter la révocation gracieuse (P2)

Quand un abonnement expire (statut: EXPIRE) :

  1. Jour 0 : Bandeau alerte + notification email/SMS
  2. Jour 1-15 : Modules premium en lecture seule (données préservées)
  3. Jour 15-30 : Modules premium verrouillés (message upsell)
  4. Jour 30+ : Données archivées (export disponible)
R5 — Séparer Feature Flags et Entitlements (P2)

• Entitlements = droits contractuels (liés au plan, automatiques)
• Feature Flags = contrôle technique (rollout, A/B testing, kill switch)
• Ne JAMAIS utiliser un feature flag pour contrôler un droit payant
• Créer un EntitlementService dédié

R6 — Frontend : Upsell & Module Cards (P2)

Pour les modules non accessibles, afficher :

  • Un cadenas + label "Plan Pro requis"
  • Un bouton "Découvrir ce module" (preview/description)
  • Un bouton "Upgrader" (CTA vers page facturation)
  • Pas de toggle activable (grisé avec tooltip explicatif)

🎯 6. Architecture cible proposée

Figure 2 — Architecture cible avec EntitlementService comme source unique de vérité

Logique cible de l'EntitlementService

class EntitlementService {
  
  async check(etablissementId: string, moduleCode: string): Promise<EntitlementResult> {
    
    // 1. Module CRITIQUE → toujours accessible (bypass total)
    const catalogue = await this.getCatalogue(moduleCode);
    if (catalogue.categorie === CategorieModule.CRITIQUE) {
      return { accessible: true, visible: true, source: 'critique' };
    }
    
    // 2. Abonnement ACTIF ?
    const abonnement = await this.getAbonnement(etablissementId);
    if (!abonnement || abonnement.statut !== StatutAbonnement.ACTIF) {
      return { 
        accessible: false, 
        visible: true, 
        raison: 'ABONNEMENT_INACTIF',
        message: 'Un abonnement actif est requis pour accéder à ce module'
      };
    }
    
    // 3. Plan inclut le module ?
    if (abonnement.plan.modulesInclus.includes(moduleCode)) {
      return { accessible: true, visible: true, source: 'plan' };
    }
    
    // 4. Supplément souscrit ?
    const supplements = await this.getSupplements(etablissementId);
    if (supplements.includes(moduleCode)) {
      return { accessible: true, visible: true, source: 'supplement' };
    }
    
    // 5. planMinimal compatible ?
    if (catalogue.planMinimal) {
      const planRang = this.getPlanRang(abonnement.plan.slug);
      const requiredRang = this.getPlanRang(catalogue.planMinimal);
      if (planRang < requiredRang) {
        return { 
          accessible: false, 
          visible: true, 
          raison: 'PLAN_INSUFFICIENT',
          message: `Plan "${catalogue.planMinimal}" ou supérieur requis`
        };
      }
    }
    
    // 6. Défaut catalogue (actifParDefaut)
    return { 
      accessible: catalogue.actifParDefaut, 
      visible: true, 
      source: 'catalogue' 
    };
  }
}

📋 8. Conclusion exécutive

❌ État actuel
  • 3 registres de modules divergents
  • Pas de gating par abonnement actif
  • Tous les modules visibles par tous
  • Cascade incohérente entre services
  • Pas de révocation à l'expiration
  • Pas de distinction visible/accessible
✅ État cible (recommandé)
  • 1 source unique : EntitlementService
  • Gating strict par abonnement actif
  • Visibilité filtrée par plan + upsell
  • Cascade unifiée et cohérente
  • Révocation gracieuse à l'expiration
  • Séparation Flags / Entitlements
