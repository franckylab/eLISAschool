4. Phase P0 — Sécurité critique

🚨 P0 — Corrections sécurité critiques
CRITIQUE — 1 semaine

Prérequis : aucun | Bloque : toutes les phases suivantes

Tâches backend sécuritébackend

  • P0.1 — Supprimer bypass SUPER_ADMIN dans permission-guards
    permission-guards.ts L37-39, 83-85, 141-143, 174-176
    • Remplacer if (user.role === 'SUPER_ADMIN') return true par résolution CASL (P2)
    • En attendant P2 : ajouter logging obligatoire + restriction au scope plateforme
    • SUPER_ADMIN doit avoir TOUTES les permissions mais avec traçabilité
  • P0.2 — Isoler ADMIN des configs plateforme
    configuration.controller.ts, app.ts
    • Créer middleware requirePlatformAccess() — SUPER_ADMIN uniquement
    • Appliquer aux routes : /api/configuration/systeme/*, /api/modules/toggle
    • ADMIN établissement ne peut modifier que le scope etablissementId
  • P0.3 — Corriger permissions cross-tenant DIRECTEUR
    roles.enum.ts DEFAULT_ROLE_PERMISSIONS
    • Audit complet des permissions attribuées à DIRECTEUR/CHEF_ETABLISSEMENT
    • Supprimer toute permission sans filtre etablissementId
    • Ajouter test automatisé : vérifier que chaque permission a un guard multi-tenant
  • P0.4 — Forcer etablissementId sur TOUTES les mutations
    • Audit de tous les controllers : vérifier que etablissementId vient du JWT, jamais du body
    • Créer helper forceTenantId(req) qui override toute valeur body/query
    • Logger toute tentative de cross-tenant avec alerte
  • P0.5 — Ajouter tests de sécurité automatisés
    • Test : utilisateur tenant A ne peut PAS lire données tenant B
    • Test : ADMIN ne peut PAS accéder aux routes plateforme
    • Test : SUPER_ADMIN ne peut PAS bypasser les guards sans audit trail
    • Intégrer dans CI/CD (blocage merge si échec)
⚠ Risque : Ces corrections peuvent casser des fonctionnalités existantes qui reposent sur le bypass. Tester exhaustivement avant déploiement.

6. Phase P2 — CASL.js + RLS

🛡 P2 — CASL.js + Row Level Security
HAUTE — 3 semaines

Prérequis : P0, P1 | Bloque : P3, P6

Semaine 1 — CASL.js backend

  • P2.1 — Installer @casl/ability
    • npm install @casl/ability dans backend + shared
    • Créer shared/src/auth/ability.ts — définition des types
  • P2.2 — Définir le factory defineAbilityFor(user, tenant)
    • Mapper les 230 permissions existantes vers des règles CASL
    • Pattern : can('read', 'Eleve', { etablissementId: tenant.id })
    • SUPER_ADMIN : can('manage', 'all') + cannot('delete', 'Etablissement')
    • ADMIN : can('manage', 'all', { etablissementId: tenant.id })
    • Plans : if (tenant.plan === 'basic') cannot('export', 'AuditLog')
  • P2.3 — Middleware CASL
    • caslMiddleware : construit l'ability et l'attache à req.ability
    • Helper authorize(action, subject) pour les controllers
    • Remplacement progressif de requirePermission() par authorize()
  • P2.4 — Migration progressive des guards
    • Strangler Fig : double-write (ancien guard + CASL) pendant 1 semaine
    • Comparer les résultats (logs) — alerte si divergence
    • Supprimer ancien guard module par module

Semaine 2 — RLS PostgreSQL database

  • P2.5 — Activer RLS sur les tables business
    • 40+ tables : ALTER TABLE xxx ENABLE ROW LEVEL SECURITY
    • Policy standard : USING ("etablissementId" = current_setting('app.current_tenant')::uuid)
    • Tables SANS RLS : etablissements, parametres_systeme, nomenclatures globales
  • P2.6 — Fonction set_tenant()
    • CREATE FUNCTION set_tenant(tenant_id uuid) — set_config transaction-scoped
    • Appelée par le middleware Express au début de chaque requête
  • P2.7 — AsyncLocalStorage pour propagation tenant
    • Créer backend/src/common/async-storage/tenant-context.ts
    • Wrapper middleware : tenantContext.run({ id: etablissementId }, next)
    • Custom TypeORM subscriber : appelle set_tenant() avant chaque query
  • P2.8 — Tests RLS
    • Test : connexion avec tenant A → query retourne uniquement données A
    • Test : injection SET app.current_tenant = 'B' dans body → ignorée
    • Test : SUPER_ADMIN sans set_tenant → accès global (policy dedicated)

Semaine 3 — Intégration + Partitioning databasebackend

  • P2.9 — Hash partitioning (tables volumineuses)
    • Migration : convertir eleves, notes, heures_cours en partitioned tables
    • Strangler Fig : double-write pendant transition
    • 16 partitions HASH pour eleves/heures_cours, 32 pour notes
  • P2.10 — Range partitioning audit_logs
    • 12 partitions mensuelles (rolling window)
    • Cron job : créer partition mois+3, archiver purge mois-12
  • P2.11 — Monitoring RLS
    • Vue v_rls_stats : nombre de policies par table, tables sans RLS
    • Alerte si nouvelle table créée sans RLS
💡 Pattern CASL.js cible : 
export function defineAbilityFor(user: JwtPayload, tenant: TenantContext) {
  const { can, cannot, build } = new AbilityBuilder(createMongoAbility);
  
  if (user.role === 'SUPER_ADMIN') {
    can('manage', 'all');
    cannot('delete', 'Etablissement'); // protection plateforme
  }
  
  if (user.role === 'ADMIN') {
    can('manage', 'all', { etablissementId: tenant.id });
    cannot('manage', 'PlatformConfig');
  }
  
  // Restrictions par plan
  if (tenant.plan === 'basic') {
    cannot('export', 'AuditLog');
    cannot('create', 'Utilisateur', {}, 'maxUsers50');
  }
  if (tenant.plan === 'standard') {
    cannot('access', 'Module', { premium: true });
  }
  
  return build();
}

13. Recommandations transversales

💡 Recommandations architecture

  • Monnaie : TOUS les montants stockés en integer XAF (pas de float). Conversion centimes si nécessaire. Affichage avec Intl.NumberFormat.
  • Horodatage : Africa/Douala (UTC+1) partout. Cron jobs avec timezone explicite.
  • Soft delete : obligatoire sur toutes les entités transactionnelles (abonnements, factures, transactions). Hard delete interdit sauf nomenclatures.
  • Audit : TOUTE action plateforme loguée avec scope='platform', cible, cibleId, metadata.
  • Chiffrement : credentials providers chiffrés AES-256-GCM. Clé dans .env (jamais en base).

🎨 Recommandations UX/UI

  • Design system : réutiliser les composants existants (CustomModal, DataTable, StatCard, ElisaButton, StepperModal). Pas de nouveaux patterns.
  • i18n : toutes les nouvelles pages en FR + EN. Clés dans platform.json (nouveau namespace).
  • Responsive : clamp() partout, 11 breakpoints, transformation table→card < 480px.
  • Dark mode : CSS vars uniquement, testé sur chaque nouveau composant.
  • Performance : skeleton loading, lazy loading routes, code splitting Vite.

🔐 Recommandations sécurité

  • Defense in depth : 4 couches (RLS + CASL + Middleware + Feature Flags). Aucune couche seule ne suffit.
  • Zero trust : jamais faire confiance au body/query pour etablissementId. Toujours extraire du JWT.
  • Audit trail : toute action sensible loguée avec metadata complète. Rétention 1 an minimum.
  • Rate limiting : endpoints paiement (10/min), auth (5/min), export (3/min).
  • Secrets : rotation automatique tous les 90 jours. Vault-ready (interface abstraite).
