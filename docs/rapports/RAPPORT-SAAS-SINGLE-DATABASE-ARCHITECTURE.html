Couche 1 — Application (déjà en place)

Le middleware tenant.middleware.ts résout le etablissementId depuis le JWT et l'injecte dans req.etablissementId. Chaque service filtre systématiquement par cet ID.

Renforcement nécessaire : Ajouter un interceptor TypeORM global qui injecte automatiquement le etablissementId dans chaque requête (WHERE, CREATE, UPDATE, DELETE). Cela élimine le risque d'oubli dans un service.

Couche 2 — Row-Level Security (RLS)

RLS est une fonctionnalité native de PostgreSQL (depuis la v9.5, mature depuis la v12). Il garantit que même si le code applicatif oublie un filtre, la base de données rejette toute ligne d'un autre tenant.

-- Activer RLS sur une table
ALTER TABLE eleves ENABLE ROW LEVEL SECURITY;

-- Politique : chaque tenant ne voit que ses élèves
CREATE POLICY tenant_isolation ON eleves
  USING ("etablissementId" = current_setting('app.current_tenant')::uuid);

-- Forcer RLS même pour le owner de la table
ALTER TABLE eleves FORCE ROW LEVEL SECURITY;

-- Définir le tenant courant à chaque requête
SET app.current_tenant = 'uuid-etablissement-xxx';

Avantage clé : La politique RLS est évaluée au niveau du moteur de base de données. Même une injection SQL ne peut pas contourner cette isolation. C'est la garantie la plus forte possible en single-DB.

Couche 3 — Partitionnement par tenant

Le partitionnement divise physiquement les grandes tables en sous-tables plus petites. PostgreSQL route automatiquement les requêtes vers la bonne partition.

-- Partitionnement par hash sur les tables à fort volume
CREATE TABLE eleves (
    id uuid NOT NULL,
    "etablissementId" uuid NOT NULL,
    nom varchar(100),
    ...
) PARTITION BY HASH (id);

-- 16 partitions (couvre jusqu'à ~100K tenants)
CREATE TABLE eleves_p0 PARTITION OF eleves
  FOR VALUES WITH (MODULUS 16, REMAINDER 0);
CREATE TABLE eleves_p1 PARTITION OF eleves
  FOR VALUES WITH (MODULUS 16, REMAINDER 1);
-- ... jusqu'à eleves_p15

-- Alternative : partitionnement par liste (etablissementId)
-- pour les très gros tenants (isolation physique totale)

Tables à partitionner en priorité : eleves, notes, heures_cours, creneaux_horaires, bulletins_paie, audit_logs. Les tables de nomenclature (petites, partagées) restent non-partitionnées.

Isolation garantie

Row-Level Security (RLS) en détail

RLS est le mécanisme d'isolation recommandé par Supabase, Microsoft Azure, Citus et la communauté PostgreSQL pour le multi-tenancy single-DB. Voici comment l'implémenter correctement.

Comment fonctionne RLS

Quand RLS est activé sur une table, PostgreSQL ajoute automatiquement un filtre à CHAQUE requête (SELECT, UPDATE, DELETE). Si la requête ne satisfait pas la politique, les lignes sont invisibles — comme si elles n'existaient pas.

Requête applicative
SELECT * FROM eleves
→
PostgreSQL injecte RLS
+ WHERE etablissementId = current_tenant
→
Résultat filtré
Seules les lignes du tenant

Intégration avec TypeORM

Le défi principal est de propager le etablissementId du middleware Express vers la session PostgreSQL. Voici le pattern recommandé :

// 1. Middleware Express — définit le tenant PostgreSQL
app.use(async (req, res, next) => {
  if (req.utilisateur?.etablissementId) {
    // Définit la variable de session PostgreSQL
    await req.queryRunner?.query(
      `SET LOCAL app.current_tenant = $1`,
      [req.utilisateur.etablissementId]
    );
  }
  next();
});

// 2. TypeORM — Subscriber qui exécute SET avant chaque requête
@EventSubscriber()
export class TenantSubscriber implements EntitySubscriberInterface {
  beforeQuery(event: QueryEvent) {
    const tenant = AsyncLocalStorage.tenant; // via AsyncLocalStorage
    if (tenant) {
      event.queryRunner.query(
        `SET LOCAL app.current_tenant = $1`, [tenant]
      );
    }
  }
}

// 3. Alternative : TypeORM CustomDecorator / Interceptor
// Intercepte chaque query et injecte le WHERE automatiquement

AsyncLocalStorage (Node.js) est le mécanisme recommandé pour propager le tenant ID à travers toute la chaîne d'appel sans le passer explicitement dans chaque fonction.

Performance à l'échelle

Partitionnement — Quand et comment

Le partitionnement est optionnel pour les premiers milliers de tenants. Il devient nécessaire quand les tables dépassent ~10M de lignes. PostgreSQL gère cela nativement depuis la v10.

Stratégie de partitionnement recommandée

Table Volume estimé (1000 tenants) Stratégie Partitions Clé
eleves 500K – 2M lignes HASH 16 id
notes 2M – 10M lignes HASH 32 id
heures_cours 1M – 5M lignes HASH 16 id
creneaux_horaires 200K – 1M lignes Aucun — Index suffisant
bulletins_paie 500K – 2M lignes HASH 16 id
audit_logs 5M – 50M lignes RANGE Par mois "createdAt"
classes, matieres 50K – 200K lignes Aucun — Index suffisant

Pourquoi HASH et pas LIST par etablissementId ?

Le partitionnement LIST par etablissementId semble intuitif mais pose problème : chaque nouvel établissement nécessite de créer manuellement une partition. Le partitionnement HASH distribue uniformément les données sans maintenance. Pour les très gros tenants (ex: ministère avec 500 écoles), on peut créer une partition LIST dédiée en plus du hash.

Performance & Noisy Neighbor

Le principal risque du single-DB est le noisy neighbor : un tenant qui consomme toutes les ressources au détriment des autres. Voici les stratégies de mitigation.

Stratégies anti-noisy neighbor

1. Rate limiting par tenant

// Middleware Express
const tenantLimiter = (req, res, next) => {
  const key = `rate:${req.etablissementId}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, 60);
  if (count > 100) { // 100 req/min par tenant
    return res.status(429).json({
      error: 'RATE_LIMIT_EXCEEDED'
    });
  }
  next();
};

2. Resource quotas par plan

// EtablissementConfig (déjà en place)
{
  planAbonnement: 'PRO',
  maxEleves: 2000,
  maxUtilisateurs: 50,
  maxStockageMo: 5000,
  maxRequetesMinute: 200,
  // Nouveau : quota DB
  maxConnexionsSimultanees: 10,
  maxLignesTables: 100000
}

3. Connection pooling par tenant

# PgBouncer — transaction pooling
# Chaque tenant partage le pool
# mais ne peut pas monopoliser

[pgbouncer]
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 25
min_pool_size = 5
reserve_pool_size = 5
reserve_pool_timeout = 3s

4. Monitoring par tenant

-- Vue de monitoring par tenant
SELECT
  "etablissementId",
  count(*) as total_lignes,
  pg_size_pretty(sum(
    pg_total_relation_size(oid)
  )) as taille_totale
FROM eleves
GROUP BY "etablissementId"
ORDER BY total_lignes DESC
LIMIT 10;

Pourquoi Single-DB + RLS + Partitionnement gagne

Ce pattern offre le meilleur rapport coût/isolation/simplicité pour eLISAschool. Il est 100% compatible avec le stack existant (TypeORM + PostgreSQL), ne nécessite qu'un seul serveur à gérer, et peut évoluer vers Citus (extension distribuée PostgreSQL) si le nombre de tenants dépasse 10 000 — sans changement d'application.

C'est le pattern recommandé par Microsoft Azure (sharded multitenant = évolution de ce pattern), Supabase (RLS natif), et Citus (distribution transparente).

Au-delà du single-DB

Alternatives performantes et efficaces

Le single-DB n'est pas la seule option. Voici les alternatives viables, classées par cas d'usage.

Citus (PostgreSQL distribué) — Le plus scalable

C'est la montée en charge naturelle du single-DB. Citus est une extension PostgreSQL qui transforme une instance unique en cluster distribué. Le tenant_id devient la clé de distribution. Transparent pour l'application (requêtes SQL standard).

  • Scale : jusqu'à 1M+ tenants
  • Coût : 3 nœuds minimum (~$150/mo DigitalOcean)
  • Compatibilité : TypeORM 80% (quelques limitations sur les transactions cross-shard)
  • Migration : depuis single-DB sans downtime (Citus supporte la redistribution)
  • Quand : >10 000 tenants ou >100M lignes

Hybrid Sharded (Microsoft) — Le plus flexible

Combine single-DB et DB-per-tenant. Les petits tenants partagent des bases shardées, les gros tenants ont leur propre base. Le routing est géré par un shard mapper.

  • Scale : illimité (shards + dedicated DBs)
  • Coût : optimisé (partage pour les petits, dédié pour les gros)
  • Complexité : élevée (routing, shard management)
  • Compatibilité TypeORM : nécessite DataSource dynamique
  • Quand : tenants très hétérogènes (de 10 à 10 000 élèves)

Neon / Serverless PostgreSQL — Le plus moderne

Serverless PostgreSQL avec branching. Neon propose un PostgreSQL serverless avec scale-to-zero, branching (comme Git pour la DB), et separation storage/compute. Idéal pour le dev/testing.

  • Scale : automatique (scale-to-zero)
  • Coût : pay-per-use (très économique en dev)
  • Compatibilité : 100% PostgreSQL (donc TypeORM)
  • Limitation : cold start (~200ms), vendor lock-in
  • Quand : dev/testing, ou production si <500 tenants

Elastic Pools (Azure SQL) — Le plus économique

Partage de ressources entre DBs. Azure SQL Elastic Pools permettent de partager un pool de ressources (CPU, RAM) entre plusieurs bases de données tenant. Chaque tenant a sa DB (isolation maximale) mais partage le coût.

  • Scale : 100-100 000 tenants
  • Coût : très bas (partage ressources)
  • Isolation : maximale (DB séparée)
  • Limitation : Azure-only, pas PostgreSQL
  • Quand : si migration vers Azure SQL (non recommandé pour eLISAschool)

Plan d'implémentation pour eLISAschool

Voici les étapes concrètes pour transformer l'architecture actuelle d'eLISAschool en architecture SaaS single-DB optimisée.

Phase 1 — Durcissement RLS (2-3 jours)

  1. Audit des tables : lister toutes les tables avec etablissementId (~40 tables)
  2. Créer la fonction helper : current_tenant_id() qui lit current_setting('app.current_tenant')
  3. Activer RLS sur les 40 tables métier (ENABLE ROW LEVEL SECURITY)
  4. Créer les politiques : SELECT/INSERT/UPDATE/DELETE pour chaque table
  5. FORCE RLS : forcer RLS même pour le table owner (FORCE ROW LEVEL SECURITY)
  6. Middleware SET LOCAL : définir app.current_tenant au début de chaque requête HTTP
  7. Tests : vérifier qu'aucune fuite cross-tenant n'est possible (tests d'injection)

Phase 2 — Interceptor TypeORM (1-2 jours)

// TypeORM Subscriber — propagation automatique du tenant
@EventSubscriber()
export class TenantIsolationSubscriber implements EntitySubscriberInterface {

  async beforeQuery(event: QueryEvent) {
    const tenant = AsyncResource.bind(
      AsyncLocalStorage.getStore()?.get('etablissementId')
    );
    if (tenant) {
      await event.queryRunner.query(
        `SET LOCAL app.current_tenant = $1`,
        [tenant]
      );
    }
  }
}

// Enregistrer dans le DataSource
dataSource.subscribers.push(new TenantIsolationSubscriber());

Avec RLS actif, même si un développeur oublie le filtre etablissementId dans un service, PostgreSQL bloque l'accès aux lignes d'un autre tenant. Double sécurité : application + base de données.

Phase 3 — Monitoring & quotas (2-3 jours)

  • Dashboard admin : vue par tenant (nombre de lignes, taille, requêtes/min)
  • Alertes noisy neighbor : alerte si un tenant dépasse 80% de son quota
  • Rate limiting : middleware Express avec Redis (par tenant)
  • Export par tenant : pg_dump --schema-only + COPY filtré par etablissementId
  • Backup granulaire : possibilité de restaurer un tenant spécifique

Phase 4 — Partitionnement (optionnel, 1-2 jours)

À implémenter uniquement quand les tables dépassent 10M de lignes (~2 000+ tenants actifs).

-- Migration de partitionnement (idempotent)
-- 1. Créer la table partitionnée
CREATE TABLE eleves_partitioned (LIKE eleves INCLUDING ALL)
  PARTITION BY HASH (id);

-- 2. Créer les partitions
DO $$ BEGIN
  FOR i IN 0..15 LOOP
    EXECUTE format(
      'CREATE TABLE eleves_p%s PARTITION OF eleves_partitioned
       FOR VALUES WITH (MODULUS 16, REMAINDER %s)',
      i, i
    );
  END LOOP;
END $$;

-- 3. Migrer les données
INSERT INTO eleves_partitioned SELECT * FROM eleves;

-- 4. Swap (atomique)
BEGIN;
ALTER TABLE eleves RENAME TO eleves_legacy;
ALTER TABLE eleves_partitioned RENAME TO eleves;
COMMIT;

-- 5. Vérifier + drop legacy après validation

Stratégie de migration

La migration vers le single-DB RLS peut se faire progressivement, sans downtime, grâce au pattern Strangler Fig.

Pattern Strangler Fig pour RLS

  1. Étape 1 — Double écriture : le code applicatif continue de filtrer par etablissementId ET RLS est activé en mode PERMISSIVE (ne bloque rien, logue seulement les violations)
  2. Étape 2 — Monitoring : observer les logs pendant 1-2 semaines pour détecter les requêtes qui violent RLS (fuites potentielles)
  3. Étape 3 — Mode restrictif : passer RLS en mode RESTRICTIVE (bloque les violations). Les requêtes sans filtre tenant échouent avec une erreur claire
  4. Étape 4 — Confiance : après 1 mois sans violation, activer FORCE ROW LEVEL SECURITY (applique RLS même au table owner)

Checklist de migration

Pré-requis

  • ☐ PostgreSQL ≥ 15 (RLS mature)
  • ☐ Toutes les tables ont etablissementId
  • ☐ Le middleware tenant est fonctionnel
  • ☐ Les services filtrent systématiquement
  • ☐ Tests d'intégration multi-tenant existent
  • ☐ Backup complet fonctionnel

Post-migration

  • ☐ RLS activé sur toutes les tables métier
  • ☐ Middleware SET LOCAL en place
  • ☐ Subscriber TypeORM enregistré
  • ☐ Monitoring par tenant actif
  • ☐ Tests de fuite cross-tenant (pentest)
  • ☐ Documentation RLS pour l'équipe

Rollback plan

Sécurité : RLS peut être désactivé instantanément avec ALTER TABLE ... DISABLE ROW LEVEL SECURITY. En cas de problème, le rollback est immédiat et sans perte de données. L'application continue de fonctionner avec le filtrage applicatif existant.
