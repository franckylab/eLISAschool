2. Source Unique de Vérité — ParametreSysteme

Confirmé

Chaque paramètre est identifié par une clé en notation pointée (ex: notes.require_validation). Le modèle supporte le multi-tenant via etablissementId nullable.

Mécanisme de Résolution

ℹ
Algorithme getParametre(clé, etablissementId)

1. Chercher (cle, etablissementId) → si trouvé, retourner
2. Chercher (cle, NULL) → valeur globale
3. Retourner valeurDefaut du paramètre (ou undefined)
Cache in-memory 60s avec invalidation par événement (EventEmitter)

// Exemple de résolution multi-tenant

  'notes.require_validation',
  etablissementId  // UUID tenant ou undefined pour global
);

// Priorité : override tenant → global → défaut

3. Cascade de Configuration — 4 Niveaux

Vérifié

Le système de cascade permet des overrides hiérarchiques : une valeur globale peut être surchargée au niveau groupe, puis au niveau établissement.

Priorité 1 Système (code defaults)

Valeurs par défaut codées dans configuration-seed.service.ts — 100+ paramètres initialisés. Fallback ultime.

Priorité 2 Global (etablissementId = NULL)

Valeur globale dans parametres_systeme. Appliquée à tous les établissements sauf override.

Priorité 3 Groupe (groupeEtablissementId)

Override pour un groupe d'établissements (SaaS v7 — Lot C). Intermédiaire entre global et établissement.

Priorité 4 Établissement (etablissementId = UUID)

Override spécifique à un établissement. Priorité maximale. Isolation stricte par RLS.

4. Isolation Multi-Tenant — 5 Couches de Défense

Confirmé

L'isolation des configurations tenant est garantie par 5 couches successives. Chaque couche est indépendante — la compromission d'une seule ne suffit pas à exposer les données d'un autre tenant.

1

Contrainte Unique (Data Layer)

UNIQUE(cle, etablissementId) — chaque paramètre est physiquement isolé par établissement dans la base de données.

PostgreSQL
2

Row-Level Security (RLS)

Toutes les tables avec etablissementId ont RLS activé (migrations 152-153-164). Policy : etablissementId = current_setting('app.current_tenant').

RLS
3

Service Layer (Résolution)

configurationService.getParametre() filtre toujours par etablissementId. Le fallback global est contrôlé (NULL explicite).

TypeScript
4

Controller Layer (Scoping)

Le controller force etablissementId depuis le token JWT pour les rôles non-SUPER_ADMIN. SUPER_ADMIN peut spécifier un etablissementId via query param.

Express
5

Middleware Layer (Cross-Plane Rejection)

platformAuthMiddleware rejette les tokens plane: 'platform' sur les routes tenant. rlsMiddleware rejette les tokens platform via rejectCrossPlaneRequest().

Guard

✓
Isolation Vérifiée

Chaque établissement a sa propre configuration isolée. Les 5 couches garantissent qu'aucun tenant ne peut accéder aux paramètres d'un autre tenant, même en cas de compromission d'une seule couche.

// Cascade de résolution (module-resolution.service.ts v3)
async resoudre(etablissementId: string): Promise<ModuleResolu[]> {
  // 1. Charger catalogue actif
  const catalogue = await this.getCatalogueActif();

  // 2. Résoudre plan abonnement
  const plan = await this.getPlanAbonnement(etablissementId);
  const modulesInclus = plan?.modulesInclus ?? [];

  // 3. Résoudre groupe (SaaS v7)
  const groupeOverrides = await this.getModulesGroupe(etablissementId);

  // 4. Résoudre souscriptions supplémentaires
  const supplements = await this.getAbonnementModules(etablissementId);

  // 5. Appliquer overrides ParametreSysteme
  const overrides = await this.getParamOverrides(etablissementId);

  // Fusion : catalogue → plan → groupe → supplément → override
  return this.fusionner(catalogue, modulesInclus, groupeOverrides, supplements, overrides);
}

Recommandations

⚠
R1 — Supprimer ConfigurationApp (v3.0)

L'entité ConfigurationApp est marquée dépréciée depuis v2.0. Planifier sa suppression complète pour éliminer toute ambiguïté sur la source de vérité.

ℹ
R2 — Étendre le cache Redis pub/sub

L'invalidation cache via EventEmitter est locale au processus. En cluster (multi-instance), le pub/sub Redis est nécessaire pour propager les invalidations. Déjà implémenté dans moduleResolutionService — étendre à configurationService.

ℹ
R3 — Paramètres sensibles : chiffrement valeur

Certains paramètres (ex: credentials notifications) sont stockés en clair dans valeur. Envisager un type ENCRYPTED dans typeValeur pour chiffrement automatique via CleCryptographique.

★
Conclusion

Le système de configuration eLISAschool est robuste, cohérent et enterprise-grade. La source unique de vérité (ParametreSysteme) est correctement implémentée avec isolation multi-tenant stricte (5 couches), séparation plateforme/tenant (RBAC-2 + dual-plane), et cascade 4 niveaux avec détection d'incohérences. Les paramètres critiques de plateforme ne sont jamais exposés aux tenants. Le panel admin permet la gestion complète de toutes les configurations.
