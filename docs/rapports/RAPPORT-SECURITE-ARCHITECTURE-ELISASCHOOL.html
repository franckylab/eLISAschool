2 Authentification

Le système d'authentification supporte 5 modes de login, un chiffrement bcrypt(12), des JWT avec résolution serveur des permissions, et une MFA TOTP optionnelle.

2.1 — Flux d'authentification

2.2 — Modes de login supportés

Email

Mode principal. Unique dans la table utilisateurs. Recherche case-insensitive.

Matricule

Identifiant scolaire unique. Utilisé par le personnel et les élèves.

Pseudonyme

Nom d'utilisateur libre. Unique, alphanumérique + tirets.

QR Code

Champ qrCodeId unique. Scan carte d'identité scolaire.

UUID direct

Identifiant interne. Usage API et intégrations.

Détection SQLi

Regex de détection d'injection SQL sur tous les identifiants avant requête.

2.3 — JWT & Sessions

// JWT Payload — Permissions EXCLUES (éviter HTTP 431) { "sub": "uuid-utilisateur", "email": "admin@ecole.cm", "role": "ADMIN", "roles": ["ADMIN"], "etablissementId": "uuid-etab", "etablissements": ["uuid-1", "uuid-2"], "iat": 1723200000, "exp": 1723286400 } // Taille token : ~829 octets (vs 16 453 avec permissions) // Permissions résolues côté serveur à chaque requête (cached)

2.4 — MFA TOTP

Configuration TOTP

Algorithme : HMAC-SHA1
Période : 30 secondes
Chiffres : 6
Tolérance : ±1 période (fenêtre 90s)
Secret : AES-256-GCM (chiffré en base)
Backup codes : 10 codes, 8 hex chars, usage unique

Sécurité du secret

Clé de chiffrement : SHA256(MFA_PEPPER + JWT_SECRET)
Stockage : Colonne secret chiffrée AES-256-GCM dans mfa_configs
IV : 16 bytes aléatoires par chiffrement
Auth tag : GCM authentication tag
Format : iv:authTag:encrypted (base64)

2.5 — Protection contre les attaques

Lockout par identifiant

5 tentatives échouées → verrouillage 15 minutes. Compteur dans login_attempts. Reset après succès.

Lockout par IP

20 tentatives échouées depuis la même IP → verrouillage 1 heure. Protection contre brute-force distribué.

Rate Limiting

Token bucket par etablissementId. Limites par plan : Gratuit=100, Standard=500, Premium=2000, Enterprise=3000 req/min.

Détection SQLi

Regex patterns détectent OR 1=1, UNION SELECT, --, ; dans les identifiants de login.

4 Isolation Multi-Tenant — 4 couches

L'isolation des données entre établissements est assurée par 4 couches de défense en profondeur. Chaque couche est indépendante — la compromission d'une seule ne suffit pas à accéder aux données d'un autre tenant.

Couche 1 — HTTP Tenant Middleware

Résout req.etablissementId depuis le JWT ou la table utilisateur_etablissements. Valide l'existence de l'établissement. SUPER_ADMIN peut cibler n'importe quel tenant via query param.

1

Couche 2 — Dual CASL Middleware

Injecte req.ability (CASL). Routes /api/platform/* → definePlatformAbility(). Autres routes → defineAbility() avec permissions JWT. Guards granulaires : requireCasl(), requirePlatformCasl().

2

Couche 3 — PostgreSQL Row-Level Security

RLS activé sur 40+ tables via migrations 152→153→164. Policy : "etablissementId"::text = current_setting('app.current_tenant'). Bypass SUPER_ADMIN via sentinelle UUID 000...000. Bypass GROUP via 000...001.

3

Couche 4 — TypeORM Subscriber (ORM)

tenant-isolation.subscriber.ts — beforeInsert : auto-inject etablissementId depuis AsyncLocalStorage. beforeUpdate : overwrite silencieux si mismatch. afterLoad : audit-only.

4

6.1 — Cycle de vie des données de sécurité

Audit Logs

Création : Automatique sur chaque action critique (130+ types)
Rétention : 30 jours en base active → archivage dans audit_logs_archive
Purge : 365 jours → suppression définitive (cron quotidien 02:00)
Metadata : JSONB extensible (IP, user-agent, browser, OS, device)

Sessions Plateforme

Création : À chaque login plateforme réussi
Limite : Max 3 sessions actives par utilisateur (LRU — la plus ancienne est révoquée)
Expiration : 24h par défaut, configurable
Nettoyage : Cron supprime les sessions expirées

Actions Critiques

Création : Demande d'action sensible → statut EN_ATTENTE
Approbation : Code MFA TOTP requis, max 5 tentatives
Expiration : 24h → statut EXPIREE (cron)
Exécution : Après approbation → statut EXECUTEE + résultat JSONB

Login Attempts

Création : Chaque tentative échouée (par identifiant + par IP)
Seuil identifiant : 5 échecs → lockout 15 min
Seuil IP : 20 échecs → lockout 1h
Reset : Automatique après login réussi

9 Failles & Gaps identifiés

9 failles identifiées lors de l'audit, classées par sévérité. Chaque faille inclut une recommandation de correction.

CRITIQUE G1 — Fallback RLS vers SUPER_ADMIN

Fichier : rls.middleware.ts — resolveTenantId()

Quand aucun contexte tenant n'est trouvé dans la requête, le middleware fallback vers la sentinelle SUPER_ADMIN (000...000), ce qui bypass le RLS. Un bug dans la chaîne de résolution pourrait permettre un accès cross-tenant silencieux.

Recommandation : Remplacer le fallback par un rejet explicite (403) quand aucun tenant n'est résolu et que l'utilisateur n'est pas SUPER_ADMIN. Logger en CRITICAL.

CRITIQUE G2 — Routes backup sans CASL guard

Fichier : platform.routes.ts

Les routes /api/platform/configuration/backup/* n'ont pas de guard CASL. Tout membre de la plateforme (même OBSERVATEUR) peut créer/restaurer des backups de n'importe quel tenant.

Recommandation : Ajouter requirePlatformCasl('manage', 'Backup') sur les routes backup/restore. Restreindre la restauration aux rôles SUPER_ADMIN et ADMIN_PLATEFORME.

CRITIQUE G3 — Path traversal dans restore backup

Fichier : backup.controller.ts

Le paramètre backupPath est passé depuis le body de la requête sans validation. Un attaquant pourrait injecter un chemin arbitraire (../../etc/passwd) pour lire des fichiers système.

Recommandation : Valider que le chemin est dans le répertoire de backup autorisé. Utiliser path.resolve() + vérification du préfixe. Rejeter les chemins contenant ...

MODÉRÉ G4 — Rate limiter non cluster-safe

Fichier : rate-limit.middleware.ts

Le rate limiter utilise une Map en mémoire. En cluster (multi-processus Node), chaque processus a son propre compteur → un attaquant peut contourner la limite en répartissant les requêtes.

Recommandation : Migrer vers un rate limiter Redis-based (ex: rate-limit-redis) pour un compteur partagé entre tous les processus.

MODÉRÉ G5 — Cross-tenant update silencieux

Fichier : tenant-isolation.subscriber.ts

Le subscriber TypeORM beforeUpdate écrase silencieusement le etablissementId s'il ne correspond pas au contexte tenant. Au lieu de rejeter la requête (403), il corrige en silence — masquant les bugs applicatifs.

Recommandation : En mode strict (production), lever une erreur au lieu d'écraser silencieusement. Ajouter un flag STRICT_TENANT_ISOLATION activable par environnement.

MODÉRÉ G6 — Données JWT potentiellement stale

Fichier : tenant.middleware.ts

La vérification cross-tenant utilise le tableau etablissements du JWT, qui peut être périmé si l'utilisateur a été ajouté/retiré d'un établissement après l'émission du token.

Recommandation : Vérifier systématiquement contre la base de données (table utilisateur_etablissements) au lieu de faire confiance au JWT. Accepter le coût DB car c'est déjà fait en fallback.

MODÉRÉ G7 — 5 rôles plateforme sans CASL tenant

Fichier : shared/src/casl/abilities.ts

Les 5 rôles plateforme (ADMIN_PLATEFORME, SUPPORT, OBSERVATEUR, GESTIONNAIRE_GROUPES, FACTURATION) n'ont pas de règles CASL dans defineAbility() (Data Plane). Si un membership les assigne aussi à un contexte tenant, ils n'auront aucune permission contextuelle.

Recommandation : Ajouter des règles CASL minimales pour les rôles plateforme dans le contexte tenant, ou interdire les doubles memberships (plateforme + tenant) pour ces rôles.

MINEUR G8 — Commentaires trompeurs dans platform.routes.ts

Fichier : platform.routes.ts

Plusieurs commentaires indiquent "SUPER_ADMIN uniquement" alors que les routes sont accessibles à tout rôle plateforme disposant de la permission. Le code est correct (guard requirePlatformAccess()), mais les commentaires sont trompeurs pour les développeurs.

Recommandation : Mettre à jour les commentaires pour refléter la réalité : "Nécessite membership plateforme actif + permission CASL".

MINEUR G9 — dualCaslMiddleware error path

Fichier : dual-casl.middleware.ts

En cas d'erreur lors de la résolution des abilities, le middleware appelle next() sans req.ability. Les routes qui n'utilisent pas de guard CASL explicite continuent sans autorisation.

Recommandation : En cas d'erreur, appeler next(error) pour retourner un 500 au lieu de laisser passer la requête sans ability.

Points forts

Defense-in-depth à 4 couches

L'isolation multi-tenant est assurée par 4 mécanismes indépendants. La compromission d'une seule couche ne suffit pas à accéder aux données d'un autre tenant.

RLS PostgreSQL étendu

40+ tables protégées par RLS avec détection dynamique. Les sentinelles de bypass sont documentées et tracées. C'est la couche la plus robuste.

Audit trail exhaustif

130+ actions auditées, metadata JSONB riche, rétention avec archivage automatique. La traçabilité est excellente pour l'investigation post-incident.

MFA + Actions critiques 2FA

8 opérations sensibles exigent une double approbation MFA. Le système TOTP est implémenté correctement (HMAC-SHA1, fenêtre 90s, backup codes chiffrés).

Points faibles

Fallback RLS dangereux

Le fallback vers SUPER_ADMIN quand aucun tenant n'est résolu est un risque de privilege escalation. C'est la faille la plus critique à corriger.

Routes backup non protégées

Tout membre de la plateforme peut accéder aux backups de tous les tenants. Le path traversal dans restore est un risque d'exécution de code.

Rate limiter non distribué

En cluster, le rate limiting est inefficace car chaque processus a son propre compteur. Un attaquant peut contourner la limite.

Permissions JWT stale

Les permissions sont résolues côté serveur (bon), mais le tableau etablissements du JWT n'est pas vérifié en base à chaque requête.
