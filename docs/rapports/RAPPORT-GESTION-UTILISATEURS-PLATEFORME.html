Faille critique : Le SUPER_ADMIN actuel détient Object.values(Permission) — soit ~230 permissions incluant toutes les permissions tenant. Un compromis du compte SUPER_ADMIN donne accès à tous les établissements et toutes les fonctionnalités.

Points forts conservables

✅ Séparation route-level

Routes /api/platform/* avec guard global SUPER_ADMIN. Séparation clean des endpoints.

✅ RLS PostgreSQL

Isolation DB par etablissementId avec bypass sentinel UUID. Defense-in-depth efficace.

✅ CASL cannot rules

L'ADMIN a des cannot explicites sur Configuration delete, Module toggle, GroupeEtablissement, Monitoring.

◆ Benchmark enterprise

Bonnes pratiques — 8 sources analysées

Recherche approfondie sur les architectures RBAC des principales plateformes SaaS enterprise.

  • Microsoft Azure AD — Control Plane / Data Plane
    Séparation physique des identités : comptes organisation (tenant) vs comptes invité (externes). RBAC distinct par plan. Global Admin ≠ Directory Reader.
  • Auth0 — Tenant = Platform, Organization = Customer
    Modèle à 2 niveaux : le tenant Auth0 = la plateforme SaaS, les Organizations = les clients. Roles et Permissions séparés par niveau. B2B SaaS reference architecture.
  • WorkOS — Roles tied to Organizations
    Roles toujours scopés à une Organization. Un utilisateur peut avoir des rôles différents dans chaque Organization. Admin Connection pour le SSO enterprise.
  • Cerbos — Externalized PDP
    Policy Decision Point externalisé. Principals ont des roles + attributes. Resources ont des types. Policies définissent qui peut faire quoi sur quoi. Séparation complète authZ/authN.
  • Aserto — Three-Entity Model
    Users, Roles, Permissions comme 3 entités distinctes avec relations M:N. Support natif du multi-tenancy via directory instances séparées.
  • SuperTokens — Dedicated User Pools
    User pools dédiés par tenant. Chaque tenant a son propre espace d'utilisateurs. Platform users dans un pool séparé (admin pool).
  • Clerk — Organization Model
    Users appartiennent à des Organizations avec des memberships et roles. Platform admins = membres d'une "platform organization" spéciale.
  • Next.js SaaS Starter — Role-Based Access
    Pattern communautaire : table users avec role enum + table organizations + junction organization_members avec role par org. Simple et efficace.

◆ Propositions d'architecture

3 modèles de séparation

Trois approches progressives, de la moins invasive (réorganisation logique) à la plus complète (séparation physique totale). Chaque modèle est auto-portant et peut être implémenté indépendamment.

A

Modèle Hybride — Séparation logique (recommandé)

Une seule table utilisateurs + scope tagging sur permissions + rôles plateforme activés. Effort modéré, impact maximal.

Principe

Conserver la table utilisateurs unique mais ajouter un champ scope ('platform' | 'tenant' | 'both'). Les permissions sont taguées par scope. Les rôles plateforme sont activés avec leurs permissions propres.

Modèle de données

+ scope: platform|tenant|both
utilisateur_etablissements (junction)
roles_tenant
scope = 'tenant'
roles_plateforme
scope = 'platform'
permissions_tenant
~190 perms
permissions_plateforme
~40 perms

Avantages

  • Migration douce — pas de split de table, pas de changement d'auth flow
  • Rétro-compatible — les utilisateurs existants continuent de fonctionner
  • Scope tagging — les permissions sont clairement étiquetées platform/tenant
  • UI séparée — la matrice RBAC affiche 2 vues distinctes

Inconvénients

  • Table unique = risque de confusion si un user a scope='both'
  • Le SUPER_ADMIN reste un super-user avec toutes les permissions

B

Modèle Dual-Table — Séparation physique totale

Deux tables utilisateurs distinctes : utilisateurs_plateforme et utilisateurs (tenant). Auth flow séparé. Isolation complète.

Principe

Créer une table utilisateurs_plateforme dédiée aux admins de la plateforme. Ces utilisateurs n'ont aucun lien avec les établissements. Leur auth flow est séparé (endpoint /api/platform/auth/login, JWT avec claim scope: 'platform').

Avantages

  • Isolation totale — un compromised tenant admin ne peut pas accéder à la plateforme
  • Auth flow dédié — MFA obligatoire pour les platform users, optionnel pour tenant
  • Audit clair — les logs plateforme et tenant sont naturellement séparés
  • Conformité — répond aux exigences SOC2/ISO27001 de séparation des accès

Inconvénients

  • Migration lourde — extraction des platform users existants, création de la nouvelle table
  • Double auth — un utilisateur qui est à la fois platform admin et tenant user doit se connecter 2 fois
  • Complexité — 2 systèmes de session, 2 middleware d'auth, 2 JWT validators

C

Modèle Auth0 — Organizations + Platform Directory

Inspiré d'Auth0/WorkOS : un « Platform Directory » séparé + les établissements comme « Organizations ». Le plus aligned enterprise.

Principe

S'inspirer du modèle Auth0 B2B : la plateforme SaaS est un « Directory » supérieur qui contient des « Organizations » (établissements). Les platform users sont dans le Directory, les tenant users sont dans leur Organization.

Modèle conceptuel

Implémentation concrète pour eLISAschool

  • utilisateurs_plateforme = Platform Directory (table séparée)
  • utilisateurs = Organization Members (table existante, rebaptisée conceptuellement)
  • etablissements = Organizations (table existante)
  • utilisateur_etablissements = Organization Memberships (junction existante)
  • Les rôles dans roles avec etablissementId = null = Platform Roles
  • Les rôles dans roles avec etablissementId = uuid = Organization Roles

Avantages

  • Alignement enterprise — modèle éprouvé par Auth0, WorkOS, Clerk
  • Extensibilité — facile d'ajouter des « Organization types » (groupes, sous-traitants)
  • Marketplace-ready — si eLISAschool vend des modules, le modèle supporte les « vendor users »

Inconvénients

  • Complexité maximale — 2 auth flows, 2 tables users, concept d'Organization à introduire
  • Over-engineering risk — pour un SaaS scolaire camerounais, le modèle Auth0 peut être excessif
  • Migration la plus longue — estimation 3-4 semaines de développement
◆ Recommandation

Modèle recommandé : A → B progressif

🎯 Stratégie en 2 temps

Commencer par le Modèle A (séparation logique, ~1 semaine) puis migrer vers le Modèle B (dual-table, ~2 semaines) quand la base utilisateurs plateforme sera définie.

Plan d'implémentation — Modèle A

5 phases incrémentales, chaque phase est déployable indépendamment.

Phase 1 — Scope tagging (2 jours)
Taguer toutes les permissions par scope
Ajouter un attribut scope: 'platform' | 'tenant' | 'shared' à chaque entrée de l'enum Permission. Créer un helper isPlatformPermission() et isTenantPermission().
shared/src/enums/roles.enum.ts shared/src/enums/permission-scope.ts
Phase 2 — Rôles plateforme activés (2 jours)
Définir les permissions des 5 rôles plateforme
Ajouter les entrées DEFAULT_ROLE_PERMISSIONS pour ADMINISTRATION_PLATEFORME, SECURITE_PLATEFORME, SUPPORT_PLATEFORME, COMMERCIAL_PLATEFORME, MONITORING_PLATEFORME. Ajouter GESTIONNAIRE_GROUPES à l'enum Role. Mettre à jour le guard platform.routes.ts pour accepter ces rôles.

Phase 3 — Page utilisateurs plateforme (3 jours)
CRUD complet des utilisateurs plateforme
Créer la page /platform/utilisateurs avec DataTable, filtres par rôle/statut, modal création (email, rôle plateforme, MFA obligatoire), actions (activer/désactiver/reset MFA). Backend : endpoints /api/platform/utilisateurs avec guard SUPER_ADMIN.

Phase 4 — Matrice RBAC séparée (2 jours)
2 vues dans la page Permissions
Ajouter un toggle « Plateforme / Tenant » en haut de la matrice. La vue Plateforme n'affiche que les 6 rôles plateforme + leurs permissions. La vue Tenant affiche les 62 rôles tenant. Filtrage par scope côté backend.

MFA obligatoire + audit + least privilege
Rendre MFA obligatoire pour tous les rôles plateforme. Restreindre SUPER_ADMIN aux seules permissions plateforme (retirer les permissions tenant). Ajouter les règles CASL pour les 5+1 rôles plateforme.

◆ Alternatives explorées

Autres approches considérées

🔌 Externalized PDP (Cerbos-style)

Déléguer toute la logique d'autorisation à un service externe (Cerbos, OPA). Séparation complète authN/authZ.

Complexité élevée Infrastructure supplémentaire

Verdict : Rejeté — over-engineering pour un SaaS scolaire. CASL.js suffit.

📚 ABAC pur (attributes-based)

Remplacer RBAC par ABAC : chaque décision basée sur des attributs (rôle, établissement, module, heure). Plus granulaire mais plus complexe.

Courbe d'apprentissage Très flexible

Verdict : Complémentaire. CASL supporte déjà ABAC via les conditions. À enrichir progressivement.

🔗 Multi-tenant via claims JWT

Stocker toutes les permissions dans le JWT (pas de lookup DB). Plus rapide mais tokens lourds (déjà rencontré : 16KB → 431).

Token trop lourd Invalidation impossible

Verdict : Rejeté — le bug HTTP 431 a déjà montré les limites. Permissions résolues côté serveur.

🛡 Zero-Trust per-request

Chaque requête re-vérifie toutes les permissions depuis la DB. Sécurité maximale mais latence ajoutée.

Latence +5-10ms/req Sécurité max

Verdict : Partiellement en place via le cache permissions (Redis TTL). Suffisant pour le moment.
