3 Benchmark editeurs visuels

Comparaison approfondie des 3 principaux editeurs open source compatibles React 19, avec analyse d'integration dans l'architecture eLISAschool.

Puck Editor

MIT · @puckeditor/core v0.23.0 · ~117K downloads/sem

  • React-native — composants = composants React
  • API fields/render elegante et typee
  • Plugin rail system (insertion zones)
  • JSON serializable (compatible CmsSection.contenu)
  • Utilise @dnd-kit en interne (deja dans eLISAschool)
  • AI Copilot integre (optionnel)
  • Active development (v0.23, release frequente)
  • Vertical-only layouts (pas de grid 2D libre)
  • Client-side rendering uniquement
  • CSS scoping necessaire pour eviter les conflits

GrapesJS

BSD-3 · v0.23.5 · ~251K downloads/sem

  • Framework-agnostic (pas React-native)
  • UI complete out-of-the-box
  • Style editor + Layer manager + Code editor
  • Export HTML/CSS propre
  • Wrapper @grapesjs/react v2.x (React 19)
  • NE PEUT PAS render React components dans le canvas
  • Modele de donnees proprietaire (migration complexe)
  • Integration frontend lourde (2 modeles de donnees)
  • DOM manipulation directe (conflits avec React)

Craft.js

MIT · v0.2.12 · ~8K downloads/sem

  • Fully React-native (hooks useNode, useEditor)
  • JSON state serialization
  • 100% custom — controle total sur l'UI
  • Flexible — pas de contraintes de layout
  • Pre-1.0 — stabilite incertaine
  • AUCUNE UI pre-construite (tout a construire)
  • Documentation incomplete
  • Communaute petite (8K vs 117K/251K)
  • Effort d'implementation 3-5x superieur

Implementation du resolver

// backend/src/modules/cms/services/data-binding.service.ts

export class DataBindingService {
  private cache = new Map<string, { value: any; ts: number }>();
  private readonly TTL = 60_000; // 60 secondes

  /**
   * Resout toutes les variables {{}} dans le contenu d'une section
   * Ex: "Bienvenue a {{etablissement.nom}}" → "Bienvenue a Lycée Bilingue"
   */
  async resoudreContenu(
    contenu: Record<string, any>,
    etablissementId: string
  ): Promise<Record<string, any>> {
    const contexte = await this.getContexte(etablissementId);
    return this.resoudreRecursive(contenu, contexte);
  }

  /**
   * Construit le contexte de donnees pour un etablissement
   * Cache 60s pour eviter de surcharger la DB
   */
  private async getContexte(etabId: string): Promise<BindingContexte> {
    const cacheKey = `cms:binding:${etabId}`;
    const cached = this.cache.get(cacheKey);
    if (cached && Date.now() - cached.ts < this.TTL) return cached.value;

    const [etablissement, statsEleves, personnel, statsNotes] = await Promise.all([
      this.getEtablissement(etabId),
      this.getStatsEleves(etabId),
      this.getPersonnel(etabId),
      this.getStatsNotes(etabId),
    ]);

    const contexte = { etablissement, eleves: statsEleves, personnel, stats: statsNotes };
    this.cache.set(cacheKey, { value: contexte, ts: Date.now() });
    return contexte;
  }

  /**
   * Resolution recursive — parcourt tous les niveaux du JSON
   * Detecte les patterns {{variable.chemin}} et les remplace
   */
  private resoudreRecursive(obj: any, ctx: BindingContexte): any {
    if (typeof obj === 'string') return this.resoudreString(obj, ctx);
    if (Array.isArray(obj)) return obj.map(item => this.resoudreRecursive(item, ctx));
    if (typeof obj === 'object' && obj !== null) {
      const result: any = {};
      for (const [key, value] of Object.entries(obj)) {
        result[key] = this.resoudreRecursive(value, ctx);
      }
      return result;
    }
    return obj;
  }
}
ⓘ

Flux de resolution : Le data binding s'execute cote backend lors du rendu public (API /api/public/e/:code/*). Les pages sont servies deja resolues au frontend. Le cache Redis (TTL 300s) evite de recalculer a chaque requete. Cote editeur, les variables sont affichees en l'etat ({{etablissement.nom}}) avec un apercu en temps reel via un endpoint dedie GET /api/cms/pages/:id/preview-binding.

6 Securite & correctifs critiques

Plan de correction des 3 failles critiques et 4 failles majeures identifiees dans l'audit.

P0 — Failles critiques (a corriger AVANT toute nouvelle fonctionnalite)

CRITIQUE

XSS via dangerouslySetInnerHTML

Fichier : CmsPageRenderer.tsx (lignes ~420 et ~980)
Probleme : Les sections TexteSection et HtmlCustomSection utilisent dangerouslySetInnerHTML sans aucune sanitization. Un admin malveillant (ou un compte compromis) peut injecter du JavaScript qui s'execute sur tous les visiteurs de la page publique. 

// FIX — Ajouter DOMPurify
import DOMPurify from 'dompurify';

// Avant (vulnerable) :
<div dangerouslySetInnerHTML={{ __html: contenu.html }} />

// Apres (securise) :
<div dangerouslySetInnerHTML={{
  __html: DOMPurify.sanitize(contenu.html, {
    ALLOWED_TAGS: ['p','br','strong','em','u','h1','h2','h3','h4','ul','ol','li','a','img','blockquote','pre','code'],
    ALLOWED_ATTR: ['href','src','alt','class','target','rel'],
  })
}} />
CRITIQUE

RBAC non enforce — 18 permissions ignorees

Fichier : cms.controller.ts (33 routes)
Probleme : Seules les permissions authMiddleware sont appliquees. Les 18 permissions RBAC definies dans la migration 182 (cms:pages:create, cms:sections:delete, etc.) ne sont JAMAIS verifiees. 

// FIX — Ajouter requirePermission sur chaque route
router.post('/pages',
  authMiddleware,
  requirePermission('cms:pages:create'),  // AJOUTER
  requireModuleActive('cms'),
  async (req, res, next) => { ... }
);

// Matrice des permissions a appliquer :
// GET    /pages         → cms:pages:view
// POST   /pages         → cms:pages:create
// PATCH  /pages/:id     → cms:pages:edit
// DELETE /pages/:id     → cms:pages:delete
// POST   /pages/:id/publish → cms:pages:publish
// POST   /sections      → cms:sections:create
// PATCH  /sections/:id  → cms:sections:edit
// DELETE /sections/:id  → cms:sections:delete
// POST   /medias/upload → cms:medias:upload
// ... etc (18 routes au total)
CRITIQUE

Pas de vrai drag & drop (boutons up/down uniquement)

Fichier : _auth.cms.pages.$id.tsx
Probleme : L'editeur affiche des icones GripVertical mais elles sont purement decoratives. Le reordonnement se fait via des boutons fleche up/down. Aucun handler DnD n'est attache.

Solution : Integration de Puck Editor qui fournit nativement le DnD via @dnd-kit (dependance deja presente dans le projet pour l'EDT). Voir section 4 pour l'architecture cible.

Integration Puck Editor

• Installer @puckeditor/core + creer la config (18 composants Puck)

Data Binding & donnees dynamiques

Phase P4 — 1 semaine

Polish, type safety & performance

• Creer 18 interfaces typees (HeroSectionContent, TexteSectionContent, ...)
