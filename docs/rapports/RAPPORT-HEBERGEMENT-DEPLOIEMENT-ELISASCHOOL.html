2. Fondamentaux de l'Hébergement Web
Comment fonctionne l'hébergement d'une application web moderne
Principe fondamental

L'hébergement web consiste à rendre une application accessible sur Internet 24h/24. Un serveur (machine physique ou virtuelle) exécute le code applicatif, stocke les données dans une base, et répond aux requêtes HTTP des utilisateurs via un reverse proxy (Nginx, Caddy). Pour une application SaaS multi-tenant comme eLISAschool, l'hébergement doit garantir : isolation des données (RLS PostgreSQL), disponibilité (SLA 99.9%), scalabilité (montée en charge progressive), et sécurité (chiffrement, certificats TLS, pare-feu).

🔄 Cycle de vie d'une requête
1 DNS — domain → IP du serveur
2 TLS — Handshake HTTPS (Let's Encrypt)
3 Reverse Proxy — Nginx route vers le backend
4 Middleware — Auth JWT, RLS tenant, rate limit
5 Cache — Redis hit ? → réponse directe
6 PostgreSQL — Query + RLS policy → résultat

⚠️

Hébergement mutualisé : incompatible avec eLISAschool

L'hébergement mutualisé ne supporte pas Node.js/Express, ne permet pas d'installer PostgreSQL/Redis, et ne fournit pas les accès root nécessaires pour Docker, PgBouncer ou la configuration RLS. À exclure totalement.

✅ Recommandé pour eLISAschool

Stratégie hybride optimale

  • VPS/Dédié pour l'application (contrôle total)
  • DB managée ou VPS SSD NVMe (IOPS élevés)
  • Redis sur le même serveur ou managé
  • CDN pour le frontend statique (Cloudflare)
  • Docker Compose pour l'orchestration
  • Backups automatisés (S3 ou local)
    • ❌ À éviter

    Pièges courants

  • Hébergement mutualisé (pas de Node.js)
  • VPS HDD au lieu de SSD NVMe (IOPS ×100 moins)
  • Single point of failure sans backup
  • Cloud AWS complet sans expertise (coût ×3-5)
  • PaaS sans contrôle DB (RLS non supporté)
  • Serverless pour app stateful (WebSocket, cron)

    5. Architecture d'Hébergement Idéale
    Structure optimisée pour eLISAschool — scalable, sécurisée, maintenable
    💡

    Architecture mono-serveur puis multi-nœuds

    Pour 1 000–5 000 utilisateurs, un seul VPS (4-8 vCPU, 8-16 GB RAM) suffit avec Docker Compose. Au-delà de 5 000, séparer la DB sur un serveur dédié ou managé, et ajouter un load balancer Nginx devant 2+ nœuds applicatifs. Le RLS PostgreSQL garantit l'isolation multi-tenant sans modification applicative.

    🔒 Souveraineté & Conformité

    Le Cameroun a adopté la loi n° 2010/012 sur les communications électroniques et la loi n° 2010/013 sur la cybersécurité. L'OHADA harmonise le droit commercial. Points clés :

    • Données personnelles — Pas encore de loi type RGPD, mais les tendances réglementaires vont vers la localisation. Un DC européen (France) est acceptable et rassurant.
    • Données scolaires — Les données des élèves (mineurs) nécessitent une protection renforcée. Le chiffrement AES-256-GCM d'eLISAschool + RLS PostgreSQL satisfont ces exigences.
    • Facturation OHADA — La TVA 19.25% et la numérotation des factures sont gérées applicativement. Pas de contrainte d'hébergement local.
    • Paiements mobile money — MTN MoMo, Orange Money, Wave : les APIs sont accessibles depuis l'Europe sans latence supplémentaire significative.
    • Backups — Stocker dans un DC différent du DC principal (ex: principal à Paris, backup à Helsinki/Hetzner) pour la résilience.

    Stratégie d'hébergement optimale pour eLISAschool
    🏆 Stratatégie recommandée : Hetzner (EU) + Cloudflare Best Value

    Pour eLISAschool, le rapport performance/prix de Hetzner est inégalé (~60% moins cher que DigitalOcean pour des performances supérieures). La localisation européenne (Frankfurt/Helsinki) offre une latence optimale vers le Cameroun. Cloudflare en CDN complète parfaitement l'offre.

    Phase 1 — Lancement (0 → 1 000 users)
    1× Hetzner CX32 (€7.99/mo) + Storage Box 50 GB (€3.81/mo) + Cloudflare Free
    Coût total : ~€15/mo — Docker Compose mono-serveur, tout-en-un
    Phase 2 — Croissance (1 000 → 5 000 users)

    Coût total : ~€250/mo — Load balancing, Redis cluster, replication DB

    9. Stratégie de Déploiement
    Pipeline CI/CD, environments, et bonnes pratiques de mise en production
    🔄 Pipeline CI/CD recommandé
    1. Git Push → GitHub Actions
    Lint + TypeScript check + tests unitaires (jest)
    2. Build Docker
    Image multi-stage (build → runtime slim). Tag = git SHA.
    3. Déploiement staging
    Pull image, docker-compose up, health check, smoke tests
    4. Déploiement production
    Rolling update (0 downtime), migration DB avant, rollback automatique si health check échoue
    🛡️ Checklist de sécurité production
    ✓ HTTPS obligatoire (Cloudflare SSL strict)
    ✓ JWT_SECRET_PLATFORM + JWT_SECRET_TENANT ≥ 32 chars
    ✓ ENCRYPTION_KEY ≥ 32 chars (AES-256-GCM)
    ✓ RLS activé sur toutes les tables avec etablissementId
    ✓ Firewall : seuls ports 22 (SSH), 80, 443 ouverts
    ✓ SSH par clé uniquement (PasswordAuthentication no)
    ✓ Fail2ban installé (brute force protection)
    ✓ Backups chiffrés quotidiens testés (restauration mensuelle)
    ✓ IP Allowlist pour l'accès plateforme (fail-closed)
    ✓ Rate limiting par plan (100-3000 req/min)
    📦 Structure Docker Compose recommandée
    services:
      app:
        image: elisaschool-api:latest
        restart: unless-stopped
        ports: ["3000:3000"]
        environment:
          NODE_ENV: production
          DB_HOST: db
          REDIS_URL: redis://cache:6379
        depends_on: [db, cache]

      db:
        image: postgres:16-alpine
        volumes: [pgdata:/var/lib/postgresql/data]
        shm_size: 256mb
        command: postgres -c shared_buffers=256MB -c max_connections=200

      cache:
        image: redis:7-alpine
        command: redis-server --maxmemory 1gb --maxmemory-policy allkeys-lru

      proxy:
        image: nginx:alpine
        ports: ["80:80", "443:443"]
        volumes: [./nginx.conf:/etc/nginx/nginx.conf:ro]
        depends_on: [app]
