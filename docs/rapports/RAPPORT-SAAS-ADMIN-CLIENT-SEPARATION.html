Resume executif

Verdict global

eLISAschool dispose d'une base technique solide pour le multi-tenant (cascade de configuration a 3 niveaux, resolution serveur des permissions, detection cross-tenant). Cependant, la separation entre espace client (etablissement) et panel proprietaire de la plateforme est insuffisante. Les roles ADMIN et SUPER_ADMIN cumulent des permissions operatives (gestion etablissement) et des permissions plateforme (activation modules, audit global, monitoring infrastructure) sans cloisonnement structurel.

5.5/10
Maturite partielle — Les fondations sont la, mais le cloisonnement proprietaire/client et la separation des plans d'administration necessitent une refonte structurelle avant la mise en production multi-tenant.

Synthese en 3 points

  • Pas de separation structurelle : une seule arborescence de routes (_auth/), un seul sidebar, un seul contexte utilisateur. Les items plateforme (Roles, Audit, Monitoring) cohabitent avec les items client (Finances, Transport) sans cloisonnement visuel ni technique.
  • Permissions trop larges : le role ADMIN dispose de 230+ permissions dont des operations plateforme (toggle modules, backup/restore, config globale). SUPER_ADMIN et ADMIN bypassent toutes les gardes frontend, ce qui rend tout audit de permissions inoperant pour ces roles.
  • Isolation multi-tenant fonctionnelle mais perfectible : le filtrage par etablissementId est applique systematiquement dans les services, et la detection cross-tenant est en place. Mais certains endpoints (configuration publique, stats etablissement) sont accessibles sans guard adequat.

Points forts actuels

Cascade de configuration 3 niveaux

ParametreSysteme avec resolution : etablissement (priorite 1) → global (fallback) → MODULE_REGISTRY (defaut). Permet aux clients de personnaliser sans toucher au global.

Resolution serveur des permissions

Les permissions ne sont PAS dans le JWT (evite le gonflement a 16KB). permissionResolverService avec cache Redis 5 min + in-memory. Toutes les verifications sont cote serveur.

Detection cross-tenant

filterByEtablissement() force l'etablissementId depuis le token et logue les tentatives d'acces inter-etablissements avec alerte CROSS_TENANT_ACCESS_DENIED.

Multi-etablissement natif

Table de jointure utilisateur_etablissements, modal de selection, switchEtablissement() dans le store. Un utilisateur peut appartenir a plusieurs etablissements.

Activation modules middleware

requireModuleActive() protege chaque route de module. 4 modules critiques exemptes (auth, utilisateurs, configuration, notifications). Cascade 3 niveaux pour la resolution.

Soft delete systematique

19 tables transactionnelles avec @DeleteDateColumn(). Les nomenclatures systeme sont protegees par assertNotSystem() (backend) et UI adaptee (bouton supprimer cache).

Audit RBAC — 9 failles

RBAC-1 : DIRECTEUR — permissions cross-tenant Critique
Le role DIRECTEUR possede les 9 permissions GROUPES_ETABLISSEMENTS_* qui permettent de gerer des groupes d'etablissements. Un directeur d'etablissement client ne devrait jamais avoir de visibilite sur d'autres etablissements.
Impact : Un client peut voir et modifier la composition de groupes multi-etablissements, accedant indirectement aux donnees d'autres clients.
Creer un role dedie DIRECTEUR_GROUPE (portee plateforme) et retirer ces permissions du role DIRECTEUR client.
RBAC-2 : ADMIN — permissions plateforme Haute
Le role ADMIN (client) dispose de CONFIG_APP_EDIT, CONFIG_MODULE_TOGGLE, CONFIG_PARAM_CREATE/EDIT/DELETE/RESET, CONFIG_BACKUP_CREATE/RESTORE. Ces operations sont de portee plateforme et ne devraient etre accessibles qu'au proprietaire (SUPER_ADMIN).
Impact : Un admin client peut activer/desactiver des modules globalement, modifier la configuration applicative, et creer/restaurer des backups de la plateforme entiere.
Spliter les permissions config en 2 tiers : config:etablissement:* (client, parametres scopés) et config:plateforme:* (proprietaire, global).
RBAC-3 : ADMIN — acces monitoring infrastructure Haute
NETWORK_ADMIN attribue a ADMIN donne acces aux metriques infrastructure (latence DB, memoire serveur, sondes internet). Ces donnees revelent l'architecture technique de la plateforme.
Impact : Exposition d'informations sensibles sur l'infrastructure hebergeant tous les clients.
Restreindre NETWORK_ADMIN a SUPER_ADMIN uniquement. Creer NETWORK_VIEW (statut connexion) pour les clients.
RBAC-4 : TECHNICIEN_INFO — config view Moyenne
TECHNICIEN_INFO a CONFIG_VIEW et MONITORING_VIEW. Ce role est cense etre un role client technique, pas un administrateur plateforme.
Limiter aux parametres scopes a l'etablissement. Retirer MONITORING_VIEW.
RBAC-5 : AUDITEUR_INTERNE — config + roles view Moyenne
AUDITEUR_INTERNE a CONFIG_VIEW, ROLES_VIEW, MONITORING_VIEW. Un auditeur client ne devrait auditer que les operations de son etablissement.
Scoper l'audit aux logs de l'etablissement. Retirer les permissions config et monitoring globales.
RBAC-6 : STATISTICIEN — monitoring Moyenne
STATISTICIEN possede des permissions MONITORING_*. Le role devrait se limiter aux statistiques metier, pas a l'infrastructure.
Retirer toutes les permissions MONITORING_* du role STATISTICIEN.
RBAC-7 : COMPTABLE — audit multi-modules Basse
COMPTABLE a des permissions d'audit sur des modules non-financiers (classes, eleves, etc.). Principe de moindre privilege viole.
Limiter l'audit comptable aux modules financiers (paie, bulletins, cotisations).
RBAC-8 : SUPER_ADMIN_ALL non utilise Basse
La permission super_admin:all est definie dans l'enum mais n'est jamais attribuee dans DEFAULT_ROLE_PERMISSIONS. Code mort qui prete a confusion.
Supprimer la definition ou documenter son usage prevu.
RBAC-9 : Pas de separation SUPER_ADMIN / ADMIN Basse (design)
SUPER_ADMIN et ADMIN partagent la majorite des permissions admin. La distinction actuelle est principalement dans le bypass frontend et la portee multi-etablissement. Pas de modele formel de "proprietaire plateforme" vs "admin etablissement".
Definir un modele a 3 niveaux : Super Admin (plateforme) → Tenant Admin (etablissement) → Tenant User.

Configuration & Isolation — 7 failles

CFG-1 : Endpoint configuration sans authentification Moyenne
GET /api/configuration (controller configuration, ligne 68) n'a pas de authMiddleware. Retourne tous les parametres globaux visibles a tout appelant non authentifie.
Impact : Exposition de la configuration globale de la plateforme (langue defaut, modules actifs, etc.) a des acteurs non authentifies.
Ajouter authMiddleware ou limiter strictement les parametres retournes aux seuls parametres publics documentes.
CFG-2 : Categories parametres sans garde Moyenne
GET /api/configuration/parametres/categories (ligne 328) n'a que authMiddleware sans requirePermission. Tout utilisateur authentifie peut lister les categories de configuration.
Ajouter requirePermission('config:view').
CFG-3 : Stats etablissement accessibles Basse
GET /api/etablissements/:id, /:id/config, /:id/stats sont accessibles a tout utilisateur authentifie sans verification d'appartenance a l'etablissement cible.
Ajouter une verification d'appartenance ou restreindre aux roles SUPER_ADMIN/ADMIN de l'etablissement.
CFG-4 : SUPER_ADMIN etablissementId via query Basse (design)
Le tenantMiddleware permet au SUPER_ADMIN de specifier n'importe quel etablissementId via query parameter. Par conception, mais sans validation de la cible existante.
Documenter ce comportement. Ajouter une validation d'existence de l'etablissement cible.
CFG-5 : Pas de RLS PostgreSQL Basse
L'isolation multi-tenant repose entierement sur le code applicatif (WHERE etablissementId = X). Aucune Row-Level Security PostgreSQL en defense-in-depth.
Impact : Un bug dans le code applicatif peut exposer des donnees inter-établissements sans detection au niveau DB.
Implementer RLS sur les tables critiques (eleves, notes, bulletins, personnel) comme couche de securite supplementaire.
CFG-6 : Cache Redis sans prefix tenant Basse
Le cache Redis pour les permissions et la configuration n'utilise pas systematiquement un prefix par etablissement. Risque de collision si deux etablissements ont des parametres homonymes.
Prefixer toutes les cles cache par tenant:{etablissementId}:.
CFG-7 : Pas de quotas d'API par tenant Basse
Le rate limiting est global (pas par tenant). Un etablissement peut consommer tout le quota au detriment des autres.
Implementer un rate limiting par etablissementId avec des quotas proportionnels au plan d'abonnement.

Frontend Permissions — 6 failles

FE-1 : Bypass total SUPER_ADMIN + ADMIN Haute
permission-guards.ts lignes 37-39, 83-85, 141-143, 174-176 : SUPER_ADMIN et ADMIN bypassent toutes les gardes de permission. Cela rend impossible l'audit de ce que ces roles voient ou font, et masque les bugs de permission.
Impact : Si une route est montee sans garde backend, un ADMIN y accedera sans jamais voir de refus. Les erreurs de configuration de permissions sont invisibles.
Remplacer le bypass par une evaluation reelle des permissions. SUPER_ADMIN devrait avoir toutes les permissions attribuees, pas un bypass magique.
FE-2 : 3 routes production sans guard Haute
_auth.finances.tsx, _auth.transport.tsx, _auth.bibliotheque.tsx n'ont aucun beforeLoad guard. Tout utilisateur authentifie peut y acceder independamment des permissions.
Ajouter requirePermission('finances:view'), requirePermission('transport:view'), requirePermission('bibliotheque:view') en beforeLoad.
FE-3 : Pas de separation plateforme/client Haute
Une seule arborescence _auth/ pour tout. Les routes admin plateforme (_auth.admin.roles, _auth.admin.audit) sont dans le meme layout que les routes client. Pas de route tree _platform/ ou _auth.admin/ dedie.
Creer un layout _platform/ separe avec ses propres guards, ou au minimum un sous-layout _auth.admin/ avec guard global.
FE-4 : Sidebar — pas de section plateforme dediee Moyenne
Le Sidebar melange les items plateforme (Roles & Permissions, Audit global) et client (Finances, Transport) dans les memes sections. Pas de separation visuelle ni de section "Administration plateforme" distincte.
Ajouter une section "Administration plateforme" (visible uniquement SUPER_ADMIN) separee des sections "Administration etablissement".
FE-5 : PermissionGate — hook dans conditionnel Moyenne
PermissionGate.tsx ligne 102 : useModulePermissions est appele dans une branche conditionnelle, violant les regles des hooks de React. Peut causer des bugs de rendu imprevisibles.
Deplacer le hook avant tout conditionnel. Utiliser un composant wrapper si necessaire.
FE-6 : Inconsistence sidebar vs route guards Basse
La sidebar utilise useModulePermissions (verifie view OU manage), les route guards utilisent une logique differente (view, read, manage, list). Un item peut etre visible dans la sidebar mais la route refusee, ou l'inverse.
Unifier la logique de verification : un seul helper hasPermission() utilise partout.

Ecart principal

Les meilleures pratiques SaaS 2025-2026 recommandent une separation structurelle entre le plan de gestion de la plateforme (proprietaire) et le plan de gestion des donnees (client). eLISAschool fonctionne avec un modele "plat" ou les deux plans sont fusionnes. C'est la source de la majorite des failles identifiees.

A

Separation structurelle des routes et layouts

Creer un arbre de routes _platform/ distinct du layout client _auth/. Le panel proprietaire a son propre layout, sa propre sidebar, ses propres guards.

Implmentation

  • _platform/dashboard.tsx — Dashboard proprietaire (etablissements, revenus, sante)
  • _platform/etablissements.tsx — CRUD etablissements (cree depuis _auth.admin/)
  • _platform/configuration.tsx — Config applicative globale
  • _platform/monitoring.tsx — Monitoring infrastructure
  • _platform/audit.tsx — Audit global (tous etablissements)
  • _platform/facturation.tsx — Plans, abonnements, quotas
  • Guard global : requireRole('SUPER_ADMIN') en beforeLoad du layout

Avantages

  • Separation visuelle immediate : le proprietaire sait qu'il est dans le panel plateforme
  • Guards centralises au niveau du layout (pas de guard oublie par route)
  • Sidebar dediee : pas de melange des items
  • Facilite l'evolution future (multi-proprietaire, support tickets, etc.)

Efort estime

2-3 semaines — Deplacement de 6-8 routes existantes + creation du layout + migration sidebar

B

Integration CASL.js — Authorization declarative

Remplacer le systeme custom requirePermission() par CASL.js, le standard TypeScript pour l'autorisation. Permet des regles contextuelles (ABAC) en plus du RBAC.

Exemple d'implementation

  • defineAbility(user, etablissementId) — construit les regles en fonction du role ET du contexte
  • can('manage', 'Etablissement') — uniquement si SUPER_ADMIN
  • can('read', 'Note', { etablissementId }) — filtrage automatique par tenant
  • Middleware Express : app.use(caslMiddleware) injecte req.ability
  • Frontend : <Can I="read" a="Note"> remplace PermissionGate

Avantages

  • Regles contextuelles : "un enseignant ne voit que les notes de ses matieres"
  • Testable unitairement (les regles sont des fonctions pures)
  • Partage frontend/backend (meme DSL)
  • Communaute active, documentation exhaustive

Efort estime

3-4 semaines — Definition des ability + migration progressive des controllers + tests

C

PostgreSQL RLS — Defense-in-depth

Ajouter des politiques Row-Level Security sur les tables critiques comme couche de securite supplementaire. Meme si le code applicatif a un bug, la DB refuse les acces cross-tenant.

Politiques a implementer

  • CREATE POLICY tenant_isolation ON eleves USING ("etablissementId" = current_setting('app.current_tenant')::uuid)
  • Appliquer sur : eleves, notes, bulletins, personnel, creneaux_horaires, heures_cours, absences_personnel
  • Set current_tenant dans le middleware tenant : SET LOCAL app.current_tenant = '...'
  • SUPER_ADMIN bypass : SET LOCAL app.current_tenant = '00000000-0000-0000-0000-000000000000' + policy permissive

Avantages

  • Zero trust au niveau DB — aucun bug applicatif ne peut fuir des donnees
  • Transparent pour le code existant (pas de changement de requetes)
  • Auditable : les politiques RLS sont versionnees avec les migrations

Efort estime

1-2 semaines — Migrations SQL + test sur tables critiques

D

Feature flags par tenant + quotas enforcees

Transformer le ParametreSysteme en systeme de feature flags complet avec targeting par tenant, et activer le controle des quotas definis dans EtablissementConfig.

Feature flags

  • Interface FeatureFlagService.isEnabled(flag, etablissementId) avec cache
  • Flags par plan : export_pdf, api_access, multi_etablissements, white_label
  • Override par tenant : un etablissement premium peut avoir des flags supplementaires
  • UI : composant <FeatureFlag flag="export_pdf"> pour masquer/afficher les fonctionnalites

Quotas

  • Middleware requireQuota('eleves', 1) avant les creations
  • Verification : count(eleves) < EtablissementConfig.maxEleves
  • Alerte a 80% de consommation (notification admin etablissement)
  • Blocage a 100% avec message d'upgrade de plan

Efort estime

2-3 semaines — Service feature flags + middleware quotas + UI gating

Patterns d'isolation multi-tenant

PatternIsolationCoutComplexite

Recommandation pour eLISAschool : rester en shared DB + RLS (hybride). Le modele actuel est fonctionnel ; le RLS ajoute la defense-in-depth sans changer l'architecture.

Feature flags — Solutions 2025-2026

  • ConfigCat — SDK TypeScript, targeting par attributs (plan, etablissementId), dashboard UI, 0 latence (evaluation locale)
  • GrowthBook — Open source, self-hostable, SDK TypeScript, experiments A/B integres
  • AWS AppConfig — Natif AWS, validation de schemas, deployments progressifs
  • Custom (ParametreSysteme actuel) — Fonctionnel, sans dependance externe, mais manque le targeting avance et le rollback instantane

Recommandation : GrowthBook (self-hosted, gratuit, SDK TypeScript natif) ou conserver le systeme custom en ajoutant le targeting par plan.
