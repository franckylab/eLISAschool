🏛️ Architecture Globale

Le système de configuration repose sur une source unique de vérité : la table parametres_systeme. Chaque paramètre peut avoir une valeur globale (partagée) et/ou des overrides par établissement.

💡 Principe fondamental

La résolution suit toujours l'ordre : Établissement → Global → Défaut. Si un override existe pour l'établissement, il est utilisé. Sinon, on fallback vers le paramètre global.

🔄 Cascade de Résolution

Quand un paramètre est demandé pour un établissement, le système suit cette cascade :

  1. Override Établissement — WHERE cle = X AND etablissementId = Y
    Valeur spécifique à l'établissement. Priorité maximale.
  2. Paramètre Global — WHERE cle = X AND etablissementId IS NULL
    Valeur par défaut pour tous les établissements. Fallback.
  3. Valeur par défaut — defaultValue passé en argument
    Utilisé si aucun paramètre trouvé en base.

Exemple concret

// Code métier dans un service
const requireValidation = await getParamBoolean(
    'bulletins.require_validation', 
    { etablissementId: 'abc-123', defaultValue: false }
);

// 2. Sinon cherche: cle='bulletins.require_validation' AND etablissementId IS NULL
//    → Trouvé ? Retourne la valeur globale (ex: false)
// 3. Sinon retourne: defaultValue (false)

⚡ Scénario : Global=false, Établissement=true

Question : Que se passe-t-il si globalement un paramètre vaut false et que l'établissement a un override à true ?

✅ Réponse : L'établissement EMPIORTE toujours

La valeur true de l'établissement sera utilisée. L'override établissement a toujours la priorité sur le paramètre global, quelle que soit la valeur.

⚠️ Contrainte UNIQUE

La contrainte UNIQUE (cle, etablissementId) garantit qu'un même paramètre ne peut avoir qu'une seule valeur par établissement (ou une seule valeur globale si etablissementId IS NULL).

💻 Implémentation Technique

Service de Résolution (extrait)

// backend/src/modules/configuration/services/configuration.service.ts

async getParametre<T = any>(cle: string, etablissementId?: string): Promise<T | null> {
    const cacheKey = etablissementId ? `${cle}:${etablissementId}` : cle;
    
    // 1. Vérifier le cache
    if (this.cache.parametres.has(cacheKey) && this.isCacheValid()) {
        return this.cache.parametres.get(cacheKey) as T;
    }

    // 2. Chercher d'abord le paramètre scopé à l'établissement
    if (etablissementId) {
        const paramScope = await this.parametreRepository.findOne({
            where: { cle, etablissementId }
        });
        if (paramScope) {
            const value = this.parseParametreValue(paramScope);
            this.cache.parametres.set(cacheKey, value);
            return value as T;
        }
    }

    // 3. Fallback vers le paramètre global
    const paramGlobal = await this.parametreRepository.findOne({
        where: { cle, etablissementId: IsNull() }
    });
    
    if (!paramGlobal) return null;

    const value = this.parseParametreValue(paramGlobal);
    this.cache.parametres.set(cacheKey, value);
    return value as T;
}

Helper Utilitaire

// backend/src/modules/configuration/utils/config.helper.ts

export async function getParamBoolean(
    cle: string, 
    options?: { etablissementId?: string; defaultValue?: boolean }
): Promise<boolean> {
    const value = await getParam<boolean | string>(cle, options);
    if (typeof value === 'boolean') return value;
    return value === 'true' || value === '1';
}

🚀 Pistes d'Amélioration

1. Optimisations Performance

  • Cache warming au démarrage
    Précharger les paramètres critiques (auth, modules) au démarrage du serveur pour éviter les cold starts.
  • Batch loading
    Charger tous les paramètres d'un module en une seule requête au lieu d'un appel par paramètre.
  • Cache invalidation sélective
    Invalidation par module/catégorie au lieu de tout invalider.

2. Améliorations Fonctionnelles

  • Héritage de groupe d'établissements
    Permettre les overrides au niveau groupe (déjà supporté par la colonne groupeEtablissementId mais pas encore exploité).
  • Audit trail amélioré
    Logger systématiquement les changements de paramètres avec avant/après et contexte utilisateur.
  • Validation schema
    Utiliser Zod pour valider les valeurs des paramètres selon leur type et leur domaine.

3. Sécurité

  • Chiffrement des valeurs sensibles
    Utiliser le type ENCRYPTED pour tous les paramètres contenant des secrets (API keys, tokens...).
  • RBAC granulaire
    Autoriser la modification de certains paramètres uniquement pour des rôles spécifiques (ex: SUPER_ADMIN uniquement pour les paramètres de sécurité).
  • Rate limiting sur les writes
    Éviter les abus de modification de paramètres en limitant le nombre de changements par minute.

4. Observabilité

  • Métriques de résolution
    Exposer des métriques sur le taux de cache hit, le temps de résolution, les paramètres les plus demandés.
  • Debug mode
    Permettre de tracer la cascade de résolution pour un paramètre donné (utile pour le debugging).

✅ Conclusion

Le système de configuration d'eLISAschool est robuste et flexible. L'architecture en cascade permet une gestion fine des paramètres tout en maintenant une cohérence globale. Les points clés :

Points forts
  • Source unique de vérité : table parametres_systeme
  • Cascade multi-niveaux : Établissement → Global → Défaut
  • Cache performant : 3 niveaux (in-memory, service, Redis)
  • Multi-tenant natif : isolation par etablissementId
  • Type-safe : 6 types de valeurs supportés (STRING, NUMBER, BOOLEAN, JSON, ARRAY, ENCRYPTED)
Points d'attention
  • Override prioritaire : un override établissement écrase TOUJOURS le global
  • Cache TTL : les changements mettent jusqu'à 60s pour se propager
  • Contrainte UNIQUE : une seule valeur par (cle, etablissementId)
