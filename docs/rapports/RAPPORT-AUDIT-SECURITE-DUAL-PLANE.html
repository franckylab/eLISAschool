4. Isolation Tenant — 3 couches

Defense in depth : middleware DB + RLS PostgreSQL + TypeORM Subscriber

1

tenantMiddleware GAP 3

Verification DB (Redis-cached 5min) de l'appartenance etablissement. Double next() possible (bug). String cast fragile.

2

rlsMiddleware (v8.0.0)

PostgreSQL SET LOCAL app.current_tenant dans transaction WRITE. READ = SET session. Sentinel UUIDs pour SUPER_ADMIN et GESTIONNAIRE_GROUPES.

3

TenantIsolationSubscriber (TypeORM)

beforeInsert : auto-inject etablissementId. beforeUpdate : bloque cross-tenant. Mode strict en production (throw), dev (log).

Critique GAP 1 — Platform login ne force pas MFA

Fichier : platform-auth.service.ts

Le commentaire indique "MFA obligatoire" mais le code ne verifie PAS identite.mfaActive. Un SUPER_ADMIN sans MFA peut acceder a la plateforme. Comparer avec le flux tenant qui enforce MFA correctement.

Impact : Compromission compte super-admin sans second facteur.

Fix : Apres bcrypt.compare(), verifier identite.mfaActive et retourner un flow MFA identique au tenant.

Haute GAP 2 — IP Allowlist fail-open

Fichier : ip-allowlist.middleware.ts

Si Redis echoue ou si la table est vide, le middleware appelle next() (autorise). En cas de panne Redis, toute IP peut acceder aux routes plateforme.

Fix : Fail-closed en production. Si Redis error → throw 403. Cache local en fallback.

Critique GAP 3 — Tenant middleware double next()

Fichier : tenant.middleware.ts (lignes 208 + 217)

Le middleware peut appeler next() deux fois dans certains chemins conditionnels, causant une execution dupliquee du handler ou un crash ERR_HTTP_HEADERS_SENT.

Impact : Requetes dupliquees, corruption potentielle de donnees, crash serveur.

Fix : Ajouter return apres chaque next() ou restructurer le flow avec un seul point de sortie.

Haute GAP 4 — Deux systemes d'identite paralleles

Fichiers : identite.entity.ts vs utilisateur.entity.ts

La plateforme utilise identites (nouveau) tandis que le tenant utilise utilisateurs (legacy). Pas de synchronisation automatique entre les deux. Risque de desynchronisation email/mot de passe.

Fix : Migration progressive vers identites comme source unique, ou trigger de synchronisation bidirectionnelle.

Haute GAP 5 — WebAuthn login bypass MFA + etablissement

Fichier : webauthn.service.ts

Le login WebAuthn ne verifie pas si MFA est active (court-circuite le flow MFA) et ne passe pas par la selection d'etablissement. Un utilisateur avec MFA obligatoire pourrait se connecter sans second facteur via passkey.

Fix : Integrer WebAuthn dans le flow MFA existant (comme TOTP) et non comme alternative.

Moyenne GAP 6 — Platform auth controller utilise authMiddleware tenant

Fichier : platform-auth.controller.ts

Certaines routes plateforme utilisent authMiddleware (concue pour le tenant) au lieu d'un middleware dedie plateforme. Fonctionne car le JWT platform est valide, mais la semantique est incorrecte.

Fix : Creer platformAuthMiddleware qui valide specifiquement les tokens platform.

Moyenne GAP 7 — dualCaslMiddleware avant platform guard

Fichier : app.ts + platform.routes.ts

Le dualCaslMiddleware est monte globalement (avant les routes), tandis que le guard requirePlatformAccess() est dans le router plateforme. Si la resolution Membership echoue, CASL peut creer une ability incorrecte avant que le guard ne rejette.

Fix : Monter un platformCaslMiddleware specifique dans platform.routes.ts, avant les routes.

Critique GAP 8 — JWT secret partage entre planes

Fichier : env.config.ts

Les deux planes (platform et tenant) utilisent le meme JWT_SECRET. Un token tenant forge pourrait etre accepte par une route plateforme si le guard ne verifie pas la presence du champ platform.

Impact : Escalade de privileges tenant → platform si le guard est bypass.

Fix : Utiliser deux secrets distincts (JWT_SECRET_PLATFORM + JWT_SECRET_TENANT) ou ajouter un plane claim obligatoire dans le JWT.

Moyenne GAP 9 — rlsMiddleware skip unauthenticated requests

Fichier : rls.middleware.ts

Si req.utilisateur est absent (routes publiques), le RLS est saute. Les routes publiques (health, webhooks) n'ont pas de RLS, ce qui est correct. Mais si une route protegee est montee avant authMiddleware, elle pourrait acceder aux donnees sans isolation.

Fix : Ajouter un guard defensif : si pas de utilisateur ET pas de route publique whitelistee → throw 401.

Haute GAP 10 — String cast fragile dans tenant.middleware

Fichier : tenant.middleware.ts

Le code utilise userRole === 'SUPER_ADMIN' as unknown as Role (string cast) au lieu de l'enum. Si la valeur change ou est typo, la comparaison echoue silencieusement.

Fix : Utiliser Role.SUPER_ADMIN directement avec le typage correct.

10. Conclusion

La securite d'eLISAschool est-elle assuree ?

Verdict : Partiellement

L'architecture dual-plane est bien concue sur le papier avec une separation claire Control Plane / Data Plane, 3 couches d'isolation tenant, CASL.js dual, et des mecanismes avances (MFA, WebAuthn, RLS, audit HMAC, KeyManager). Cependant, 3 failles critiques compromettent la securite reelle :

  • Le login plateforme ne force pas MFA (GAP 1) — un super-admin peut etre compromis sans second facteur
  • Le double next() dans le middleware tenant (GAP 3) peut causer des requetes dupliquees
  • Le secret JWT partage entre planes (GAP 8) permet une escalade de privileges theorique

Apres correction des 3 failles critiques, le score passera de 7.2 a ~8.5/10. Les 7 failles restantes (hautes + moyennes) sont des ameliorations de robustesse, pas des bloquants.
