4 État de l'art 2026 — bonnes pratiques SaaS

Recherche web approfondie (24 sources, section 12). Synthèse des patterns dominants du billing SaaS multi-tenant en 2026.

⚖️

Hybride abonnement + usage

Le modèle dominant 2026 combine une base fixe (accès plateforme) et une composante à l'usage (par élève, par siège, par crédit). Stripe, Lago et Paddle convergent vers ce schéma — exactement la cible eLISAschool.

🚪

Hard-gate & essai contrôlé

Les plateformes sérieuses verrouillent l'accès sans abonnement actif et n'ouvrent que via un essai borné dans le temps avec capacités complètes, puis dégradation gracieuse (lecture seule) avant archivage.

🚀

Choix de plan à l'onboarding

Le plan se choisit dès l'inscription (cartes comparatives, CTA unique) ou via un plan par défaut explicite côté plateforme. Réduit la friction et augmente la conversion essai → payant.

📈

Overages & top-ups

Le blocage sec au quota est considéré comme anti-commercial : les leaders proposent l'achat de capacité supplémentaire au prorata du cycle en cours (overage fees / credit packs).

🧩

Architecture entitlements

Pattern « entitlement engine » : une source unique de vérité (plan → entitlements → modules/features/quotas), cache court + invalidation, audit de chaque décision. Stigg, Ordway, Quantumbyte le décrivent comme le standard multi-tenant.

🔮

Tendances 2026

Facturation par crédits, remises pilotées par stratégie (% ou montant, N premiers cycles), cycles flexibles (personnalisés en jours), transparence tarifaire self-service, classification binaire pour le client final.

5.3 Tarification par élève

// Calcul du montant d'un cycle (facturation.service.ts)
elevesFacturables = max(0, nbElevesActifs − plan.elevesGratuits)
montantCycle = plan.prixBase + elevesFacturables × plan.prixParEleve × facteurCycle
montantPlafonne = plan.plafondMensuel > 0 ? min(montantCycle, plan.plafondMensuel) : montantCycle
remiseAppliquee = resoudreRemises(abonnement, cycle) // % ou montant fixe, scope respecté
montantFinal = max(0, montantPlafonne − remiseAppliquee) // + TVA OHADA 19,25 % à la facture

Coût mensuel estimé selon l'effectif (milliers de FCFA)

Zone plate = élèves gratuits ; pente = prixParEleve. Exemple : PREMIUM à 400 élèves = 40 000 + (400−200)×120 = 64 000 F/mois.

5.5 Remises, cycles, essais, expiration — CRUD complet

💸 Remises

CRUD plateforme + entité Remise.

  • Type : POURCENTAGE ou MONTANT_FIXE
  • Scope : PREMIER_CYCLE, TOUS_CYCLES, N_CYCLES
  • Ciblage : un plan précis ou tous les plans
  • Bornage : dateDebut / dateFin
  • Application automatique dans facturation.service.calculerMontantCycle() ; mention sur la facture OHADA

🔁 Cycles de facturation

Enum étendu par plan :

  • MENSUEL · TRIMESTRIEL · SEMESTRIEL · ANNUEL
  • PERSONNALISE via dureeCycleJours
  • facteurCycle : réduction annuelle configurable (ex. −2 mois offerts)
  • Prorata conservé lors des changements de plan en cours de cycle

⏳ Essais

essaiConfig JSONB par plan :

{
  "actif": true,
  "dureeJours": 14,
  "capacitesCompletes": true,
  "conversionAuto": false
}

Auto-création de l'abonnement ESSAI à l'inscription si le plan choisi a un essai actif.

⌛ Expiration & dégradation

expirationConfig JSONB par plan :

{
  "seuilLectureSeuleJours": 15,
  "seuilVerrouillageJours": 30,
  "seuilArchivageJours": 90
}

Cron quotidien billing-expiration : assigne EXPIRE, alimente dateExpirationReelle, pilote les 3 phases.

📊 Quotas inclus

JSONB quotas par plan — 5 ressources :

  • eleves (cohérent avec elevesGratuits)
  • utilisateurs, classes
  • stockage_go, sms_mensuel
  • Alertes 80 % / 95 %, blocage 429 à 100 %
  • 0 = illimité (convention ENTIER)

🧾 Facturation OHADA

Inchangée et renforcée :

  • TVA 19,25 % (1925 centièmes)
  • Numérotation FAC-OHADA-YYYY-NNNNNN
  • Lignes facture : base + élèves + suppléments − remise
  • Avoirs conservés

Le plan est décidé pendant l'inscription, pas après : le tenant entre directement avec des entitlements cohérents (source : jimo.ai, flowjam, arcade.software).

Permet l'inscription sans friction (auto-DECOUVERTE) tout en restant pilotable par le SUPER_ADMIN. Jamais de création d'établissement sans abonnement (source : kompassify, adeptdev).

ALTER TABLE plans_abonnement DROP COLUMN tranchesConfigurables, DROP COLUMN modeFacturationTranches; puis ajout : prixParEleve numeric NOT NULL DEFAULT 0, elevesGratuits int NOT NULL DEFAULT 50, plafondMensuel numeric NOT NULL DEFAULT 0, cycleFacturation varchar(20) NOT NULL DEFAULT 'MENSUEL', dureeCycleJours int, essaiConfig jsonb, expirationConfig jsonb, quotaTopupPrix jsonb, estDefaut boolean NOT NULL DEFAULT false, fonctionnalitesIncluses jsonb.

2
Nouvelles tables — remises et quota_supplements

remises : id uuid PK, code varchar UNIQUE, type varchar CHECK IN ('POURCENTAGE','MONTANT_FIXE'), valeur numeric, scope varchar CHECK IN ('PREMIER_CYCLE','TOUS_CYCLES','N_CYCLES'), nbCycles int, dateDebut/dateFin date, planId uuid FK NULLABLE (null = tous plans), actif boolean, timestamps. Index sur (planId, actif) et code.

quota_supplements : id uuid PK, abonnementId uuid FK ON DELETE CASCADE, ressource varchar, quantite int, montantPaye numeric, dateDebut date, dateFin date, timestamps. Index sur (abonnementId, ressource, dateFin).

3
Suppression brutale des tranches

DROP TABLE tranches_eleves, tranches_supplement, tranches_groupe CASCADE; — les services tranche-config.service.ts et le cron billing-controle-tranches sont supprimés dans le même commit (remplacés par le calcul par élève dans facturation.service).

4
Enum catégorie modules : BASE/PREMIUM/ADDON → BASE/GRATUIT/PAYANT

Colonne categorie de modules_catalogue convertie en varchar : UPDATE modules_catalogue SET categorie = CASE WHEN categorie='PREMIUM' THEN 'PAYANT' WHEN categorie='ADDON' THEN 'PAYANT' ELSE categorie END; puis CHECK IN ('BASE','GRATUIT','PAYANT'). L'enum TypeScript CategorieModule est réécrit ; ModuleCategory dans shared/ idem.

5
Fonctionnalités : labels FR/EN

ALTER TABLE feature_flag_definitions RENAME COLUMN label TO labelFr; ALTER TABLE feature_flag_definitions ADD COLUMN labelEn varchar(150); — les 8 flags système reçoivent des labels commerciaux (ex. advanced_bulletins → « Bulletins avancés » / « Advanced report cards »). La table n'est PAS renommée (le renommage est UI/i18n uniquement, la DB garde son nom technique).

6
Seeds réécrits — seed-plans-abonnement.ts (nouveau)

Seed idempotent des 4 plans (section 5.4) avec tous les champs (prixParEleve, elevesGratuits, plafond, modulesInclus, fonctionnalitesIncluses, quotas, cycle, essaiConfig, expirationConfig, quotaTopupPrix, estDefaut pour DÉCOUVERTE) + 2 remises seedées (BIENVENUE-10 : 10 % PREMIER_CYCLE tous plans ; ANNUEL-2MOIS : MONTANT_FIXE sur cycle annuel) + paramètre billing.plan_par_defaut = id DÉCOUVERTE. Branché dans initial.seed.ts après seedModulesCatalogue.

7
Backend — EntitlementService hard-gate

Réécriture de check() : après le bypass BASE, le test abonnement (ACTIF ou ESSAI valide) devient obligatoire avant toute résolution ; sinon lecture de dateExpirationReelle + expirationConfig du dernier plan pour retourner LECTURE_SEULE / VERROUILLE / ARCHIVE. Suppression des branches « plan minimal requis » et « actifParDefaut ». checkCapability() résout aussi les fonctionnalités via fonctionnalitesIncluses + rollout.

8
Backend — unification middlewares & facturation

module-active.middleware.ts supprimé ; module-access.middleware.ts reste l'unique gating (délégation entitlementService). quota.middleware.ts unique : 429 + X-Quota-Limit/Used/Remaining + code ressource. facturation.service : formule par élève (section 5.3), application des remises, cycles étendus + facteurCycle, cron billing-expiration quotidien (EXPIRE + dégradation), endpoint POST /api/billing/quotas/supplement.

9
Backend — inscription avec plan

POST /api/billing/plans/publics (route publique, projection commerciale sans données sensibles). register accepte planId ; fallback billing.plan_par_defaut ; refus explicite si aucun. etablissement.service appelle subscriptionService.creerAbonnementInitial() (ESSAI si essaiConfig.actif, sinon ACTIF + facture proratisée).

10
Frontend — marketplace, fonctionnalités, plan form, inscription

Marketplace : onglet Fonctionnalités + badges GRATUIT/PAYANT + CTA top-up quota (modal d'achat avec prorata affiché). plan-form-modal : champs par élève (prixParEleve, elevesGratuits, plafond), essais, expiration, prix top-up, fonctionnalités incluses, plan par défaut. Pages plateforme « Fonctionnalités » (route renommée). Wizard d'inscription : étape choix de plan avec simulateur. i18n : nouvelles clés admin.fonctionnalites.*/admin.features.*, anciennes supprimées.

🔥 Aucune rétro-compatibilité : les endpoints /api/billing/tranches/*, le simulateur par tranches et les hooks useTranches* sont supprimés dans le même commit. Les établissements sans abonnement au moment du déploiement passent en statut « sans plan » → l'admin plateforme doit leur affecter un plan via le détail établissement (action dédiée) ou le plan par défaut s'applique à leur prochaine connexion.

11 Roadmap d'implémentation

5 lots séquentiels, chacun validable indépendamment (tsc 0 erreur in-scope + walkthrough).

Lot 1 — Schéma & seeds (backend, ~1 j)

Migration 213, entités Plan/Remise/QuotaSupplement, seed des 4 plans + remises + plan par défaut, DROP tranches. Validation : seeds idempotents ×2.

Lot 2 — Entitlement hard-gate & facturation (backend, ~1,5 j)

EntitlementService 6 niveaux, middleware unique, formule par élève, remises, cycles, cron expiration, endpoint top-up. Validation : tests unitaires pricing + walkthrough 429→top-up.

Lot 3 — Inscription & API publique (backend, ~0,5 j)

/plans/publics, register avec planId + fallback défaut, abonnement initial ESSAI/ACTIF.

Lot 4 — Frontend plateforme (frontend, ~1,5 j)

plan-form-modal complet (par élève, essais, expiration, top-up, fonctionnalités), CRUD remises, page Fonctionnalités renommée, plan par défaut dans Configuration.

Lot 5 — Frontend tenant & i18n (frontend, ~1 j)

Marketplace binaire + onglet Fonctionnalités + modal top-up, wizard inscription avec choix de plan, renommage i18n brutal, grep zéro occurrence legacy.

✅ Critère de complétude : un nouvel établissement inscrit avec ESSENTIEL voit exactement les modules/fonctionnalités de son plan, est facturé 15 000 + max(0, n−100)×150 F, reçoit une remise BIENVENUE-10 sur le premier cycle, et peut acheter 50 élèves supplémentaires au prorata si son quota est dépassé.
