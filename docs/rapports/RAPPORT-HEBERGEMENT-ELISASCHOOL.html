🟢 Verdict — Démarrage (1 000 utilisateurs)

Recommandé Hetzner CX32 ou OVH VPS Comfort (4 vCPU / 8 Go / ~160 Go SSD) — ≈ 16–26 €/mois.

Toute la stack Docker Compose sur un seul VPS (nginx + backend + frontend + PostgreSQL + Redis + PgBouncer), Cloudflare CDN gratuit devant.

Redondance : backups quotidiens pg_dump vers R2/Backup Storage + monitoring Uptime Kuma.

🔵 Verdict — Croissance (5 000 utilisateurs)

Recommandé Split applicatif / données : 2 app nodes (4 vCPU/8 Go) + 1 VPS base (PostgreSQL 16 + Redis + PgBouncer) + nginx load balancer + Cloudflare CDN — ≈ 80–120 €/mois.

Instances Node.js multiples (pas de PM2 cluster en stratégie long terme), session state dans Redis, zero-downtime deploys.

🟣 Verdict — Échelle (10 000 utilisateurs)

Recommandé 3+ app nodes autoscalés + PostgreSQL managé HA (AWS RDS / DigitalOcean / Supabase) ou dédié DB avec réplicas — ≈ 250–450 €/mois.

Stockage objets S3/R2 pour les fichiers (exports PDF, uploads), redis cluster, monitoring Prometheus/Grafana, multi-région optionnel.

✅ Points clés à retenir • eLISAschool est un SaaS multi-tenant à 8 tables lourdes — la base de données est LE goulot d'étranglement, pas Node.js.
• Le bon ordre de scaling : optimiser SQL + cache Redis → PgBouncer → scaler l'app horizontalement → scaler la DB.
• PM2 cluster = rustine temporaire ; instances multiples + nginx = stratégie durable (source BSWEN 2026).
• Cloudflare CDN gratuit = −60 % de bande passante, essentiel pour la latence Afrique.
• Aucun cloud majeur n'a de région au Cameroun : Paris (~130 ms) reste le meilleur compromis prix/latence ; Johannesburg/Cape Town en alternative.

3. Comment fonctionne l'hébergement web

3.1 Le chemin d'une requête — de l'utilisateur à la base de données

Utilisateur (Douala) ── DNS (Cloudflare, ~10 ms) ──▶ CDN / WAF ──▶ Reverse proxy (nginx) │ │ HTTPS (TLS 1.3, cache statique + brotli) ▼ Frontend statique (React/Vite, servi par nginx ou CDN) ◀── assets JS/CSS/PNG │ ▼ Application Node.js (Express) ──▶ Redis (cache, rate-limit, sessions, pub/sub) │ │ │ pool de connexions (PgBouncer : 20 clients actifs, 200 max) ▼ PostgreSQL 16 (RLS par établissement, 8 tables partitionnées, backups continus)

🌍 Les briques

DNS : traduit le nom de domaine en IP (TTL court pour failover).
CDN : cache les assets près de l'utilisateur (Cloudflare : réseau mondial, gratuit).
Reverse proxy : TLS, compression, protection, load balancing (nginx).
App server : exécute le code (Node.js, mono-thread → à multi-instancier).
Base de données : état durable (PostgreSQL — le goulot d'étranglement n°1).
Cache : Redis — absorde les lectures répétées (−80 % de requêtes DB).

⚖️ Ce que ça implique pour eLISAschool

• Stateless app : aucun état en mémoire processus (sessions, files) → tout dans Redis/Postgres → scale horizontal propre.

• socket.io inutilisé : pas de contrainte sticky-session WebSocket à gérer aujourd'hui (un point de moins à scaler).

• PDF côté client (jsPDF) : les exports PDF n'engendrent aucune charge CPU serveur — excellente décision d'architecture.

6. Dimensionnement & architecture par palier

6.1 Règles de dimensionnement appliquées

🧠 Node.js

≈ 1 vCPU pour 50–150 req/s sur Express typique (hors requêtes DB lourdes). Chaque instance ~300–500 Mo RAM (V8 + dépendances). Pour 400 req/s de pointe : 3–4 instances × 2–4 vCPU.

🗄️ PostgreSQL

shared_buffers ≈ 25 % de la RAM (ex : 8 Go → 2 Go). Index + partitionnement déjà en place. Prévoir 1 vCPU pour 200–400 req/s simples, mais les agrégats (bulletins) consomment 10–50× plus.

🟥 Redis

512 Mo actuel → 1 Go dès 5 000 utilisateurs (cache config + rate-limit + sessions). Persistance RDB + AOF. Toujours ne pas faire de Redis la source de vérité métier.

7. Scaling Node.js & PostgreSQL — stratégie

⚡ PM2 Cluster vs Instances multiples (source BSWEN, 2026)

ApprocheQuandLimites
PM2 cluster (1 serveur, -i max)Rustine rapide pour exploiter un VPS multi-cœur (palier 1 000)Partage des ressources, débogage complexe, pas d'isolation, zéro-downtime difficile, limité à 1 machine
Instances multiples (Docker compose replicas / 2+ VPS)Production (5 000+)Nécessite LB, sessions partagées (Redis), pooling DB

« Le clustering est imprévisible et doit être évité comme stratégie long terme » — recommander les instances multiples pour la production.

⚙️ La recette pour eLISAschool

1. Stateless : sessions + rate-limit + cache dans Redis (déjà le cas).
2. nginx upstream avec least_conn + health checks sur /api/health.
3. 2+ replicas Docker Compose du backend (ports internes 3000, 3001…).
4. Zero-downtime : blue-green ou rolling deploys (2 nodes → drain pendant upgrade).
5. PgBouncer côté app (pool 20/instance) pour ne pas épuiser les 200 connexions max.
6. Redis partagé pour les states entre instances.

8. Recommandations & offres complètes

8.1 Offre Économie — 1 000 utilisateurs (≈ 20–30 €/mois)

🖥️ VPS unique : Hetzner CX32 (4 vCPU / 8 Go / 160 Go NVMe) ≈ 16 € ou OVH VPS Comfort ≈ 15,80 €.

🐳 Docker Compose : nginx + backend (cluster PM2 2–3) + frontend + PostgreSQL 16 + Redis 512 Mo + PgBouncer.

☁️ Cloudflare Free : CDN + DDoS + SSL + cache statique (≈ −60 % bande passante).

💾 Backups : pg_dump 6 h + upload Cloudflare R2 (0 € egress) · rétention 30 jours.

📈 Monitoring : Uptime Kuma (self-hosted, alertes Telegram/WhatsApp).

🔐 Sécurité : UFW (80/443/SSH), fail2ban, Let's Encrypt auto, clés SSH uniquement.

8.2 Offre Standard — 5 000 utilisateurs (≈ 80–120 €/mois)

⚖️ Split app / données (3 VPS Hetzner) : LB nginx 2 vCPU/4 Go (~8 €) + 2 app nodes 4 vCPU/8 Go (~32 €) + node données 4 vCPU/8 Go (~20 €) ≈ 60 €.

🗄️ PostgreSQL 16 avec shared_buffers 2 Go + PgBouncer (pool 20 × 2 apps, max 200) + réplica standby local.

🟥 Redis 1 Go (cache partagé entre instances, sessions, rate-limit par plan).

🔄 Zero-downtime deploys : blue-green sur les 2 nodes (drain + bascule upstream nginx).

☁️ Cloudflare Pro (option 20 €) : WAF règles personnalisées + analytics. Backups R2 + restauration testée mensuellement.

📈 Monitoring : Prometheus + Grafana (ou Uptime Kuma avancé), alertes seuils CPU/RAM/DB/5xx (le code alerte déjà à 80/90/100 % quotas).

🧰 Option recommandée : installer Coolify sur le node LB — push-to-deploy, SSL auto, backups S3, dashboard unique.

8.3 Offre Premium — 10 000 utilisateurs (≈ 250–450 €/mois)

🌐 Cloud managé : AWS af-south-1 (Cape Town) / Azure South Africa / GCP africa-south1 — ou Vultr LAG (Nigeria) en compromis budget.

📦 App : 3–6 instances (4 vCPU/8 Go) autoscalées derrière un ALB/LB managé + au moins 2 AZ.

🗄️ PostgreSQL managé HA (RDS Multi-AZ / DO Managed / Supabase) : failover auto, PITR, 2 réplicas en lecture.

🟥 Redis Cluster ou ElastiCache (3 nœuds) + stockage objets S3/R2 (uploads, exports, backups).

📈 Observabilité : Prometheus/Grafana/Alertmanager + traces, SLO 99,9 %, runbook d'incident.

🌍 Option multi-région : lecture proche utilisateur via CDN + éventuel hébergement local Douala (colocation Axian/Orange DC, < 5 ms) pour la base primaire si le marché camerounais domine.

8.4 Best practices transverses

🔒 Sécurité

• TLS 1.3 + HSTS + DNSSEC (Cloudflare)
• UFW : 80/443 uniquement ; SSH sur port custom + fail2ban
• Secrets via vault/env gitignorés (JWT_SECRET_PLATFORM/TENANT séparés, ENCRYPTION_KEY ≠ JWT_SECRET)
• IP allowlist plateforme + MFA/TOTP + WebAuthn déjà implémentés côté app

💾 Backups & RPO/RTO

• pg_dump toutes les 6 h + WAL continu → R2/Backup Storage
• RTO < 1 h · RPO < 6 h
• Test de restauration mensuel obligatoire
• Redis : RDB 1 h + AOF
• docker-compose + .env versionnés (Git privé)

🚀 CI/CD

• GitHub Actions : lint → tsc → jest → docker build → push GHCR → SSH deploy
• Blue-green sur 2 nodes (zéro downtime)
• Health check /api/health avant bascule, rollback automatique
