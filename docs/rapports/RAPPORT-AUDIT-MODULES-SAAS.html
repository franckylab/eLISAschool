Probleme critique : Double source de verite

Le systeme maintient deux sources de verite divergentes : MODULE_REGISTRY (code, legacy) et ModuleCatalogue (base de donnees). Le service configurationService.isModuleActive() ignore totalement le catalogue DB, tandis que moduleResolutionService l'utilise partiellement. Cela cree des incoherences d'activation et de facturation.

Fuite multi-tenant dans la resolution des modules

La requete AbonnementModule dans module-resolution.service.ts (lignes 134-137) ne filtre pas par etablissementId — elle recupere les abonnements de TOUS les etablissements. Risque de cross-tenant et degradation des performances.

Perimetre de l'audit

Analyse complete du code source (shared/, backend/, frontend/), verification de coherence entre les 3 sources de definition des modules, audit de la cascade d'activation, analyse du graphe de dependances, evaluation de la securite multi-tenant, benchmark des meilleures pratiques SaaS (web research), et proposition d'architecture cible.

L'activation d'un module pour un etablissement suit une cascade a 4 niveaux. Chaque niveau peut override le precedent.

Module souscrit en supplement par l'etablissement

Incoherence majeure : ConfigurationService ignore le catalogue DB

configurationService.isModuleActive() utilise ParametreSysteme → fallback MODULE_REGISTRY.defaultActive. Il ne lit JAMAIS ModuleCatalogue. Resultat : un module desactive dans le catalogue DB peut rester actif via le ParametreSysteme.

Architecture ideale proposee

Couche Definition

  • ModuleCatalogue (DB) — source unique
  • MODULE_REGISTRY supprime (legacy)
  • Seed automatique depuis catalogue
  • Categories unifiees : CRITIQUE/PREMIUM/ADDON
  • Dependencies validees (acyclique)

Couche Resolution

  • ModuleResolutionService v2
  • Cache Redis (TTL 60s, pas memoire)
  • Cascade : catalogue → plan → groupe → supplement
  • Invalidation event-driven (pub/sub)
  • Scoped par etablissementId (RLS)

Couche Enforcement

  • requireModuleAccess() simplifie
  • Plus de MODULES_PREMIUM_LEGACY
  • Verification dependances automatique
  • Audit log systematique
  • Rate limiting par plan

ModuleLifecycle — Interface publique stable

interface ModuleLifecycle {
  onActivate(etablissementId: string): Promise<void>;
  onDeactivate(etablissementId: string): Promise<void>;
  onUpgrade(etablissementId: string, newPlan: Plan): Promise<void>;
  getDependencies(): string[];
  getDependents(): string[];
  canDeactivate(): { allowed: boolean; blockedBy?: string[] };
}

// Chaque module implemente cette interface
// Le ModuleRegistryService orchestre les evenements
// Pub/Sub via EventEmitter pour le decouplage

Schema de donnees cible

modules_catalogue          -- Source unique (41 modules)
  ├── code (unique)
  ├── categorie (CRITIQUE|PREMIUM|ADDON)
  ├── dependencies[]       -- Validated acyclic
  ├── config (jsonb)       -- Module-specific settings
  └── actifParDefaut       -- Override global

plans_abonnement
  ├── modulesInclus[]      -- References catalogue codes
  └── featureFlags{}       -- Decoupled from modules

modules_groupe             -- Override par groupe
  ├── groupeEtablissementId
  ├── moduleCatalogueId    -- FK vers catalogue
  └── actif                -- Boolean override

abonnements_modules        -- Supplements par etablissement
  ├── etablissementId
  ├── moduleCatalogueId    -- FK vers catalogue
  └── actif

parametres_systeme         -- Runtime overrides (trace only)
  ├── cle: "modules.{code}.actif"
  └── etablissementId      -- Scope

Plan de migration recommande

Phase 1 — Corrections critiques (1-2 jours)

P1.1 Supprimer MODULES_PREMIUM_LEGACY du middleware — utiliser uniquement le catalogue DB.
P1.2 Ajouter etablissementId filter dans la requete AbonnementModule (module-resolution.service.ts l.134).
P1.3 Ajouter dependance auth au module parking.
P1.4 Corriger la categorie de recrutement : CRITIQUES → ADDON (ou defaultActive: true).

Phase 2 — Unification source de verite (3-5 jours)

P2.1 Migrer configurationService.isModuleActive() pour lire ModuleCatalogue en priorite.
P2.2 Migrer toggleModule() pour mettre a jour ModuleCatalogue.
P2.3 Supprimer MODULE_REGISTRY — remplacer par des lectures du catalogue DB.
P2.4 Ajouter les 6 modules plateforme au catalogue DB.

Phase 3 — Cache et performance (2-3 jours)

P3.1 Unifier les TTL cache a 60s (ConfigurationService + ModuleResolutionService).
P3.2 Migrer le cache memoire vers Redis (partage entre instances).
P3.3 Ajouter invalidation explicite apres toggle/activation.
P3.4 Cache isModuleFacturable() (actuellement uncached).

Phase 4 — Validation et audit (2-3 jours)

P4.1 Ajouter validation des dependances dans toggleModule() (verifier que les dependants sont prets).
P4.2 Ajouter audit log systematique dans toggleModule().
P4.3 Implementer ModuleLifecycle interface pour les modules critiques.
P4.4 Decoupler feature flags des modules (service dedie).

Phase 5 — Packaging et UI (3-5 jours)

P5.1 Implementer les 8 Tiers de groupement dans l'UI plateforme.
P5.2 Creer un simulateur de plan avec les packs proposes.
P5.3 Ajouter une vue "Impact de desactivation" (modules affectes).
P5.4 Documentation publique des modules pour les clients.

Estimation effort total

11-18 jours de developpement (1 developpeur senior). Priorite : Phases 1-2 (critiques, 4-7 jours). Les phases 3-5 sont des ameliorations progressives non-bloquantes.
