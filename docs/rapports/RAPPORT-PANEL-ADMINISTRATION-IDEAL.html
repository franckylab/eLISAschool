1 État des lieux

Audit de l'administration actuelle — ce qui existe, ce qui manque, ce qui bloque.

🔴 Critique — Routes vides

4 routes retournent null :

  • /infrastructure
  • /modules-administratifs
  • /modules-complementaires
  • /modules-pedagogiques

🟠 Données simulées

La page /admin/permissions utilise des données fictives (SIMULATED_PERMISSIONS). Aucun lien avec le RBAC réel en base.

🟡 Pas de séparation Control/Data Plane

SUPER_ADMIN et ADMIN partagent le même layout, les mêmes routes et les mêmes guards. Pas de frontière architecturale.

⚠️ Problème fondamental

L'administration actuelle mélange la gestion de la plateforme (multi-tenant, facturation, monitoring global) et la gestion d'un établissement (élèves, notes, bulletins). Cette confusion crée des failles de sécurité et empêche l'évolution vers un vrai SaaS.

2 Benchmark — Bonnes pratiques 2025-2026

Ce que font les meilleurs panels d'administration SaaS.

🏢 Vercel Dashboard

  • Séparation Team vs Personal
  • Command Palette (Cmd+K)
  • Activity Feed temps réel
  • Dark-first design

📊 Linear

  • Sidebar 2 niveaux max
  • 3-5 KPIs par dashboard
  • Tables > Charts pour données structurées
  • Progressive disclosure

🔐 Stripe Dashboard

  • RLS + ABAC granulaire
  • Audit trail complet
  • API-first (tout est API)
  • Feature flags par compte

🎯 Refine (framework)

  • 57KB bundle headless
  • Multi-tenancy built-in
  • Auth hooks intégrés
  • CRUD generators

💡 Tendances clés 2025-2026

1. Control Plane / Data Plane separation — isoler l'admin plateforme de l'admin métier.
2. Authorization-as-code — CASL.js, SpiceDB, OpenFGA remplacent les guards manuels.
3. Observabilité intégrée — RED/USE + Four Golden Signals dans le dashboard.
4. Feature flags per tenant — contrôle granulaire sans déploiement.
5. Command Palette — navigation Clavier-first (Cmd+K).

3 Proposition A — Évolution progressive

Conserver l'architecture actuelle, remplir les vides, renforcer la sécurité. Effort modéré.

A

Approche incrémentale

Effort : 3-4 semaines · Risque : faible · Impact : moyen

✅ Actions

  • Implémenter les 4 routes vides (infrastructure, modules-*)
  • Remplacer SIMULATED_PERMISSIONS par les données RBAC réelles
  • Ajouter un dashboard monitoring basique (uptime, erreurs, latence)
  • Créer un guard requirePlatformAdmin() distinct
  • Ajouter des KPIs globaux (nb établissements, utilisateurs actifs)

⚠️ Limites

  • Pas de séparation Control/Data Plane
  • Pas de RLS PostgreSQL
  • Toujours des guards manuels par route
  • Pas de feature flags
  • Bundle monolithique (pas de code splitting admin)

4 Proposition B — Refonte architecturale (Recommandée)

Séparer Control Plane / Data Plane, introduire CASL.js, RLS PostgreSQL et monitoring avancé.

B

Architecture dual-plane avec authorization-as-code

Effort : 6-8 semaines · Risque : modéré · Impact : élevé

🛡️ CASL.js

Authorization déclarative. Une seule définition des capacités par rôle. Plus de guards manuels par route.

🔒 RLS PostgreSQL

Defense-in-depth. Même si le backend bug, la DB rejette les requêtes cross-tenant automatiquement.

🚩 Feature Flags

Activation/désactivation par tenant sans déploiement. Plans basic/standard/premium.

// shared/src/abilities/admin.abilities.ts import { AbilityBuilder, createMongoAbility } from '@casl/ability'; export function defineAbilityFor(user: JwtPayload, tenant: TenantContext) { const { can, cannot, build } = new AbilityBuilder(createMongoAbility); // SUPER_ADMIN = contrôle tout la plateforme if (user.role === 'SUPER_ADMIN') { can('manage', 'all'); cannot('delete', 'Etablissement'); // soft-delete uniquement } // ADMIN = contrôle son établissement uniquement if (user.role === 'ADMIN') { can('manage', 'all', { etablissementId: tenant.id }); cannot('manage', 'PlatformConfig'); cannot('manage', 'FeatureFlag'); } // Contraintes par plan if (tenant.plan === 'basic') { cannot('create', 'Utilisateur', {}, 'maxUsers50'); cannot('export', 'AuditLog'); } return build(); }

5 Proposition C — Refonte totale avec Refine

Remplacer le frontend admin par le framework Refine. Multi-tenant natif, CRUD generators, auth hooks.

C

Framework headless Refine + backend existant

Effort : 10-14 semaines · Risque : élevé · Impact : très élevé

✅ Avantages

  • CRUD auto-généré pour chaque entité
  • Multi-tenancy built-in (pas de code custom)
  • Auth hooks + audit trail intégrés
  • Bundle 57KB (vs ~500KB actuel pour l'admin)
  • Thèmes dark/light natifs
  • GraphQL-ready si migration future

⚠️ Inconvénients

  • Réécrire TOUT le frontend admin
  • Perte de la cohérence UI avec le reste de l'app
  • Formation équipe sur un nouveau framework
  • Dépendance externe (Refine → communauté)
  • Personnalisation avancée = fight the framework
  • 10-14 semaines de travail

💡 Recommandation

La proposition C est sur-ingéniérée pour eLISAschool. Le framework Refine apporte de la valeur quand on démarre de zéro. Ici, 80% du frontend admin existe déjà. Le coût de migration ne justifie pas le gain. Proposition B recommandée.

7 Sécurité — Architecture zero-trust

5 couches de défense pour l'administration.

🔒 RLS PostgreSQL — Implémentation

-- Migration: enable-rls-admin-tables.sql -- Activer RLS sur les tables critiques admin ALTER TABLE etablissements ENABLE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation ON etablissements USING (id = current_setting('app.current_tenant')::uuid); -- Forcer le contexte à chaque requête CREATE OR REPLACE FUNCTION set_tenant(tenant_id uuid) RETURNS void AS $$ BEGIN PERFORM set_config('app.current_tenant', tenant_id::text, true); END; $$ LANGUAGE plpgsql; -- Middleware Express applique set_tenant() avant chaque requête

🔐 MFA pour SUPER_ADMIN

TOTP (Google Authenticator) obligatoire pour :

  • Créer/supprimer un établissement
  • Modifier les feature flags globaux
  • Accéder au monitoring infrastructure
  • Exporter les audit logs

📊 Alertes sécurité

  • 5 échecs login consécutifs → lock 15min + email
  • Changement rôle SUPER_ADMIN → approval workflow
  • Suppression établissement → confirmation 2 facteurs
  • Accès depuis nouvelle IP → notification email
  • Export masse données → log + alerte

8 Performance — Bundle splitting + monitoring

Optimisations pour un panel admin rapide et observable.

📦 Vite — Code splitting admin

// vite.config.ts — manualChunks pour l'admin export default defineConfig({ build: { rollupOptions: { output: { manualChunks: { // Vendor admin (chargé uniquement sur /platform/* et /admin/*) 'admin-vendor': ['@casl/ability', 'recharts', 'cmdk'], // Routes platform (lazy-loaded) 'admin-platform': [ './src/routes/_platform/dashboard.tsx', './src/routes/_platform/etablissements.tsx', './src/routes/_platform/feature-flags.tsx', './src/routes/_platform/monitoring.tsx', ], // Routes admin tenant (lazy-loaded) 'admin-tenant': [ './src/routes/_auth.admin/audit.tsx', './src/routes/_auth.admin/roles.tsx', './src/routes/_auth.admin/permissions.tsx', ], }, }, }, }, });

⚡ Optimisations frontend

  • React.memo sur les KPI cards (re-render uniquement si data change)
  • useMemo pour les calculs de statistiques
  • useCallback pour les handlers passés en props
  • react-window pour les tables > 100 lignes
  • TanStack Query — staleTime: 30s pour les données admin
  • Virtualisation des logs d'audit (> 1000 entrées)
  • Debounce 300ms sur les recherches

📊 Monitoring — Four Golden Signals

  • Latence : p50, p95, p99 par endpoint
  • Trafic : requêtes/seconde, utilisateurs connectés
  • Erreurs : taux d'erreur 5xx, 4xx par type
  • Saturation : CPU, mémoire, connexions DB, pool

Stockage : Prometheus + Grafana (ou InfluxDB + dashboard custom)

10 Roadmap d'implémentation

Plan de déploiement en 4 phases — Proposition B retenue.

Phase 1 — Fondation (2 sem)

Séparation Control Plane + RLS PostgreSQL

• Créer le layout _platform avec sidebar dédiée
• Routes : /platform/dashboard, /platform/etablissements
• Migration RLS sur 10 tables critiques (etablissements, utilisateurs, eleves, notes...)
• Middleware setTenantContext() dans Express
• Guard requirePlatformAdmin() séparé de requireAdmin()

Phase 2 — Authorization (2 sem)

CASL.js + Feature Flags + Permissions réelles

• Installer @casl/ability — définir les abilities par rôle
• Remplacer les guards manuels par CASL dans 30 controllers
• Page /admin/permissions connectée aux données RBAC réelles
• Feature flags JSONB dans etablissements + UI de gestion
• Tests : couverture > 90% sur les abilities

Phase 3 — Monitoring (2 sem)

Dashboard monitoring + Command Palette + Performance

• Endpoint /api/platform/metrics (latence, erreurs, trafic, saturation)
• Page /platform/monitoring avec graphiques temps réel (recharts)
• Command Palette (cmdk) — navigation rapide vers toutes les routes
• Vite manualChunks — split admin-vendor, admin-platform, admin-tenant
• Virtualisation react-window pour les tables > 100 lignes

Phase 4 — Polish (1-2 sem)

Remplir les routes vides + MFA + Alertes

• Implémenter /infrastructure (health checks, DB stats, cache)
• Implémenter les 4 /modules-* (vues synthétiques des modules)
• MFA TOTP obligatoire pour SUPER_ADMIN
• Alertes email (5 échecs login, suppression établissement, export masse)
• Documentation admin complète (guide opérateur)

✓ Conclusion

Recommandation finale : Proposition B

L'architecture dual-plane (Control Plane / Data Plane) avec CASL.js et RLS PostgreSQL offre le meilleur rapport effort/impact. Elle transforme eLISAschool en vrai SaaS enterprise-grade sans réécrire le frontend existant. Le score passe de 5.5/10 à 9.0/10 en 7-8 semaines.
