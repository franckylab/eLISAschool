01 Executive Summary

Vue d'ensemble stratégique

eLISAschool doit évoluer d'un RBAC monolithique vers une architecture dual-plane inspirée du modèle Auth0 Organizations, permettant une séparation stricte entre les utilisateurs/roles/permissions de la plateforme et ceux des établissements tenants.

🔴

Problème

67 rôles et ~230 permissions mélangés dans un seul enum. Pas de distinction entre utilisateurs plateforme et tenant. 5 rôles plateforme définis mais non fonctionnels. Un seul table utilisateurs pour tous.

🔵

Solution

Architecture dual-plane : table identites (identité globale), utilisateurs_plateforme (admins plateforme), memberships (pivot user×org+role). Deux systèmes CASL indépendants.

🟢

Impact

Séparation complète des responsabilités. Scalabilité multi-tenant enterprise. Conformité SOC2. Isolation des données plateforme. Délégation d'administration par groupe.

03 Auth0 Organizations

Modèle conceptuel approfondi

Auth0 Organizations est le modèle de référence pour le B2B SaaS. Il introduit une couche d'abstraction entre la plateforme (Auth0 tenant) et les clients (Organizations).

🏢

Tenant (Auth0)

Le SaaS lui-même (eLISAschool). Contient la configuration globale : providers d'identité, policies de mot de passe, MFA, branding par défaut, catalogues de rôles.

🏫

Organization

Un client B2B = un établissement. Possède ses propres membres, roles assignés, connections (SSO), branding, et paramètres. Isolation complète des données.

👤

Member

Un utilisateur dans une Organization. Le même email peut être membre de plusieurs organizations avec des rôles différents. C'est le concept de membership.

🔑

Connection

Provider d'identité (Google, Microsoft, SAML, OIDC). Peut être assigné à une Organization spécifique pour du SSO par établissement.

🎭

Platform Admin

Existe en dehors des Organizations. Gère la plateforme elle-même : billing, monitoring, configuration globale. Rôle au niveau du tenant, pas d'une Organization.

🎫

Token Claims

Le JWT contient org_id (Organization courante), org_roles (rôles dans cette Organization). Permet au backend de résoudre les permissions au vol.

Structure du token JWT Auth0 Organizations

JWT Payloadapplication/json
{
  "sub": "auth0|user_abc123",         // Identité globale
  "org_id": "org_etab_lyon_001",       // Organization courante
  "org_name": "Lycée International de Lyon",
  "org_roles": ["ADMIN", "ENSEIGNANT"],  // Rôles dans CETTE org
  "permissions": ["notes:create", "bulletins:generate"],
  "platform_role": null,                // null = pas admin plateforme
  "email": "directeur@lyon.edu",
  "email_verified": true
}

06 Architecture Recommandée

Modèle C — Auth0 Internalisé en détail

Architecture dual-plane avec séparation stricte des identités, rôles et permissions entre la plateforme et les tenants.

🌐 Control Plane (Plateforme)

Table : utilisateurs_plateforme
Rôles : SUPER_ADMIN, ADMIN_PLATEFORME, SUPPORT, BILLING_MANAGER, ANALYST, AUDITOR
Permissions : PermissionPlateforme enum séparé (~40 permissions)
CASL : definePlatformAbility() indépendant

🏫 Data Plane (Tenant/Établissement)

Table : utilisateurs (existante, via membership)
Rôles : Role enum existant (ADMIN, ENSEIGNANT, ELEVE, etc.)
Permissions : Permission enum existant (~230 permissions)
CASL : defineAbility() existant, inchangé

🔗 Couche Identité (Globale)

Table : identites
Rôle : Source unique de vérité pour l'email, le mot de passe hashé, le MFA. Une identité peut avoir N memberships (plateforme + établissements).
Clé : email unique global

🎫 Pivot Membership

Table : memberships
Rôle : Associe une identité à un contexte (plateforme OU établissement) avec un rôle. Permet le multi-rôle : même user = admin plateforme + enseignant dans étab A.

Flux d'authentification dual-plane

Flux JWT — Résolution dual-planeTypeScript
// 1. Login → résout toutes les memberships de l'identité
const identite = await identitesRepo.findOne({ email });
const memberships = await membershipsRepo.find({
  where: { identiteId: identite.id }
});

// 2. Construire le JWT avec les deux contextes
const payload = {
  sub: identite.id,
  email: identite.email,
  // Contexte plateforme (si membership plateforme existe)
  platform: memberships.find(m => m.contexteType === 'PLATEFORME')
    ? { role: 'SUPER_ADMIN' }
    : null,
  // Contexte tenant (établissement sélectionné)
  tenant: {
    etablissementId: selectedMembership.contexteId,
    role: selectedMembership.role,
    permissions: resolveTenantPermissions(selectedMembership.role)
  }
};

// 3. Middleware résout le bon CASL ability
if (req.path.startsWith('/api/platform/')) {
  req.ability = definePlatformAbility(payload.platform);
} else {
  req.ability = defineTenantAbility(payload.tenant);
}

09 Intégration CASL.js

Dual Ability System — Code complet

Deux fonctions defineAbility indépendantes : une pour la plateforme, une pour les tenants. Même package @casl/ability, règles totalement séparées.

shared/src/casl/platform-abilities.tsTypeScript
import { AbilityBuilder, createMongoAbility } from '@casl/ability';

// Actions plateforme
type PlatformAction =
  | 'manage' | 'read' | 'create' | 'update' | 'delete'
  | 'approve'      // Actions critiques MFA
  | 'export'
  | 'toggle';      // Activer/désactiver modules

// Subjects plateforme
type PlatformSubject =
  | 'Etablissement' | 'Abonnement' | 'Facture'
  | 'Plan' | 'Provider' | 'Module'
  | 'PlatformUser' | 'PlatformRole'
  | 'Monitoring' | 'AuditLog'
  | 'ActionCritique' | 'Backup'
  | 'Configuration' | 'GroupeSaaS'
  | 'all';

export type PlatformAbility = createMongoAbility<
  [PlatformAction, PlatformSubject]
>;

export function definePlatformAbility(
  role: string | null
): PlatformAbility {
  const { can, cannot, build } = new AbilityBuilder(createMongoAbility);

  switch (role) {
    case 'SUPER_ADMIN':
      can('manage', 'all');
      break;

    case 'ADMIN_PLATEFORME':
      can('manage', ['Etablissement', 'Abonnement', 'PlatformUser']);
      can('read', ['Monitoring', 'AuditLog', 'Configuration']);
      can('update', 'Configuration');
      cannot('approve', 'ActionCritique'); // Réservé SUPER_ADMIN
      cannot('delete', 'PlatformUser', { role: 'SUPER_ADMIN' });
      break;

    case 'SUPPORT':
      can('read', ['Etablissement', 'Monitoring', 'AuditLog']);
      cannot('create', 'all');
      cannot('update', 'all');
      cannot('delete', 'all');
      break;

    case 'BILLING_MANAGER':
      can('manage', ['Facture', 'Plan', 'Provider', 'Abonnement']);
      can('read', ['Etablissement', 'Module']);
      cannot('delete', 'Etablissement');
      break;

    case 'ANALYST':
      can('read', 'all');
      can('export', 'all');
      cannot('create', 'all');
      cannot('update', 'all');
      cannot('delete', 'all');
      break;

    case 'AUDITOR':
      can('read', ['AuditLog', 'Monitoring', 'Etablissement']);
      can('export', ['AuditLog', 'Monitoring']);
      cannot('create', 'all');
      break;

    default:
      // Pas de rôle plateforme → aucun accès
      cannot('manage', 'all');
  }

  return build();
}
backend/src/common/middlewares/dual-casl.middleware.tsTypeScript
import { definePlatformAbility } from '@shared/casl/platform-abilities';
import { defineAbility } from '@shared/casl/abilities';

// Middleware qui résout le bon CASL ability selon le contexte
export function dualCaslMiddleware(req: Request, res: Response, next: NextFunction) {
  const user = req.utilisateur;

  if (req.path.startsWith('/api/platform/')) {
    // Contexte PLATEFORME → utiliser definePlatformAbility
    const platformMembership = user.memberships?.find(
      m => m.contexteType === 'PLATEFORME'
    );
    req.ability = definePlatformAbility(platformMembership?.role ?? null);
    req.contexteType = 'PLATEFORME';
  } else {
    // Contexte TENANT → utiliser defineAbility (existant)
    const tenantMembership = user.memberships?.find(
      m => m.contexteId === user.etablissementId
    );
    req.ability = defineAbility({
      role: tenantMembership?.role ?? 'ANONYME',
      etablissementId: user.etablissementId,
    });
    req.contexteType = 'TENANT';
  }

  next();
}

Recommandation finale

Le Modèle C (Auth0 Internalisé) est recommandé car il offre le meilleur équilibre entre :

  • Séparation complète des identités, rôles et permissions plateforme/tenant
  • Zéro dépendance externe — pas de coût SaaS, pas de latence réseau
  • Migration progressive — compatible avec le codebase existant (CASL.js, TypeORM, PostgreSQL)
  • Multi-org natif — un enseignant peut être membre de plusieurs établissements
  • Souveraineté totale — toutes les données restent dans PostgreSQL, conformité SOC2/OHADA

Prochaine étape : validation du cadrage par le sponsor projet, puis lancement de la Phase 1 (Fondations) — estimée à 2 semaines.
