Section 03

Trois propositions — Comparatif

Analyse de 3 approches : moteur custom, plateforme Lago (open-source), ou Stripe Billing. Contexte Afrique = contraintes spécifiques.

A. Moteur Custom

0 licence + dev interne

Construction interne TypeORM + Express, adapters paiement Afrique natifs.

  • Contrôle total sur la logique SaaS
  • Mobile Money natif (MTN, OM, Wave)
  • Conformité OHADA sur mesure
  • Intégration parfaite avec ModuleRegistry
  • Pas de dépendance externe critique
  • Facturation XAF/XOF sans conversion
  • Effort de développement initial (~8 s.h.)
  • Responsabilité PCI-DSS (allégé si pas de stockage carte)

B. Lago (open-source)

~150€ /mois (cloud) ou self-hosted

Plateforme de facturation usage-based open-source, API REST.

  • Usage meters built-in
  • Facturation récurrente avancée
  • Self-hosted possible (Docker)
  • Pas de support Mobile Money natif
  • Devise EUR/USD uniquement (pas XAF)
  • Infrastructure supplémentaire (PostgreSQL dédié)
  • Intégration complexe avec ModuleRegistry
  • Conformité OHADA à implémenter

C. Stripe Billing

34€ /mois + 1.4% + 0.24€ / transaction

Leader mondial SaaS billing. Webhooks, dunning, proration.

  • Feature-complete (dunning, proration, credits)
  • Dashboard propriétaire puissant
  • Mobile Money très limité en Afrique
  • Pas de support XAF/XOF natif
  • Frais élevés pour petits montants
  • Dépendance vendor lock-in forte
  • Non disponible dans tous les pays CEMAC
  • Conformité OHADA non native
✅
Recommandation : Option A (Moteur Custom) — Le contexte Afrique (XAF/XOF, Mobile Money dominant, OHADA) rend les solutions internationales inadaptées. Le coût de développement est amorti en 6 mois par l'absence de commissions per-transaction. L'architecture existante (TypeORM, ModuleRegistry, ParametreSysteme) fournit 70% des briques nécessaires.
Section 04

Catégorisation dynamique des modules

Le propriétaire de plateforme configure depuis l'interface quels modules sont gratuits, premium, ou add-on — sans toucher au code.

requireModuleAccess.middleware.tsTypeScript
// Middleware unifié : remplace requireModuleActive
export function requireModuleAccess(moduleNom: string) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const etabId = req.utilisateur?.etablissementId;
    const config = MODULE_REGISTRY[moduleNom];

    // 1. Modules critiques = toujours accessibles
    if (config?.critical) return next();

    // 2. Vérifier activation (ParametreSysteme)
    const estActif = await configService.isModuleActive(moduleNom, etabId);
    if (!estActif) throw new AppError('Module inactif', 403, 'MODULE_INACTIVE');

    // 3. Gating premium → vérifie l'abonnement
    if (config?.premium) {
      const abonnement = await subscriptionService.getActiveSubscription(etabId);
      if (!abonnement?.modulesSouscrits.includes(moduleNom)) {
        throw new AppError('Module premium non souscrit', 403, 'MODULE_PREMIUM_REQUIS');
      }
    }

    // 4. Quotas (ex: max 500 élèves en plan gratuit)
    const quotaOk = await quotaService.checkQuota(etabId, moduleNom);
    if (!quotaOk) throw new AppError('Quota dépassé', 429, 'QUOTA_EXCEEDED');

    next();
  };
}

Schéma de base de données

💡
Convention montants : Tous les montants sont stockés en entiers (XAF) — pas de float. 15000 = 15 000 FCFA. La TVA (19.25% Cameroun) est calculée au moment de la facturation, pas stockée dans le prix du plan.
Section 06

Intégration paiement Afrique

6 adapters pour couvrir le paysage de paiement en Afrique centrale et de l'Ouest. Strategy pattern pour ajouter de nouveaux canaux sans modifier le core.

📱

MTN Mobile Money

19+ pays africains. API REST avec OAuth2. Push payment (USSD trigger). Callback webhook asynchrone. Frais ~1%.

🍊

Orange Money

OAuth2 (tokens 55min). API Web + USSD. Couverture : 15+ pays. Push payment + pull payment. Frais ~1.5%.

🌊

Wave

Frais les plus bas (~1%). Sénégal, Côte d'Ivoire, Cameroun. API simple, webhook temps réel. Pas de carte bancaire.

💳

Paystack

Nigeria, Ghana, Afrique du Sud, Kenya. Cartes + mobile money + bank transfer. 1.5% + ₦100. Dashboard excellent.

🔄

Flutterwave

34+ pays africains. Multi-devise (XAF, XOF, NGN, GHS...). Cartes + mobile money + bank. 3.8% international.

🏦

Manuel (Virement/Espèces)

Saisie manuelle par le SUPER_ADMIN après vérification bancaire. Preuve de paiement uploadée. Aucun frais API.

payment-adapter.interface.tsStrategy Pattern
interface IPaymentAdapter {
  initialiserPaiement(params: {
    montant: number;         // en XAF
    devise: 'XAF' | 'XOF';
    referenceFacture: string;
    canal: CanalPaiement;    // 'mtn_momo' | 'orange_money' | 'wave' | ...
    returnUrl: string;
    webhookUrl: string;
    metadata?: Record<string, unknown>;
  }): Promise<{ urlPaiement: string; referenceExterne: string }>;

  verifierStatut(referenceExterne: string): Promise<{
    statut: 'succes' | 'echec' | 'en_attente';
    montantRecu: number;
    frais?: number;
  }>;

  traiterWebhook(payload: unknown, signature: string): {
    type: 'payment.succeeded' | 'payment.failed' | 'refund.completed';
    referenceFacture: string;
    montant: number;
  };
}

Section 07

Facturation multi-établissement & Groupes

3 modèles de facturation pour les groupes d'établissements. Le modèle hybride est recommandé pour la flexibilité.

A. Facturation individuelle

Chaque établissement a son propre abonnement et sa propre facture. Indépendance totale.

Avantage : Simple, isolation comptable
Inconvénient : Pas de volume discount

B. Facturation consolidée

Une seule facture pour le groupe. Le propriétaire du groupe reçoit tout. Répartition interne libre.

Avantage : Volume discount, une seule facture
Inconvénient : Pas de visibilité par établissement

C. Hybride (recommandé)

Facture consolidée + détail par établissement. Le groupe voit le total, chaque établissement voit sa part.

Avantage : Le meilleur des deux mondes
Inconvénient : Plus complexe à implémenter
facture-groupe.service.tsModèle hybride
async genererFactureGroupe(groupeId: string, periode: Date) {
  const membres = await groupeService.getMembres(groupeId);
  const plan = await planService.getPlanGroupe(groupeId);

  // Calculer le total consolidé avec dégressivité
  const totalBrut = plan.prix_mensuel * membres.length;
  const reduction = calculerDegressivite(membres.length); // ex: -10% si >5
  const totalNet = totalBrut * (1 - reduction);

  // Créer la facture consolidée
  const facture = await this.repo.save({
    groupeId,
    numero: await genererNumero('GR'),
    total_ht: totalNet,
    total_ttc: calculerTVA(totalNet),
    lignes: membres.map(m => ({
      etablissementId: m.id,
      etablissementNom: m.nom,
      montant: totalNet / membres.length, // répartition égale
    })),
  });

  // Notification au propriétaire du groupe + chaque établissement
  await notifierFactureGroupe(facture, membres);
  return facture;
}

Section 09

Roadmap d'implémentation

4 phases sur 12 semaines. Chaque phase livre de la valeur immédiatement et est testable indépendamment.

Phase 1 — Fondations (Semaines 1-3)

Entités TypeORM (plans, abonnements, factures, paiements). Migration SQL. CRUD API pour plans et abonnements. Middleware requireModuleAccess. Seed de 4 plans par défaut.

~3 semaines • 2 personnes

Phase 2 — Paiement (Semaines 4-6)

Interface IPaymentAdapter + 3 adapters prioritaires (MTN MoMo, Orange Money, Wave). Webhook handler. Gestion des échecs de paiement. Dunning basique (3 relances email). Paiement manuel (virement/espèces).

~3 semaines • 2 personnes

Phase 3 — UI Propriétaire (Semaines 7-9)

Page admin /admin/billing avec dashboard revenus (MRR, ARR, churn). Configuration des plans depuis l'interface (CRUD complet). Gestion des modules par plan (drag & drop). Suivi des établissements (filtres, export).

~3 semaines • 2 personnes

Phase 4 — Avancé (Semaines 10-12)

Facturation de groupe (modèle hybride). Usage meters pour add-ons (SMS, stockage). Crédits et avoirs (credit notes). Conformité OHADA complète (numérotation séquentielle, TVA, export comptable). Paystack + Flutterwave adapters.

~3 semaines • 2 personnes
