Modèle actuel : Shared Schema (single database)

eLISAschool utilise un modèle shared schema : une seule base PostgreSQL, toutes les tables contiennent une colonne etablissementId (UUID) qui assure l'isolation multi-tenant. Chaque requête est filtrée par ce champ via des middlewares globaux.

🔒

Isolation par middleware

tenant.middleware.ts résout l'etablissementId depuis le JWT et force le filtrage sur toutes les requêtes API. Détection de cross-tenant avec log de violation.

👥

Multi-établissement utilisateur

Table UtilisateurEtablissement permet à un utilisateur d'accéder à N établissements avec des rôles différents par établissement.

⚙

Modules activables

ParametreSysteme scopé (NULL = global, UUID = établissement). Middleware requireModuleActive() protège les routes par module.

📈

Quotas SaaS (existant)

EtablissementConfig stocke déjà : maxEleves, maxUtilisateurs, maxClasses, stockageMaxMB, planAbonnement, dateExpiration.

🔌

Configuration scopée

ParametreSysteme avec override établissement : un paramètre global peut être surchargé par établissement (priorité cascade).

🔗

Switch établissement

Flow complet : login → détection multi-établissement → sélection → JWT scopé. EtablissementSwitcher dans le header frontend.

2 Évaluation de faisabilité SaaS

Le modèle proposé est-il compatible avec l'architecture existante ?

✓

Verdict : Faisable — Migration progressive recommandée

L'architecture actuelle d'eLISAschool est pré-saaS : l'isolation multi-tenant par etablissementId, les quotas (EtablissementConfig), les modules activables et le RBAC granulaire constituent une base solide. La transition vers un modèle hybride (catalog + database-per-instance) est réalisable sans réécriture complète.

⚠️ Architecture actuelle

  • 1 base PostgreSQL partagée
  • Isolation par colonne etablissementId
  • Tous les clients dans la même DB
  • Pas de séparation par souscripteur
  • Pas de catalogue de tenants
  • Pas de provisioning automatique
  • Pas de facturation intégrée
  • Modules activables par établissement (pas par instance)

✅ Architecture cible SaaS

  • 1 base catalogue + N bases instances
  • 1 souscripteur = 1 instance (1..N établissements)
  • Isolation physique des données clients
  • Multi-tenant par établissement dans chaque instance
  • Catalogue central (routing, billing, provisioning)
  • Provisioning automatique à l'inscription
  • Facturation Stripe intégrée
  • Modules activables par instance (feature flags)

Modèle proposé par le porteur de projet

Client (souscripteur) → souscrit à un plan → obtient 1 instance (base de données dédiée).
Instance → contient 1 à N établissements (selon le plan) avec isolation multi-tenant interne.
Modules → activables/désactivables par instance via feature flags.
Catalogue central → route les utilisateurs vers la bonne instance, gère la facturation et le provisioning.

4 Stratégie d'implémentation

Approche progressive en 6 phases pour minimiser les risques et livrer de la valeur à chaque étape.

Principe directeur : Migration progressive (Strangler Fig)

L'architecture existante reste opérationnelle pendant la migration. Chaque phase ajoute une couche sans casser le système actuel. Le pattern Strangler Fig permet de remplacer progressivement les composants monolithiques par les composants SaaS.

P1

Phase 1 — Catalogue

Créer la base catalogue avec les entités Souscripteur, Instance, Plan, Abonnement. Ajouter le InstanceResolver qui détermine la DB cible depuis le JWT.

~2 semaines Risque faible
P2

Phase 2 — Connection Pool dynamique

Implémenter le ConnectionManager : pool de connexions par instance, cache LRU, health checks, fallback. TypeORM supporte les DataSource multiples.

~2 semaines Risque moyen
P3

Phase 3 — Provisioning

Automatiser la création d'instance : clone DB template, exécute migrations, crée le premier admin, enregistre dans le catalogue. Script provision-instance.ts.

~1.5 semaines Risque moyen
P4

Phase 4 — Feature Flags

Remplacer ParametreSysteme pour les modules par les FeatureFlags du catalogue. Middleware requireModuleActive() lit désormais le catalogue (cache Redis 5min).

~1 semaine Risque faible
P5

Phase 5 — Billing Stripe

Intégrer Stripe : webhooks (invoice.paid, customer.subscription.deleted), portal client, upgrade/downgrade de plan, trial period, prorata.

~2 semaines Risque élevé
P6

Phase 6 — Portal Admin + Migration données

Dashboard souscripteur (usage, factures, settings). Outil de migration des données existantes vers des instances séparées. Monitoring par instance.

~3 semaines Risque moyen

Détail technique — Connection Manager

// backend/src/common/database/connection-manager.ts export class ConnectionManager { private pools = new Map<string, DataSource>(); private catalogRepo: Repository<Instance>; private readonly MAX_POOLS = 50; // LRU eviction async getConnection(instanceId: string): Promise<DataSource> { // 1. Cache hit if (this.pools.has(instanceId)) { return this.pools.get(instanceId)!; } // 2. LRU eviction si limite atteinte if (this.pools.size >= this.MAX_POOLS) { await this.evictLeastUsed(); } // 3. Charger config depuis catalogue const instance = await this.catalogRepo.findOne({ where: { id: instanceId, statut: 'ACTIF' } }); // 4. Créer DataSource dynamique const ds = new DataSource({ type: 'postgres', host: instance.dbHost, port: instance.dbPort, database: instance.dbName, username: process.env.DB_USER, password: process.env.DB_PASSWORD, synchronize: false, // JAMAIS en prod entities: [/* mêmes entités */], }); await ds.initialize(); this.pools.set(instanceId, ds); return ds; } }

Middleware de résolution d'instance

Le JWT contient désormais un claim instanceId. Le middleware resolveInstance (appliqué globalement) récupère la connexion DataSource correspondante via le ConnectionManager et l'attache à req.dataSource. Tous les repositories utilisent cette connexion dynamique au lieu du DataSource global.

6 Analyse des risques

Risques identifiés et stratégies de mitigation.

Fuite de données inter-instances Critique

Un bug dans le ConnectionManager pourrait servir les données de l'instance A à l'utilisateur de l'instance B. Mitigation : tests d'intégration systématiques avec 3+ instances, middleware de vérification croisée, audit logs de chaque requête DB.

Connection pool exhaustion Critique

Avec 50+ instances actives, le nombre de connexions PostgreSQL peut dépasser les limites serveur. Mitigation : PgBouncer en mode transaction, LRU eviction agressive, limite de connexions par pool (max 5/instance), monitoring alertes.

Migration des données existantes Élevé

Transférer les données de la DB unique vers des instances séparées sans perte ni temps d'arrêt prolongé. Mitigation : outil de migration avec dry-run, validation checksum, rollback possible, fenêtre de maintenance planifiée.

Complexité opérationnelle Élevé

Gérer N bases de données (backups, migrations schema, monitoring) au lieu d'une seule. Mitigation : scripts automatisés de backup par instance, migration runner centralisé, dashboard monitoring unifié, alertes Prometheus/Grafana.

Coût infrastructure Modéré

N bases PostgreSQL coûtent plus cher qu'une seule (stockage, RAM, CPU). Mitigation : PostgreSQL schema-per-tenant comme option intermédiaire pour les petits clients, database-per-tenant uniquement pour les plans Pro/Enterprise. Mutualisation via schemas partagés.

Latence multi-DB Modéré

Changer de connexion DB à chaque requête ajoute une latence. Mitigation : pool persistant (pas de re-connexion), Redis pour les données fréquemment lues, connexion pré-établie au login.

7 Recommandations finales

Stratégie optimale basée sur l'analyse du code existant et les meilleures pratiques SaaS 2025-2026.

1. Architecture hybride (recommandée)

Combiner shared schema pour les petits clients (Starter) et database-per-instance pour les plans Pro/Enterprise. Réduit le coût infrastructure tout en offrant l'isolation physique aux clients premium.

2. Catalogue minimaliste

La base catalogue ne contient aucune donnée métier. Uniquement : routing, billing, provisioning, feature flags. Toute la logique métier reste dans les bases instances (code existant réutilisé à 95%).

3. Migration progressive

Ne pas réécrire. Ajouter la couche catalogue par-dessus l'existant. Le système actuel continue de fonctionner pendant le développement. Migration des données en phase 6 uniquement.

4. PgBouncer obligatoire

Indispensable pour le connection pooling multi-DB. Mode transaction (pas session). Max 5 connexions actives par instance. Monitoring du pool en temps réel.

5. Stripe natif

Utiliser Stripe Checkout + Customer Portal (pas de développement de UI de paiement). Webhooks pour synchroniser les statuts. Prorata automatique pour upgrade/downgrade.

6. Template DB pour provisioning

Créer une base template avec schema + seeds système. Le provisioning clone cette template (CREATE DATABASE ... WITH TEMPLATE). Time-to-provision < 30 secondes.

Réutilisation du code existant

95% du code métier est réutilisable tel quel. Les entités, services, controllers, et le frontend ne changent pas. Seules modifications :

  • Ajout du ConnectionManager et du middleware resolveInstance
  • Remplacement du DataSource global par req.dataSource dans les repositories
  • Ajout de la couche catalogue (nouveau module backend)
  • Modification du JWT pour inclure instanceId
  • Portal souscripteur (nouveau frontend)

Conclusion

L'architecture multi-tenant actuelle d'eLISAschool est excellente base pour une transformation SaaS. Le modèle proposé (instance par client + multi-tenant interne par établissement + modules activables) est cohérent, réalisable et aligné sur les meilleures pratiques du secteur. La migration progressive (Strangler Fig) permet de livrer de la valeur à chaque phase sans interrompre le service existant. Le coût total estimé est de ~11.5 semaines de développement pour une équipe de 2 personnes, avec un taux de réutilisation du code existant de 95%.
