05 — Failles Identifiees

5 failles critiques analysees

L'audit a identifie 5 failles majeures dans la gestion actuelle des modules, classees par severite et impact.

G1
CRITIQUE P0

Exposition totale du catalogue aux etablissements

Symptome : GET /api/billing/modules/catalogue retourne les 41 modules avec prix, sans filtre par plan ni abonnement.

Impact : Un etablissement plan Gratuit voit les modules Enterprise et leurs tarifs. Fuite d'information commerciale et confusion UX.

Root cause : Le controller billing.controller.ts ne filtre pas la reponse — il retourne moduleResolutionService.getCatalogue() brut.

Etat actuel

  • Tous les modules visibles par tous
  • Prix exposes (mensuel + annuel)
  • Pas de distinction plan/abonnement
  • Categories visibles (PREMIUM, ADDON)

Etat cible

  • Modules du plan + modules souscrits uniquement
  • Prix masques ou "Contacter le support"
  • Badge "Decouvrir" pour modules upgradables
  • Teasing controle (nom + description, pas de prix)
G2
CRITIQUE P0

Double source de verite (MODULE_REGISTRY vs modules_catalogue)

Symptome : shared/src/config/config.registry.ts reference 37 modules, tandis que modules_catalogue en contient 41. Les deux peuvent diverger.

Impact : Le seed utilise MODULE_REGISTRY pour creer les modules DB. Si un module est ajoute dans le registry mais pas synchronise, il est absent de la DB. Inversement, les modules DB peuvent avoir des proprietes differentes du registry.

Recommandation : Deprecier MODULE_REGISTRY. Le catalogue DB doit etre la source unique. Les dependances et configurations doivent migrer dans le champ config JSONB.

G3
CRITIQUE P0

Incoherence isModuleActive() vs moduleResolutionService

Symptome : Le middleware utilise configurationService.isModuleActive() (via ParametreSysteme), tandis que la resolution frontend utilise moduleResolutionService (via la cascade complete). Les deux peuvent retourner des valeurs differentes.

Impact : Un module peut etre affiche comme "actif" dans le dashboard frontend mais bloque par le middleware backend (ou l'inverse). Incoherence UX + bugs d'autorisation.

Service Source Cascade Utilise par
configurationService.isModuleActive() ParametreSysteme Etab → Global → Default module-access.middleware
moduleResolutionService Cascade complete Etab → Groupe → Suppl → Plan → Catalogue Frontend, API /resolved
G4
HAUTE P1

Comportement sans plan actif non defini

Symptome : Quand un etablissement n'a pas d'AbonnementClient actif, le middleware retourne 402 pour tout module facturable. Mais les modules CRITIQUE restent accessibles via le bypass configurationService.

Impact : Comportement incoherent : certains modules fonctionnent (critiques), d'autres non (premium), sans message clair pour l'utilisateur. Pas de page "Choisir un plan" ou de periode d'essai.

Recommandation : Definir un comportement explicite : periode d'essai (14 jours tous modules), puis degradation gracieuse (modules critiques seuls) avec CTA upgrade.

G5
HAUTE P1

Cache invalidation timing (60s staleness)

Symptome : Apres un toggleModule(), l'invalidation est fire-and-forget (async). Pendant 60s (TTL cache), les requetes peuvent retourner un etat obsolete.

Impact : Un admin plateforme desactive un module, mais les etablissements continuent d'y acceder pendant 60 secondes. Incoherence temporaire mais potentiellement critique pour les modules sensibles.

Recommandation : Invalidation synchrone du cache in-memory (le plus critique). Redis invalidation peut rester async. Ajouter un header X-Cache-Status pour debugging.

06 — Benchmark SaaS

Meilleures pratiques du marche

Analyse des pratiques de 12 references SaaS (Stripe, Moesif, Flexitee, etc.) pour la gestion des modules, le feature gating et la facturation multi-tenant.

Feature Gating

Les leaders SaaS (Stripe, LaunchDarkly) utilisent un feature flag service centralise avec cascade : organisation → plan → feature flag individuel. La resolution est toujours cote serveur, jamais cote client.

stripe.com/billing, moesif.com

Catalogue Produit

Stripe Product API : un Product a des Prices (mensuel/annuel). Les Subscriptions referencent des Prices. Pas de double source de verite. Le catalogue est la source unique.

stripe.com/docs/products-prices

Graceful Degradation

Quand un abonnement expire, les donnees sont preservees en lecture seule. Pas de suppression brutale. L'utilisateur peut voir ses donnees mais pas creer de nouvelles. CTA upgrade visible.

tiun.io, flexitee.io

Teasing vs Gating

Deux strategies : Hard gate (feature invisible) vs Soft gate / Teasing (feature visible mais verrouillee avec CTA). Le teasing convertit 3-5x mieux (source : OpenView Partners).

openviewpartners.com

Entitlements

Pattern emergent : Entitlement Service qui repond a "Ce tenant a-t-il acces a cette feature ?". Combine plan + addons + overrides + trial en une seule API. Cache agressif (30s-60s).

paths.grisp.study, storminternet.co.uk

Multi-tenant Isolation

RLS PostgreSQL + schema-level isolation pour les grandes plateformes. Le feature gating doit etre coherent avec l'isolation : un module desactive ne doit pas laisser de residus dans les requetes.

medium.com/appfoster

07 — Recommandations

12 recommandations par priorite

Actions correctives et ameliorations proposees, classees par urgence. Les P0 doivent etre traitees avant le prochain deployement.

P0 Corrections critiques

R1. Filtrer le catalogue client

Action : Modifier GET /api/billing/modules/catalogue pour retourner uniquement les modules du plan + modules souscrits + modules upgradables (teasing sans prix).

// billing.controller.ts
GET /api/billing/modules/catalogue
// Avant: return catalogue complet
// Apres: return {
//   actifs: modules_resolus,
//   upgradables: modules_premium_non_souscrits 
//     (sans prix, avec description),
// }

Fichiers : billing.controller.ts, module-resolution.service.ts

R2. Unifier la resolution

Action : Remplacer configurationService.isModuleActive() dans le middleware par moduleResolutionService.isModuleActif(). Une seule cascade, une seule source de verite.

// module-access.middleware.ts
// Avant: configurationService.isModuleActive()
// Apres: moduleResolutionService.isModuleActif(
//   moduleCode, etablissementId
// )

Fichiers : module-access.middleware.ts, module-resolution.service.ts

R3. Supprimer MODULE_REGISTRY

Action : Migrer les dependances et configurations de config.registry.ts vers le champ config JSONB de ModuleCatalogue. Deprecier le registry.

// module-catalogue.entity.ts
// config: jsonb contient desormais :
{
  "dependencies": ["auth", "utilisateurs"],
  "permissionsRequises": ["notes:view"],
  "categorieLegacy": "pedagogie",
  "defaultActive": true
}

Fichiers : config.registry.ts (suppression), seed-modules-catalogue.ts (migration)

P1 Ameliorations majeures

R4. Periode d'essai automatique

Action : A la creation d'un etablissement, creer un AbonnementClient en statut ESSAI (14 jours, tous modules actifs). Notification J-3 avant expiration.

R5. Degradation gracieuse

Action : Si abonnement expire : modules critiques restent en lecture, modules premium passent en "teasing" (visible, non utilisable, CTA upgrade). Pas de 402 brutal.

R6. Invalidation cache synchrone

Action : Apres toggleModule(), invalidation synchrone du cache in-memory. Redis invalidation reste async. Ajouter X-Cache-Status: HIT|MISS|STALE dans les reponses.

R7. Page "Mes Modules" etablissement

Action : Nouvelle page dans la sidebar tenant montrant les modules actifs, les modules upgradables (teasing), et l'etat de l'abonnement. Pas de configuration, juste de la visibilite.

P2 Evolutions

R8. Entitlement Service dedie

Extraire la logique de resolution dans un EntitlementService avec API unique : canAccess(etabId, moduleCode) → {allowed, reason, upgradeUrl}.

R9. Module Builder plateforme

Interface de creation de modules custom par le SUPER_ADMIN : code, nom, categorie, prix, dependances (drag & drop), configuration JSONB. Pas de code requis.

R10. Marketplace d'add-ons

Page marketplace pour les modules ADDON : description, screenshots, avis, prix, bouton "Essayer 7 jours". Pattern app store.

R11. Analytics d'utilisation

Tracker l'utilisation reelle de chaque module par etablissement. Detecter les modules sous-utilises (optimisation plan) et les modules sur-utilises (upsell).

R12. Webhooks module lifecycle

Emettre des webhooks quand un module est active/desactive/souscrit/resilie. Permettre aux integrations externes de reagir.
