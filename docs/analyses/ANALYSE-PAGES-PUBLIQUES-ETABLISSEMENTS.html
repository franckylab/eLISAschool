Résumé exécutif

Ce rapport analyse la faisabilité d'ajouter des pages publiques dédiées par établissement dans la plateforme eLISAschool. L'objectif est de permettre à chaque établissement de disposer d'un lien partageable (ex: elisaschool.com/e/lycee-moliere) menant à une page d'accueil personnalisée avec les informations publiques de l'établissement.

✅
Verdict : Faisabilité confirmée. L'architecture multi-tenant existante (ADR-005, RLS PostgreSQL, isolation 5 couches) supporte nativement cette fonctionnalité. Le champ codeEtablissement (unique) sert de slug URL naturel. Le middleware optionalAuthMiddleware existe déjà mais est inutilisé — il est le mécanisme idéal pour enrichir les pages publiques avec le contexte utilisateur.

L'approche recommandée est le path-based routing (/e/:code) — simple, sans configuration DNS, compatible CDN, et cohérent avec le routeur TanStack existant. L'effort d'implémentation est estimé à 3-5 jours de développement répartis en 4 phases.

4.3 — Code backend proposé (endpoint public)

// backend/src/modules/etablissement/controllers/etablissement-public.controller.ts import { Router, Request, Response } from 'express'; import { optionalAuthMiddleware } from '@modules/auth/middlewares'; import { AppDataSource } from '@database/data-source'; import { Etablissement } from '../entities'; import { redisService } from '@common/services/redis.service'; const router = Router(); const CACHE_TTL = 300; // 5 minutes /** * GET /api/public/etablissements/:code * Montage : AVANT tenantMiddleware dans app.ts * Auth : optionnelle (optionalAuthMiddleware) * RLS : AUCUN (pas de contexte tenant) */ router.get('/:code', optionalAuthMiddleware, async (req: Request, res: Response) => { const { code } = req.params; // 1. Cache Redis const cacheKey = `public:etab:${code}`; const cached = await redisService.get(cacheKey); if (cached) return res.json({ success: true, data: JSON.parse(cached) }); // 2. Projection publique UNIQUEMENT (pas de données tenant) const repo = AppDataSource.getRepository(Etablissement); const etab = await repo.createQueryBuilder('e') .select([ 'e.id', 'e.nom', 'e.slogan', 'e.logo', 'e.couleurPrimaire', 'e.couleurSecondaire', 'e.typeEtablissement', 'e.sousSysteme', 'e.langueDefaut', 'e.codeEtablissement' ]) .where('e.codeEtablissement = :code', { code }) .andWhere('e.statut = :statut', { statut: 'ACTIF' }) .getOne(); if (!etab) return res.status(404).json({ success: false, error: { code: 'ETABLISSEMENT_NON_TROUVE', message: 'Établissement non trouvé' } }); // 3. Cache + réponse await redisService.setJSON(cacheKey, etab, CACHE_TTL); res.json({ success: true, data: etab }); }); export default router;

Alternatives comparées

Quatre approches architecturales ont été évaluées pour exposer des pages publiques par établissement. Chaque approche a des implications différentes en termes de DNS, cache, SEO et complexité.

A — Path-based routing

elisaschool.com/e/lycee-moliere

Sous-chemin /e/:code dans l'application TanStack existante. Aucun changement DNS. Compatible CDN standard.

✔ Avantages
  • Zero config DNS
  • CDN sans wildcard SSL
  • Routing TanStack natif
  • Partage simple (URL courte)
  • Cookie domain unique
✘ Inconvénients
  • Namespace partagé
  • Moins « premium » visuellement

B — Subdomain-based

lycee-moliere.elisaschool.com

Sous-domaine par établissement. Nécessite wildcard DNS + wildcard SSL. Isolation cookie native.

✔ Avantages
  • URL « premium »
  • Isolation cookie native
  • Meilleur SEO par établissement
  • Branding fort
✘ Inconvénients
  • Wildcard DNS + SSL requis
  • CORS complexe
  • Session cross-domain impossible
  • Infrastructure lourde

C — Token-based (signed URL)

elisaschool.com/p/abc129x?sig=...

URL signée avec token HMAC. Expiration configurable. Pas de slug lisible.

✔ Avantages
  • Sécurité maximale
  • Expiration automatique
  • Révocable
✘ Inconvénients
  • URL non-mémorable
  • Non-shareable long terme
  • Pas adapté à une landing page

D — Domaine custom par établissement

www.lycee-moliere.cm

Chaque établissement branche son propre domaine. CNAME vers la plateforme. SSL auto (Let's Encrypt).

✔ Avantages
  • Branding total
  • Indépendance URL
  • SEO propre
✘ Inconvénients
  • Complexité SSL/CNAME énorme
  • Coût infrastructure
  • Gestion certificats par tenant
  • Overkill pour le besoin

5.1 — Matrice de comparaison

Critère A: Path-based B: Subdomain C: Token D: Domaine custom

🎯
Recommandation : Approche A (Path-based) — Le path-based routing offre le meilleur rapport simplicité/fonctionnalité. Il s'intègre naturellement dans l'architecture TanStack Router existante, ne nécessite aucune modification DNS, et permet le partage de liens simples et mémorables. L'approche peut être complétée ultérieurement par des sous-domaines (B) pour les établissements premium sans changement d'architecture backend.

Sécurité & isolation des données

6.1 — Principe de projection publique

La sécurité repose sur un principe fondamental : la projection publique ne contient AUCUNE donnée tenant. L'endpoint backend sélectionne explicitement les champs publics de l'entité Etablissement via un createQueryBuilder().select([...]) restrictif.

Performance & stratégie de cache

7.1 — Impact sur les performances existantes

ℹ️
Impact négligeable. Les pages publiques sont servies depuis le cache Redis (TTL 5 min). En cas de cache miss, la requête est un simple SELECT avec index unique sur codeEtablissement — temps de réponse estimé < 2ms. Aucune jointure, aucun calcul, aucun filtrage RLS.

Plan d'implémentation

9.1 — Timeline — 4 phases, 3-5 jours

Phase 1 — Backend (0.5 jour)

Endpoint public + cache Redis

Créer etablissement-public.controller.ts avec projection restrictive. Monter dans app.ts AVANT tenantMiddleware. Ajouter rate limiting (60 req/min/IP). Cache Redis TTL 300s. Invalidation dans etablissement.service.ts (update/delete).

Phase 2 — Frontend Route (1 jour)

Route /e/$code.tsx + composant page

Créer routes/e.$code.tsx (hors layout _auth). Composant EtablissementPublicPage.tsx avec header thématique (couleurs dynamiques depuis l'établissement), section infos, CTA conditionnel. Hook useEtablissementPublic(code) avec TanStack Query + staleTime 300s.

Phase 3 — UX & thème dynamique (1 jour)

Thème établissement + responsive + dark mode

Application des couleurs de l'établissement sur la page (CSS variables dynamiques). Ultra-responsivité (clamp(), 11 breakpoints). Dark mode respecté. Animation Framer Motion (fade-in, slide-up). SEO meta tags (titre, description, og:image avec logo).

Phase 4 — Tests & polish (1 jour)

Tests E2E + invalidation cache + i18n

Tests unitaires endpoint (projection, 404, rate limit, cache). Tests E2E (navigation, affichage, CTA conditionnel). i18n FR/EN complet. Lien depuis la page établissement platform (« Voir la page publique »). Documentation et mise à jour des règles.

La création de pages publiques dédiées par établissement est techniquement faisable, sécurisée par conception (projection restrictive, pas de contexte tenant), et à faible impact sur l'existant (3-5 jours, ~500 lignes de code, 0 modification DNS).

L'approche path-based (/e/:code) est recommandée pour sa simplicité d'implémentation, sa compatibilité avec l'infrastructure existante (CDN, TanStack Router, Redis), et sa capacité d'évolution vers des sous-domaines premium sans refonte.
