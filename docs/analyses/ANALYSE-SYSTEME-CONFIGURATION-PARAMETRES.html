🏗 1. Architecture Globale

Le systeme de configuration eLISAschool repose sur un principe fondamental : une table unique (parametres_systeme) comme source de verite pour tous les parametres runtime de l'application. Cette approche centralise la configuration tout en permettant le multi-tenancy via un discriminateur cle : etablissementId.

💡 Principe fondamental (ADR-005 + v7.1)

ParametreSysteme est la source unique de verite pour tous les parametres runtime. ConfigurationApp a ete supprimee (v3.0). Les secrets d'infrastructure restent dans .env ; tout le reste va dans ParametreSysteme.

📈 3. Cascade a 4 Niveaux

Le systeme de configuration implemente une cascade a 4 niveaux pour la resolution des valeurs. Chaque niveau peut override le precedent, du plus specifique au plus general.

Priorite 1 — Plus haute

🏫 Niveau Etablissement (Tenant)

etablissementId = UUID — Override specifique a un etablissement. Cree via setParametre(cle, valeur, etablissementId).

Priorite 2

👥 Niveau Groupe

groupeEtablissementId = UUID — Override pour un groupe d'etablissements (migration 167). Utilise uniquement par ParametresCascadeService.

Priorite 3

🌐 Niveau Global (Plateforme)

etablissementId = NULL, groupeEtablissementId = NULL — Valeur par defaut pour tous les etablissements. Cree via setParametre(cle, valeur).

Priorite 4 — Fallback ultime

🔧 Niveau Systeme (valeurDefaut)

Colonne valeurDefaut sur l'entite — valeur codee en dur lors du seed. Dernier recours si aucune valeur n'est trouvee en base.

⚠️ Asymetrie critique : Runtime vs Plateforme

Le service runtime getParametre() ne consulte que 2 niveaux (etablissement → global), ignorant le niveau groupe. Seule la ParametresCascadeService (interface plateforme) exploite les 4 niveaux. Cette asymetrie est detaillee dans les sections 4 et 5.

⚡ 4. Resolution Runtime (getParametre)

La resolution runtime est le chemin emprunte par tous les services backend lorsqu'ils ont besoin d'une valeur de configuration. Elle est optimisee pour la rapidite (cache 60s).

ConfigurationService 2 niveaux
1

Verifier le cache memoire (TTL 60s)

Si la cle est en cache et non expiree → retour immediat. Cle de cache : {cle}:{etablissementId} ou {cle} (global).

2

Chercher l'override etablissement

WHERE cle = $1 AND "etablissementId" = $2 — Si trouve → parse la valeur (ENCRYPTED → decrypt, BOOLEAN → parse, etc.) → mettre en cache → retourner.

3

Fallback sur le global

WHERE cle = $1 AND "etablissementId" IS NULL — Si trouve → parse → mettre en cache → retourner.

4

Retourner null

Si aucune valeur trouvee → retourner null. Le service appelant utilise son propre fallback.

// Extrait simplifie de configuration.service.ts
async getParametre<T>(cle: string, etablissementId?: string): Promise<T | null> {
    // 1. Cache check
    const cacheKey = etablissementId ? `${cle}:${etablissementId}` : cle;
    const cached = this.cache.get(cacheKey);
    if (cached && Date.now() - cached.timestamp < this.CACHE_TTL) {
        return cached.value;
    }

    // 2. Override etablissement
    if (etablissementId) {
        const override = await this.repo.findOne({
            where: { cle, etablissementId }
        });
        if (override) {
            const value = this.parseParametreValue(override);
            this.cache.set(cacheKey, { value, timestamp: Date.now() });
            return value;
        }
    }

    // 3. Fallback global
    const global = await this.repo.findOne({
        where: { cle, etablissementId: IsNull() }
    });
    if (global) {
        const value = this.parseParametreValue(global);
        this.cache.set(cacheKey, { value, timestamp: Date.now() });
        return value;
    }

    // 4. Introuvable
    return null;
}

🚨 Niveau groupe IGNORE en runtime

Le getParametre() runtime ne consulte jamais le niveau groupeEtablissementId. Si un parametre est defini uniquement au niveau groupe (sans override etablissement ni global), le runtime retournera null au lieu de la valeur groupe. Ce comportement est une incoherence avec la cascade 4 niveaux.

💲 Tranches de facturation

TrancheConfigService resout la grille tarifaire applicable a un etablissement. Cascade : TrancheSupplement (etab) → TrancheGroupe (groupe) → TrancheEleves (plan) → vide.

Le calcul final inclut : montant base du plan + montant tranches (par palier d'effectif) + TVA OHADA 19.25%. Le mode de facturation (auto ou declaratif) est defini au niveau du plan.

💡 Comportement RLS sur parametres_systeme

La policy RLS est : "etablissementId"::text = current_setting('app.current_tenant'). Les lignes avec etablissementId = NULL (globales) sont visibles par tous les tenants car la comparaison NULL = UUID retourne NULL (falsy), mais la policy est en mode PERMISSIVE avec une seconde policy pour les lignes globales. Le SUPER_ADMIN bypass via l'UUID sentinel 00000000-0000-0000-0000-000000000000.

GLOBAL_ENTITIES — Exclusion du subscriber TypeORM

L'entite ParametreSysteme fait partie du set GLOBAL_ENTITIES dans le tenant-isolation.subscriber.ts. Cela signifie que TypeORM n'injecte pas automatiquement le etablissementId lors de l'insertion — le service doit le faire explicitement. C'est essentiel pour permettre la creation de lignes globales (etablissementId = NULL).

✅ Point fort : Redis Pub/Sub cross-instance

Depuis la v7.1 (R2), l'invalidation du cache utilise Redis Pub/Sub pour synchroniser les instances multiples du backend. Quand un parametre est modifie, un message est publie sur le canal config:cache:invalidate. Toutes les instances abonnees recoivent le message et invalident leur cache local. En mode single-instance (sans Redis), le systeme fonctionne normalement (echec silencieux du pub/sub).

💡 9. Reponse : global = false, etablissement = true

La valeur etablissement (true) l'emporte

Lorsque le parametre global vaut false et que l'etablissement a un override a true, c'est la valeur etablissement (true) qui sera utilisee.

La cascade de resolution est descendante en priorite :

  1. Etablissement (priorite maximale) — override specifique
  2. Groupe — override groupe (runtime ignore ce niveau)
  3. Global — valeur par defaut plateforme
  4. Systeme — valeurDefaut codee (fallback ultime)

Des qu'une valeur est trouvee a un niveau, la recherche s'arrete. Le runtime getParametre() cherche d'abord l'override etablissement ; s'il le trouve, il le retourne immediatement sans consulter le global.

Exemple concret

Scenario : Module notes.actif

NiveauValeurResultat
Etablissement CM1 true ✔ UTILISEE
Global (plateforme) false ✖ Ignoree (override trouve)

Resultat : le module Notes est actif pour l'etablissement CM1, meme si la plateforme l'a desactive globalement. C'est le principe de l'override : un etablissement peut activer des modules que la plateforme a desactives par defaut (et inversement).

⚠️ Cas particulier : isModuleActive()

La methode isModuleActive() a une logique legerement differente : elle consulte le parametre tenant, puis le parametre global, puis le ModuleCatalogue.actifParDefaut. Un module CRITIQUE (ex: auth) ne peut jamais etre desactive, meme avec un override explicite — le service bloque la desactivation via la categorie CRITIQUE du catalogue.

🔎 10. Incoherences Detectees

L'audit approfondi du systeme a revele plusieurs incoherences et asymetries dans l'architecture de configuration.

IC-1 : Niveau groupe ignore en runtime

Probleme : Le getParametre() runtime ne consulte que 2 niveaux (etablissement → global). Le niveau groupeEtablissementId (migration 167) est ignore, bien que la colonne existe dans la table.

Impact : Si un parametre est defini uniquement au niveau groupe (sans global), les services backend retourneront null au lieu de la valeur groupe. Seule l'interface plateforme (ParametresCascadeService) voit la valeur groupe.

Severite : HAUTE — Les parametres de groupe ne sont pas appliques en runtime.

IC-2 : TTL de cache heterogenes

Probleme : Les 4 cascades billing ont des TTL de cache differents (60s, 5min, 5min) sans coordination. Une modification de parametre peut mettre jusqu'a 5 minutes pour etre prise en compte par les feature flags, alors que les parametres generaux sont rafraichis en 60s.

Severite : MOYENNE — Incoherence de comportement entre modules, pas de bug fonctionnel.

IC-3 : Double cache memoire (helpers + service)

Probleme : Les config.helper.ts ont leur propre quick-cache (Map statique, 60s) en plus du cache du ConfigurationService. Cela cree un double cache avec des invalidations potentiellement desynchronisees.

Severite : MOYENNE — Risque de stale cache leger entre les deux niveaux.

IC-4 : Pas de validation de coherence inter-cascades

Probleme : Les 4 cascades (parametres, modules, feature flags, tranches) sont independantes. Il est possible d'avoir un module actif dans la resolution modules mais desactive via un parametre {module}.actif, ou un feature flag actif alors que le module correspondant est inactive.

Severite : BASSE — Pas de bug direct, mais risque de configuration incoherente.

🚀 11. Recommandations d'Amelioration

P0 — Critique

Unifier la cascade runtime avec la cascade plateforme

Ajouter le niveau groupe dans getParametre(). Apres la recherche de l'override etablissement, avant le fallback global, consulter WHERE cle = $1 AND "groupeEtablissementId" = $2 (necessite de resolver le groupe de l'etablissement courant).

P0 — Critique

Supprimer le double cache des helpers

Les config.helper.ts devraient deleguer directement au ConfigurationService sans quick-cache local. Le cache du service (60s + pub/sub) est suffisant. Cela elimine le risque de desynchronisation.

P1 — Important

Harmoniser les TTL de cache

Standardiser tous les caches de configuration a 60s avec invalidation pub/sub. Les 5 minutes des feature flags et tranches peuvent creer des incoherences temporaires apres modification.

P1 — Important

Validation inter-cascades

Ajouter une verification de coherence : si un module est desactive via {module}.actif = false, ses feature flags devraient automatiquement retourner false. Creer un ConfigConsistencyChecker.

P1 — Important

Cache Redis pour les parametres

Actuellement, le cache du ConfigurationService est uniquement in-memory. Ajouter un cache Redis (avec TTL 60s) reduirait les requetes DB en cas de cache miss et synchroniserait les instances automatiquement.

P2 — Amelioration

Batch loading des parametres

Ajouter une methode getParametresBatch(cles[], etablissementId) qui charge tous les parametres demandes en une seule requete SQL. Utile pour les services qui consultent 10-20 parametres au demarrage.

P2 — Amelioration

Schema de validation Zod pour les valeurs

Associer un schema Zod a chaque parametre (ou categorie) pour valider les valeurs a l'ecriture. Exemple : notes.validation_levels doit etre un JSON avec des niveaux numerotes.

P2 — Amelioration

Dashboard de configuration temps reel

Creer une vue plateforme montrant tous les parametres avec leur valeur effective par etablissement, les incoherences detectees, et un editeur inline. S'appuyer sur le ParametresCascadeService existant.

✅ Conclusion

Le systeme de configuration eLISAschool est bien architecture avec une source unique de verite (ParametreSysteme), une isolation multi-tenant robuste (RLS + sentinelle SUPER_ADMIN), et un mecanisme de cache performant (memoire + Redis pub/sub).

La principale incoherence est l'asymetrie entre la cascade runtime (2 niveaux) et la cascade plateforme (4 niveaux) — le niveau groupe n'est pas consulte en runtime. Cette limitation est corrigible en ajoutant une etape intermediaire dans getParametre().

La reponse a la question fondamentale est : quand global = false et etablissement = true, la valeur etablissement (true) l'emporte, car la cascade priorise les overrides specifiques sur les valeurs generales.
