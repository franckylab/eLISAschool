✅ Points forts — Le modèle est globalement bien conçu
  • AnneeScolaire → Periode : relation parent/enfant correctement modélisée (FK + OneToMany)
  • NiveauPeriode v5.0 : flexibilité totale (config par établissement, usages sémantiques)

  • TemplatesPeriode : génération automatique depuis structures JSON récursives
  • Anti-chevauchement : détection conflits dates par niveau + entre frères
  • Clôture cascade : verrouillage périodes enfants + impact notes/bulletins
❌ Problèmes critiques identifiés
  • C1 — Double indicateur actif : enCours (boolean) + statut (enum) sur AnneeScolaire → risque d'incohérence
  • C2 — anneeScolaireId nullable sur Note et Bulletin (nullable=true) alors que toujours dérivé de Periode
  • C3 — anneeScolaireId redondant sur 15+ entités — toujours dérivable via periodeId → classeAnnee.anneeScolaireId
  • C4 — Pas de contrainte d'intégrité entre periode.etablissementId et anneeScolaire.etablissementId
  • C5 — Module periodes surdimensionné (5 entités, 2000+ lignes) vs annees-scolaires minimaliste (1 entité, 260 lignes)
  • C6 — Import dynamique circulaire : periodes.service importe annees-scolaires.service et vice-versa
💡 Verdict — L'utilisateur a raison sur le principe

AnneeScolaire EST la racine et Periode EST lié à chaque année. Le modèle actuel respecte déjà cette logique. MAIS la convention d'usage est inconsistante : certains modules stockent anneeScolaireId en double (redondance), d'autres non. La correction est un alignement conventionnel, pas une refonte architecturale.

⚠ C1 — Redondance enCours + statut
enCours = true devrait être équivalent à statut = EN_COURS. Mais le code contient des cas où enCours = true ET statut = OUVERTE (lignes 43, 122 du service). Cette dualité crée des bugs possibles :
  • findActive() cherche enCours: true — ignore le statut
  • cloturer() vérifie enCours ET statut — logique contradictoire
  • activer() met à jour les deux — mais update() ne synchronise pas toujours

⚠ C4 — Cohérence multi-tenant non contrainte
Periode.etablissementId DOIT correspondre à AnneeScolaire.etablissementId (via anneeScolaireId). Aucune contrainte DB ne garantit cela — seule la logique du service create() vérifie via anneesScolairesService.findOne(dto.anneeScolaireId, etablissementId).

📋 NiveauPeriode + UsageNiveau — Configuration (87 + 73 lignes)

✅ Excellent design v5.0 — Ces deux entités sont le meilleur élément du modèle.
  • NiveauPeriode : niveaux configurables (0=base, 1, 2, 3+) avec label personnalisé et usage sémantique
  • UsageNiveau : codes d'usage (NOTES, BULLETIN, COMPOSITION, ANNEE, AUTRE) — système + personnalisés
  • Unique par établissement : chaque école définit sa propre structure de périodicité
  • Supporte tous les systèmes : 3 trim × 2 évaluations (Cameroun), 2 sem × 3 seq, 4 terms (Afrique du Sud), 6 séquences directes

💡 Convention actuelle — 3 patterns coexistent
  1. Pattern A (propre) : periodeId uniquement, anneeScolaireId dérivé via jointure → Notes, Bulletins

06 — Incohérences identifiées (C1 → C6)

C1 — Double indicateur enCours + statut sur AnneeScolaire
CasenCoursstatutCohérent ?
Année crééefalseOUVERTE✓
Année activéetrueEN_COURS✓
Année en attente clôturefalseEN_ATTENTE_CLOTURE✓
Année clôturéefalseCLOTUREE✓
Bug update() — ligne 122trueOUVERTE✗ INCOHÉRENT

Résolution : Supprimer enCours (boolean). Utiliser uniquement statut === EN_COURS. Ajouter un getter de compatibilité.

C2 — anneeScolaireId nullable sur Note et Bulletin

Les entités Note et Bulletin ont anneeScolaireId?: string (nullable). Or, cette valeur est toujours renseignée dans le service via periode.anneeScolaireId. La nullable est un artefact historique.

Résolution : Rendre anneeScolaireId NOT NULL sur Note et Bulletin. Ou le supprimer (C3).

C3 — anneeScolaireId dénormalisé sur 10+ entités

Dans les modules suivi-eleves, suivi-personnel, scoring : anneeScolaireId est stocké en double alors qu'il est dérivable via periodeId → periode.anneeScolaireId.

💡 Trade-off performance vs normalisation
  • Arguments POUR la dénormalisation : requêtes plus rapides (pas de jointure), filtrage direct par année, index composites
  • Arguments CONTRE : risque d'incohérence, maintenance accrue, migration coûteuse
  • Recommandation : CONSERVER la dénormalisation pour les entités à fort volume de requêtes (Notes, Bulletins, Suivi). C'est un pattern CQRS-lite acceptable.
C4 — Pas de contrainte d'intégrité cross-tenant

Periode.etablissementId pourrait différer de AnneeScolaire.etablissementId si un appel API malveillant passe un anneeScolaireId d'un autre établissement. Seule la logique service (pas la DB) protège.

Résolution : Ajouter une contrainte CHECK ou un trigger PostgreSQL vérifiant la cohérence.

C5 — Module periodes surdimensionné vs annees-scolaires minimaliste

Ce n'est pas un problème en soi — c'est cohérent avec la responsabilité de chaque module. Mais le déséquilibre suggère que AnneeScolaire pourrait être absorbé dans le module Periodes (ou inversement).

3 options :

OptionDescriptionAvantageInconvénient
A — FusionMerge annees-scolaires dans periodes → module "calendrier-scolaire"Plus de circularitéModule très large, migration risquée

✅ Recommandation : Option C (statut quo) — Les 2 modules ont des responsabilités distinctes et des cycles de vie différents. Résoudre les imports dynamiques (C6) suffit.

10 — Plan de migration — Direct et sans intermédiaire

⚠ Approche demandée : « migration directe et brutale sans intermédiaire »

Les corrections F1-F7 doivent être appliquées en une seule migration pour éviter les états transitoires incohérents.

📊 Séquence de migration (ordre critique)

📝 Structure de la migration SQL

Fichier cible : backend/database/migrations/220-coherence-annee-periode.sql
-- ═══ MIGRATION 220 — Cohérence AnneeScolaire / Periode ═══
-- Directe et sans intermédiaire — 7 étapes en 1 fichier

-- ÉTAPE 1 : Backfill anneeScolaireId NULL → valeur dérivée
UPDATE "notes" SET "anneeScolaireId" = p."anneeScolaireId"
  FROM "periodes" p WHERE "notes"."periodeId" = p.id
  AND "notes"."anneeScolaireId" IS NULL;

UPDATE "bulletins" SET "anneeScolaireId" = p."anneeScolaireId"
  FROM "periodes" p WHERE "bulletins"."periodeId" = p.id
  AND "bulletins"."anneeScolaireId" IS NULL;

-- ÉTAPE 2 : Suppression enCours + code
ALTER TABLE "annees_scolaires" DROP COLUMN IF EXISTS "enCours";
ALTER TABLE "annees_scolaires" DROP COLUMN IF EXISTS "code";

-- ÉTAPE 3 : NOT NULL
ALTER TABLE "notes" ALTER COLUMN "anneeScolaireId" SET NOT NULL;
ALTER TABLE "bulletins" ALTER COLUMN "anneeScolaireId" SET NOT NULL;

-- ÉTAPE 4 : CHECK contrainte cross-tenant
-- (via trigger car CHECK ne peut pas faire de sous-requête)
CREATE OR REPLACE FUNCTION fn_check_periode_etab()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW."etablissementId" != (
    SELECT "etablissementId" FROM "annees_scolaires"
    WHERE id = NEW."anneeScolaireId"
  ) THEN
    RAISE EXCEPTION 'Periode etablissement mismatch';
  END IF;
  RETURN NEW;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_periode_etab_check
  BEFORE INSERT OR UPDATE ON "periodes"
  FOR EACH ROW EXECUTE FUNCTION fn_check_periode_etab();

-- ÉTAPE 5 : Index composites
CREATE INDEX IF NOT EXISTS idx_notes_etab_periode
  ON "notes" ("etablissementId", "periodeId");
CREATE INDEX IF NOT EXISTS idx_bulletins_etab_periode
  ON "bulletins" ("etablissementId", "periodeId");

-- ÉTAPE 6 : Seeds niveaux + usages (idempotent)
-- (voir section 11)

-- ÉTAPE 7 : Vérification
DO $$ BEGIN
  ASSERT (SELECT count(*) FROM "notes" WHERE "anneeScolaireId" IS NULL) = 0;
  ASSERT (SELECT count(*) FROM "bulletins" WHERE "anneeScolaireId" IS NULL) = 0;
  RAISE NOTICE 'Migration 220 OK — cohérence vérifiée';
END $$;
