🔴
CRITIQUE — Discipline frontend déconnectée du backend
Le module frontend features/discipline/ appelle des endpoints /api/discipline/* qui n'existent pas. Le backend expose /api/suivi-eleves/* avec 4 entités (Incident, Observation, Sanction, Félicitation) et 18 types de sanctions. Le frontend n'en connaît que 6. La page DisciplinePage est du code mort — aucun routeur ne l'importe.
🟡
ATTENTION — Redondance AnneeScolaire.enCours
Le boolean enCours sur AnneeScolaire duplique l'information déjà portée par statut === EN_COURS. Risque d'incohérence si les deux sont modifiés indépendamment. De même, anneeScolaireId sur Note et Bulletin est une dénormalisation qui peut diverger du chemin Periode → AnneeScolaire.
🟢
VALIDÉ — TypeEvaluation couvre tous les types d'évaluation
L'enum TypeEvaluation (DEVOIR, INTERROGATION, EXAMEN, PROJET, PARTICIPATION, AUTRE) sur l'entité Note gère nativement tous les types d'évaluation. Aucun module séparé n'est nécessaire pour devoirs, interrogations ou concours. Le module frontend examens est un système distinct de planification d'examens (calendrier, convocations).
🔵
REFACTORING — 5 fusions de modules recommandées
Sur les 61 modules, 5 fusions sont identifiées : rbac→auth (0 entités propres), platform-*→platform-admin (5 modules minces), paiement→finances (pattern adapter), types-enum→configuration (1 entité), suivi-eleves+suivi-personnel→shared (abstraction commune). Cela réduirait le nombre de modules de ~12%.

RECOMMANDATION — Pas de modules séparés pour devoirs/interrogations/concours
L'enum TypeEvaluation suffit. Créer des modules séparés ajouterait de la complexité sans bénéfice. Le module examens (frontend) gère la planification logistique des examens (calendrier, salles, convocations) — c'est un complément, pas un doublon.

🔵
ARCHITECTURE — Séparation claire AnneeScolaire / Periode
AnneeScolaire = cadre temporel annuel (septembre → août). Contient les périodes.
Periode = subdivision configurable (trimestre, semestre, mois). Porte les notes et bulletins.
NiveauPeriode = catalogue des niveaux configurables par établissement (pas une instance).
PeriodeComposition = sous-période d'évaluation (composition 1, 2...) avec poids relatif.
Pas de fusion nécessaire — la hiérarchie est saine.

8.3 — Autonomie des modules

Chaque module est activable/désactivable indépendamment via EntitlementService. Les modules critiques (auth, utilisateurs, configuration, notifications) ne peuvent pas être désactivés. Les dépendances inter-modules sont gérées via le champ dependencies dans modules_catalogue.

🟢
VALIDÉ — Autonomie module respectée
Aucun module non-critique n'est hardcodé comme dépendance d'un autre. La cascade EntitlementService gère dynamiquement les activations. Un établissement peut désactiver CMS, Cantine, Transport, etc. sans casser le système.
