1. Résumé exécutif

Ce rapport présente l'analyse approfondie de 7 modules existants liés aux élèves dans eLISAschool et propose une refactorisation architecturale complète pour créer un Espace Enseignant cohérent, modulaire et autonome.

Problèmes majeurs identifiés

Double système de points (Scoring vs Gamification) Deux mécanismes parallèles attribuent des points aux élèves : ScoreEleve.score (decimal, 5 indicateurs) et PointsUtilisateur.pointsTotal (int, cumulatif). Deux historiques, deux classements, pas de cohérence.
Multi-tenant incomplet ScoreEleve, RegleScoring, HistoriqueScore, PointsUtilisateur, Badge — aucune de ces entités n'a de etablissementId. Fuite de données entre établissements.
Types figés (enums codés en dur) Tous les types (incidents, sanctions, félicitations, absences) sont des enums TypeScript. Impossible pour un établissement d'ajouter un type personnalisé sans modifier le code.
Absences/Retards — Pas de module backend Le frontend a des types d'absences (absences.types.ts) mais le backend n'a pas de module dédié. Les absences sont gérées dans IncidentEleve (type ABSENCE_NON_JUSTIFIEE, RETARD), sans lien avec les cours (HeureCours).

Solution proposée — 4 modules autonomes

Module Présence

Appel par cours, QR code, statistiques assiduité, motifs configurables. Pivot: HeureCours.

NOUVEAU

Module Discipline

Incidents cours, sanctions, observations, félicitations. Étend suivi-eleves avec contexte cours.

REFACTORISÉ

Module Journal de Classe

Cahier de texte numérique, progressions, devoirs, ressources. Pivot: HeureCours.

NOUVEAU

Module Évaluation Élève

Fusion Scoring + Gamification. Un seul système de points, badges, classement, règles.

FUSION

4.2 Meilleures pratiques identifiées

BP-1 : Nomenclatures configurables

Les meilleurs SMS permettent aux établissements de définir leurs propres types d'incidents, sanctions, motifs d'absence. Pattern : table de nomenclature avec CRUD + estSysteme pour les types par défaut.

Implémentation eLISAschool : Utiliser le pattern existant TypeContratPersonnalise — table de nomenclature scopée par établissement.

BP-2 : Event-Driven Integration

Quand un module est activé/désactivé, les autres modules s'adaptent via des événements. Pas d'appels directs couplés.

Implémentation : EventEmitter existant dans ConfigurationService. Chaque module émet des événements (presence.enregistre, incident.cree, seance.creee).

BP-3 : Graceful Degradation

Si un module est désactivé, les modules en aval ignorent les données manquantes. Pas d'erreur, pas de blocage.

Implémentation : Feature flags + try/catch non-bloquant (pattern déjà utilisé dans les notifications).

BP-4 : Positive Behavior First

Les recherches montrent que les systèmes de renforcement positif (félicitations, points) sont plus efficaces que les sanctions seules. Le système doit équilibrer les deux.

Implémentation : Module Évaluation Élève unifié avec indicateurs positifs ET négatifs.

5. Architecture cible — Refactorisation proposée

5.1 Diagramme d'architecture refactorisée

5.2 Principes de refactorisation

P1 : Autonomie module

Chaque module peut être activé/désactivé via modules_catalogue. Les dépendances inter-modules passent par événements (EventEmitter) + feature flags. Si un module est désactivé, les modules aval ignorent gracieusement.

P2 : Multi-tenant strict

TOUTE entité doit avoir etablissementId. RLS PostgreSQL activé sur toutes les nouvelles tables. Les nomenclatures sont scopées par établissement (avec types système partagés).

P3 : Types configurables

Les enums figés sont remplacés par des tables de nomenclature avec CRUD complet. Pattern existant : TypeContratPersonnalise. Les types système sont pré-seedés (estSysteme = true), non supprimables mais désactivables.

P4 : Pivot HeureCours

Les modules Présence, Discipline et Journal sont ancrés sur HeureCours (instance datée d'un cours). C'est le point d'entrée enseignant : "Quel cours ? → Je fais l'appel / Je note les incidents / Je remplis le journal".

6. Types configurables — Nomenclatures CRUD

6.1 Pattern — Table de nomenclature unifiée

Le pattern existant TypeContratPersonnalise (module personnel) sert de modèle. Chaque type configurable devient une table de nomenclature scopée par établissement, avec des types système pré-seedés.

// Service abstrait réutilisable pour toutes les nomenclatures export abstract class NomenclatureService<T> { protected repo: Repository<T>; async findAll(etablissementId: string, filters?: any): Promise<T[]> { return this.repo.find({ where: { etablissementId, ...filters }, order: { ordre: 'ASC' }, }); } async create(dto: any, etablissementId: string): Promise<T> { // Vérifier unicité du code const existing = await this.repo.findOne({ where: { code: dto.code, etablissementId } }); if (existing) throw new AppError('Code déjà utilisé', 409); return this.repo.save({ ...dto, etablissementId }); } async delete(id: string): Promise<void> { const item = await this.repo.findOne({ where: { id } }); if (!item) throw new AppError('Non trouvé', 404); if (item.estSysteme) throw new AppError('Type système non supprimable', 403); // Vérifier pas d'utilisation avant suppression await this.verifierPasUtilise(id); await this.repo.softRemove(item); } }

8. Module Discipline — Conception détaillée

8.1 Stratégie de refactorisation

Approche : Extension de suivi-eleves avec contexte cours Le module Discipline ne remplace pas suivi-eleves — il l'enrichit. Les entités existantes (IncidentEleve, SanctionEleve, ObservationEleve, FelicitationEleve) sont conservées mais déplacées dans le module discipline/ et enrichies avec un lien optionnel vers HeureCours.

14. Conclusion & recommandations

Recommandations prioritaires

  1. Phase 0 IMMÉDIATE — Corriger le multi-tenant sur scoring/gamification. C'est une faille de sécurité critique. 8 entités sans etablissementId = fuite de données entre établissements.
  2. Phase 1 en priorité — Le module Présence est le plus demandé par les enseignants et le plus simple à implémenter (pivot HeureCours déjà existant).
  3. Nomenclatures en premier — Avant de créer les modules, créer le système de nomenclatures configurables (NomenclatureService abstrait). Il sera réutilisé par tous les modules.
  4. Éviter la disruption — Le module suivi-eleves/ reste fonctionnel pendant la transition. La migration vers discipline/ se fait par dépréciation progressive, pas par remplacement brutal.
  5. Tests de non-régression — Chaque phase doit inclure des tests vérifiant que les modules existants (notes, bulletins, emploi du temps) ne sont pas impactés.
