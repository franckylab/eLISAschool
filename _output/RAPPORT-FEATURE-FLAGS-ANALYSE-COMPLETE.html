1. Résumé Exécutif

eLISAschool est une plateforme SaaS multi-tenant de gestion scolaire qui dispose d'un système de gestion des fonctionnalités sophistiqué et mature, articulé autour de trois piliers :

26
Modules au catalogue

8
Niveaux de cascade
60+
Modules backend implémentés
✅ Points Forts Identifiés
  • Source unique de vérité : EntitlementService centralise tout le gating (migration 200)
  • Cascade multi-niveaux : 8 niveaux de résolution (base → essai → catalogue → abonnement → plan → groupe → supplément → défaut)
  • Dégradation gracieuse : 3 phases (lecture seule J0-J15, verrouillé J15-J30, archivé J30+)
  • Période d'essai : 14 jours avec tous modules accessibles
  • Cache performant : Redis TTL 60s + in-memory + Pub/Sub cross-instance
  • Multi-tenant strict : Isolation RLS + discrimination par établissement

3. Feature Flags — Définition, Rôle et Implémentation

3.1 Qu'est-ce qu'un Feature Flag ?

Un feature flag (ou « bascule de fonctionnalité ») est un mécanisme permettant d'activer ou désactiver une fonctionnalité spécifique sans déployer de nouveau code. Dans eLISAschool, les feature flags servent à :

1
Contrôler l'accès à des capacités transverses — export PDF, API publique, SSO, webhooks, etc.
2
Différencier les plans — certaines features ne sont disponibles qu'à partir du plan Pro/Enterprise
3
Permettre des overrides par établissement — activer une feature spécifique pour un client premium
4
Faciliter les rollouts progressifs — activer une feature pour un sous-ensemble d'établissements

3.4 Implémentation Technique

// FeatureFlagService — Méthode isEnabled()
async isEnabled(flagName: string, etablissementId: string): Promise<boolean> {
    // 1. Cache check (TTL 60s)
    const cached = this.cache.get(`${etablissementId}:${flagName}`);
    if (cached && cached.expiresAt > Date.now()) return cached.value;

    // 2. Override tenant (priorité maximale)
    const override = await this.flagRepo.findOne({
        where: { etablissementId, flagName }
    });
    if (override) return override.enabled;

    // 3. Flags du plan d'abonnement
    const abonnement = await this.abonnementRepo.findOne({
        where: { etablissementId, statut: 'ACTIF' },
        relations: ['plan']
    });
    if (abonnement?.plan?.featureFlags?.[flagName] !== undefined) {
        return abonnement.plan.featureFlags[flagName];
    }

    // 4. Modules inclus → auto-active les flags associés
    // Ex: 'transport' dans modulesInclus → module_transport = true
    
    // Défaut: désactivé
    return false;
}

5. EntitlementService — Source Unique de Vérité

L'EntitlementService (855 lignes) est le composant central qui remplace les 3 anciens registres divergents depuis la migration 200. Il fournit une réponse déterministe à la question : « Cet établissement a-t-il accès à ce module ? »

5.1 Interface de Résultat

interface EntitlementResult {
    accessible: boolean;          // Le module est-il accessible ?
    visible: boolean;             // Visible dans le catalogue ?
    raison: EntitlementRaison;    // Pourquoi ? (OK, BASE, ABONNEMENT_INACTIF...)
    message?: string;             // Message explicatif pour le frontend
    source: EntitlementSource;    // D'où vient la décision ? (base, plan, groupe...)
    planMinimalRequis?: string;   // Plan requis si applicable
    planActuel?: string;          // Plan actuel de l'établissement
    lectureSeule?: boolean;       // Mode dégradé J0-J15
}

7.2 Comment les Fonctionnalités sont Identifiées

📌 Triple Système d'Identification

Chaque fonctionnalité est identifiée par 3 mécanismes complémentaires :

  1. Code module (modules_catalogue.code) — identifiant unique du module métier (ex: transport, gamification)
  2. Feature flag (feature_flags_tenant.flagName) — capacité transverse (ex: export_pdf, sso)
  3. Permission RBAC (roles.enum.ts) — granularité fine (ex: transport:lignes:view, gamification:badges:manage)

12. Recommandations et Améliorations

🔴 Priorité Haute

R1 — Unifier Feature Flags et Module Gating

Constat : Actuellement, les feature flags et les modules sont gérés par 2 services distincts (FeatureFlagService et EntitlementService). Cette séparation crée une duplication logique (les modules inclus activent automatiquement les flags module_*).

Recommandation : Fusionner la résolution dans EntitlementService qui devient l'unique point d'entrée. Les feature flags deviennent un type particulier de capability dans le catalogue.

// Proposition : EntitlementService.checkCapability()
async checkCapability(
    etablissementId: string, 
    capability: string  // peut être un module OU un feature flag
): Promise<EntitlementResult>
🔴 Priorité Haute

R2 — Catalogue de Feature Flags Dynamique

Constat : La liste FEATURE_FLAGS_LIST est hardcodée dans le frontend (8 flags). Ajouter un nouveau flag nécessite une modification code + déploiement.

Recommandation : Créer une entité FeatureFlagDefinition en base avec metadata (label, description, catégorie, defaultValue). Le frontend charge la liste dynamiquement via API.

-- Nouvelle table
CREATE TABLE feature_flag_definitions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    key VARCHAR(100) UNIQUE NOT NULL,
    label VARCHAR(150) NOT NULL,
    description TEXT,
    categorie VARCHAR(50), -- 'billing', 'integration', 'security', 'ux'
    default_value BOOLEAN DEFAULT false,
    plan_minimal VARCHAR(50),
    est_systeme BOOLEAN DEFAULT false
);
🟡 Priorité Moyenne

R3 — Feature Flags Scopés par Utilisateur

Constat : Les feature flags sont uniquement scopés par établissement. Pas de possibilité d'activer une feature pour un rôle spécifique (ex: export_pdf seulement pour les ADMIN).

Recommandation : Ajouter une dimension roleId ou userId dans feature_flags_tenant pour permettre des overrides granulaires.

🟡 Priorité Moyenne

R4 — Dashboard Feature Flags Unifié

Constat : Pas de vue centralisée montrant tous les feature flags avec leur état par établissement dans le Control Plane.

Recommandation : Créer une page /platform/feature-flags avec :

  • Matrice établissements × flags (toggle rapide)
  • Filtres par plan, statut, groupe
  • Audit trail des modifications
  • Import/export en masse (CSV)
🟡 Priorité Moyenne

R5 — Versioning et Rollback des Feature Flags

Constat : Pas d'historique des changements de feature flags. Impossible de savoir qui a activé/désactivé quoi et quand.

Recommandation : Créer une table feature_flags_history avec audit complet et possibilité de rollback.

🟢 Priorité Basse

R6 — Feature Flags Conditionnels (Rules Engine)

Constat : Les flags sont binaires (true/false). Pas de conditions contextuelles (ex: export_pdf activé seulement si effectif > 500).

Recommandation : Implémenter un rules engine léger pour des conditions composées :

// Proposition : Feature flag avec règles
{
    "key": "export_pdf",
    "rules": [
        { "condition": "plan.rank >= 2", "value": true },
        { "condition": "etablissement.effectif > 500", "value": true },
        { "condition": "default", "value": false }
    ]
}
🟢 Priorité Basse

R7 — A/B Testing et Progressive Rollout

Constat : Pas de mécanisme de rollout progressif (activer pour 10% des établissements puis augmenter).

Recommandation : Ajouter un champ rolloutPercentage dans FeatureFlagDefinition. Le service calcule de manière déterministe si un établissement est dans le pourcentage.

🟢 Amélioration Continue

R8 — Synchroniser le Frontend MODULES_CATALOG avec le Backend

Constat : Le frontend a MODULES_CATALOG (19 modules) hardcodé, tandis que le backend en a 26 dans le seed. Désynchronisation inévitable.

Recommandation : Charger le catalogue dynamiquement via GET /api/billing/modules/catalogue au lieu de hardcoder.
