4. Les 5 Conflits Identifiés & Résolutions

⚠ CONFLIT C1 — ProgressionPedagogique vs ProgressionProgramme (CRITIQUE)

Problème : Le plan propose une nouvelle entité ProgressionPedagogique (liée à AffectationMatiere) dans le module Journal. Or, une entité identique existe déjà : ProgressionProgramme dans le module personnel/.

AspectProgressionProgramme (EXISTANT — personnel)ProgressionPedagogique (PLAN — journal)
Modulepersonnel/journal/ (planifié)
FKenseignantId, matiereId, classeId, periodeId, programmeChapitreIdaffectationMatiereId, periodeId
ContenupourcentageRealise, chapitreCourant, modeCalcul, remarqueschapitre, pourcentageAvancement, statut, nbSeancesConsacrees
Lien programmeOUI → programmeChapitreId (FK directe)NON (pas de lien vers ProgrammeChapitre)
etablissementId✓ Oui✓ Oui (plan)
Soft delete✓ @DeleteDateColumnNon prévu

✅ Résolution C1 — FUSION des deux entités

NE PAS créer ProgressionPedagogique. Étendre ProgressionProgramme existant :

  • Ajouter affectationMatiereId (nullable) pour lien direct avec l'affectation
  • Ajouter statut (PLANIFIE | EN_COURS | TERMINE)
  • Ajouter nbSeancesConsacrees (int, default 0)
  • Ajouter datePrevue / dateEffective
  • Le module Journal lit et met à jour ProgressionProgramme via son service, sans créer de nouvelle table

Gain : Pas de redondance, pas de migration de données, lien ProgrammeChapitre conservé.

⚠ CONFLIT C2 — IncidentCours vs IncidentEleve (chevauchement)

Problème : Le plan crée IncidentCours (lié à HeureCours) mais IncidentEleve existant a déjà classeId, matiereId, enseignantId — soit le contexte cours.

✅ Résolution C2 — IncidentCours comme LÉGER, IncidentEleve comme LOURD

Les deux entités ont des rôles complémentaires, pas redondants :

  • IncidentCours (NOUVEAU) = incident ponctuel pendant un cours spécifique. Résolu par l'enseignant. Pas d'escalade. Table légère.
  • IncidentEleve (EXISTANT) = incident persistant au dossier de l'élève. Escalade direction. Sanctions. Workflow complet.
  • Flux : IncidentCours (MINEUR) → résolu. Si récidive ou GRAVE+ → créer IncidentEleve (escalade).

Requis : Ajouter incidentCoursId (nullable) sur IncidentEleve pour tracer l'origine cours.

⚠ CONFLIT C3 — Structure ScoreEleve (1 ligne/type → 1 ligne/élève)

Problème : Actuellement ScoreEleve stocke 1 ligne par type (ACADÉMIQUE, COMPORTEMENT, etc.) avec type: TypeIndicateur. Le plan propose 1 ligne par élève+periode avec colonnes séparées (scoreAcademique, scoreComportement...). C'est un breaking change de structure.

✅ Résolution C3 — Conserver le modèle 1 ligne/type + ajouter GLOBAL

Garder la structure existante (plus flexible) et ajouter :

  • etablissementId (CORRECTION multi-tenant)
  • Index unique sur [eleveId, periodeId, type, etablissementId]
  • Le score GLOBAL est calculé comme une 5ème ligne type=GLOBAL

⚠ CONFLIT C4 — Badge.code contrainte unique globale

Problème : Badge.code a unique: true — impossible d'avoir des badges par établissement.

✅ Résolution C4 — Unique composite [code, etablissementId]

  • Supprimer unique: true sur code
  • Ajouter etablissementId (uuid, NOT NULL)
  • Créer index unique composite [code, etablissementId]
  • Migration : badges existants → etablissement du premier créateur

⚠ CONFLIT C5 — PointsUtilisateur utilise utilisateurId au lieu de eleveId

Problème : La gamification stocke utilisateurId (pas eleveId). Or le scoring utilise eleveId. Ce sont deux clés différentes pour le même élève.

✅ Résolution C5 — Migration vers eleveId + etablissementId

  • Renommer PointsUtilisateur → PointsEleve (ou ajouter eleveId)
  • Ajouter etablissementId sur toutes les entités gamification
  • Script migration : JOIN eleves.utilisateurId → eleves.id pour remplir eleveId
  • Fusionner avec le système de points comportement du plan (PointComportement)

8.2 Correction fondamentale — Structure ScoreEleve

✅ Solution retenue — Conserver 1 ligne par type

// EXISTANT (conservé) — 1 ligne par (eleveId, periodeId, type)
@Entity('scores_eleves')
@Index(['eleveId', 'periodeId', 'type', 'etablissementId'], { unique: true })
export class ScoreEleve {
    @Column({ type: 'uuid' })
    etablissementId!: string;  // ← AJOUT (migration 224)
    
    @Column({ type: 'uuid' })
    eleveId!: string;
    
    @Column({ type: 'uuid' })
    periodeId!: string;  // ← RENDU OBLIGATOIRE (était nullable)
    
    @Column({ type: 'enum', enum: TypeIndicateur })
    type!: TypeIndicateur;  // ACADEMIQUE, COMPORTEMENT, ASSIDUITE, PARTICIPATION, GLOBAL
    
    @Column({ type: 'decimal', precision: 5, scale: 2, default: 0 })
    score!: number;
    
    @Column({ type: 'int', nullable: true })
    rang?: number;
}
// Le score GLOBAL est calculé comme une 5ème ligne type=GLOBAL

12. Recommandations Finales

🔴 Avant implémentation

  1. Résoudre les 3 conflits CRITIQUES (C1, C2, C3)
  2. Mettre à jour le plan avec les 12 corrections
  3. Ajuster effort : 310h → 354h
  4. Valider architecture avec les parties prenantes

🟡 Pendant implémentation

  1. Phase 1 (Nomenclatures) : inclure correction D1 (cohabitation enums)
  2. Phase 2 (Présence) : inclure corrections P1+P2
  3. Phase 4 (Journal) : utiliser ProgressionProgramme existant (pas de nouvelle table)
  4. Phase 5 (Évaluation) : migration 224 en 3 étapes (ajout → backfill → contraintes)

🟢 Après implémentation

  1. Tests isolation multi-tenant sur toutes les nouvelles entités
  2. Vérification graceful degradation (désactiver chaque module)
  3. Audit performance (appel 120 élèves < 2s)
  4. Documentation migration pour établissements existants
Conclusion : Le plan d'implémentation est solide dans sa conception mais nécessite 12 corrections avant implémentation, dont 3 sont critiques. Les conflits proviennent principalement d'un manque de connaissance de 3 entités existantes : ProgressionProgramme (personnel), IncidentEleve (contexte cours déjà présent), et la structure ScoreEleve (1 ligne/type). Après corrections, le plan sera prêt pour implémentation avec un effort ajusté de ~354h.
