Two sibling NestJS-style modules share a clear dependency direction: `groupes-etablissements` depends on `etablissement`, never the reverse.

- `etablissement/`: core multi-tenant root. `entities/Etablissement` (TypeORM, soft-delete via `actif`, workflow-driven `StatutEtablissement`) owns a 1:1 `EtablissementConfig`; `services/EtablissementService` exposes CRUD plus logo upload (base64 stored in `logoBase64`, resized via `redimensionnerLogo` from `@common/utils/image-processor.util`), per-establishment regional parameters with a 4-level fallback (`etablissement` → `ParametreSysteme` scope → global `ConfigurationApp` → hardcoded default), and statistics that reach into peer modules (`Classe`, `AffectationEleve`, `MembrePersonnel`) through `AppDataSource.getRepository('...')`. Creation/deactivation/reactivation optionally trigger `validationWorkflowService.createWorkflow` when `getParamBoolean('etablissement.require_validation', false)` is true.
- `groupes-etablissements/`: overlays a logical grouping layer. `GroupeEtablissement` (owner + unique `code`) links to `Etablissement` via a many-to-many `GroupeEtablissementLien` enforcing the business rule "an establishment belongs to at most one group"; `GroupeAdmin` grants admin access. `GroupesService` handles CRUD, paginated queries via `createQueryBuilder`, and invalidates the precalc cache key `precalc:groupe:${groupeId}` after mutations. `ConsolidationService` aggregates students (`Eleve`), grades (`Note`), and finances (`Paiement`, `Depense`) across all establishments in a group using parallel SQL aggregations and caches results for 4 hours under the same key. `requireGroupeAccess` Express guard checks ownership/admin membership and bypasses for users holding `super_admin:all` via `permissionResolverService.resolvePermissions`.

Both modules export barrel `index.ts` files re-exporting entities/dto/services/controllers, and expose singleton instances (`etablissementService`, `groupesService`, `consolidationService`) rather than relying on DI containers.
