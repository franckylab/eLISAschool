Three-layer layout under `backend/src/modules/auth`:
- Entities (`entities/preference-*.entity.ts`) define the persistence schema via TypeORM decorators: `PreferenceUtilisateur` (per-user, multi-tenant via nullable `etablissementId`, unique composite on `[utilisateurId, cle, etablissementId]`), `PreferenceGlobale` (establishment-scoped, unique on `[etablissementId, cle]`), and `PreferenceRole` (role-scoped, linked to `RoleEntity`). All three share the same key/value/type/categorie shape and reuse the `CategoriePreference` enum from `preference-utilisateur.entity.ts`.
- Services (`services/preference-*.service.ts`) are plain classes instantiated as module-level singletons (`preferenceUtilisateurService`, `preferenceGlobaleService`) that own a TypeORM `Repository` obtained through `AppDataSource.getRepository(...)`. They encapsulate business rules — default seeding (`DEFAULT_PREFERENCES`, `DEFAULT_PREFERENCES_GLOBALES`), type coercion (`parseValue`/`serializeValue`/`inferType`), reset helpers, and the effective-value resolution chain (user override → global config → system default). The user service also calls `configurationService.getParametre` for cross-module fallback.
- Controllers (`controllers/preferences.controller.ts`, `controllers/preferences-globales.controller.ts`) expose Express routers mounted at `/api/preferences*`. They use `authMiddleware` plus `requirePermission('config:*')` / `utilisateurs:*` guards, validate payloads with Zod schemas, and delegate all logic to the services. The global controller lazily imports `@modules/auth/services` to break the circular dependency between the two services when computing `getValeurEffective`.

Dependency direction is strictly Controller → Service → Entity/Repository; controllers never touch TypeORM directly. Cross-cutting concerns (logging via `logger`, error wrapping via `AppError`, caching via `redisService`) come from `@common/*` aliases.
