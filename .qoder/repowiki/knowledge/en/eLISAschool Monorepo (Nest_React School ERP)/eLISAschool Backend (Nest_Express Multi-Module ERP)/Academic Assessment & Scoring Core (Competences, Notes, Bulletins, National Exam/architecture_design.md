Five sibling NestJS feature modules (`competences`, `notes`, `bulletins`, `examens-nationaux`, `scoring`) each follow an identical internal layering — `entities/` (TypeORM `@Entity` classes), `dto/` (class-validator DTOs), `services/` (stateless service class + singleton export), `controllers/` (HTTP handlers), plus a barrel `index.ts` re-exporting all four layers. Dependency direction is strictly inward: controllers depend on services; services own TypeORM repositories via `AppDataSource.getRepository(...)` and call other module services through named singletons (e.g. `notesService` → `validationWorkflowService`, `parentsService`, `notificationTemplates`, `gamificationService`). Cross-module boundaries are explicit: `bulletins` consumes `notes` (via `notesBatchLoaderService.batchLoadMoyennes` for O(1) average computation), `notes` triggers `validation-workflow`, `notifications`, `gamification`, and `audit`; `scoring` is independent and only reads configuration. Multi-tenancy is enforced by an `etablissementId` column present on every entity and propagated as a query filter in service methods. The `notes` module additionally owns a dedicated `notes-batch-loader.service.ts` that pre-computes per-student-per-subject averages to avoid N+1 queries during bulletin generation.
