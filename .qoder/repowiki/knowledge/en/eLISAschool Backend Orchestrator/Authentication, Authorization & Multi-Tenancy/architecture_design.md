- **Layered structure**: The module is organized into four sub-packages — `auth` (authentication flows, token lifecycle, audit logging), `rbac` (CRUD for roles/permissions, user-role assignment), `common` (cross-cutting concerns: error filters, interceptors, tenant middleware, Redis service, utility functions), and `config` (environment validation via Zod, database/Swagger configuration). Entry points are `backend/src/modules/auth/index.ts` and `backend/src/modules/rbac/index.ts`, which export controllers, services, entities, DTOs, guards, and middlewares.
- **Dependency direction**: Auth services depend on `@database/data-source` (TypeORM repositories), `@common/filters/error.filter` (AppError), `@common/utils/logger.util`, `@config/env.config` (JWT secrets), and the internal `permission-resolver.service`. RBAC services depend on auth entities (`Role`, `Permission`, `UtilisateurRole`) and call `permissionResolverService` to invalidate caches after role/permission mutations. Common utilities are leaf dependencies consumed by both auth and rbac layers.
- **Interface boundaries**: Authentication is exposed via Express routes in `auth.controller.ts` (login, register, refresh, logout, password management, email verification, `/me`, `/switch-etablissement`). RBAC exposes REST endpoints via `roles.controller.ts`, `permissions.controller.ts`, and `user-roles.controller.ts`. Middleware boundaries include `authMiddleware` (JWT verification attaching `req.utilisateur`), `tenantMiddleware` (multi-tenancy filtering by `etablissementId`), and permission guards (`requirePermissions`, `hasPermission`) that check JWT-embedded permissions or fall back to static role-permission maps.
- **Key architectural patterns**: Token service uses JWT access tokens (signed with HS256 via `jsonwebtoken`) and opaque refresh tokens stored in PostgreSQL with revocation support. Permission resolution combines role-based permissions (with recursive parent inheritance), user-level GRANTED/DENIED overrides, and an in-memory cache (5-min TTL) managed by `PermissionResolverService`. Security parameters (max login attempts, lockout duration, password complexity) are fetched from a centralized configuration service with a short-lived local cache (1-min TTL). Audit logging captures login attempts, password changes, access denials, and establishment switches.
