- Entry point: `controllers/dashboard.controller.ts` exposes REST endpoints under `/api/dashboard/*`, all guarded by `authMiddleware`. The controller delegates to service-layer singletons.
- Service layer (7 services in `services/`): `WidgetResolverService` resolves available widgets per user based on roles/permissions via `PermissionResolverService`; `DataAggregatorService` orchestrates data fetching through lazy-loaded cross-module service instances with timeout protection; `DashboardCacheService` provides Redis-backed caching with context-aware invalidation; `DashboardSSEService` manages server-sent event connections for real-time pushes; `DashboardDataService` centralizes dashboard-specific queries; `DashboardPrecalcService` handles precomputed aggregations; `DashboardDataLoaderService` supports batched loading.
- Declarative registry: `utils/widget-registry.ts` defines `WIDGET_REGISTRY` — an array of `WidgetDefinition` objects specifying roles, permissions, data resolvers (`'serviceName.methodName'`), cache TTLs, refresh strategies, and module affiliation. This is the single source of truth for widget metadata.
- Data layer: `entities/dashboard-layout.entity.ts` (TypeORM entity `dashboard_layouts`) persists per-user layout configurations as JSONB, scoped by `etablissementId`. DTOs in `dtos/dashboard.dto.ts` use Zod schemas for request validation.
- Dependency direction: Controller → Services → Registry + Cache + External Module Services (lazy-loaded via dynamic `require`). Cross-module coupling is deferred at runtime through string-based resolver references in the registry.
- Export boundary: `index.ts` re-exports entities, DTOs, services, controllers, and the widget registry utilities for module consumers.
