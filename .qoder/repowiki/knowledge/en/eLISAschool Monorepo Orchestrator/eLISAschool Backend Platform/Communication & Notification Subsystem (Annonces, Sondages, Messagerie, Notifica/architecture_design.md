Four sibling NestJS-style modules share a uniform barrel-export layout (`index.ts` re-exports `entities`, `dto`, `services`, `controllers`) so they can be consumed as single units from the app root.

- `annonces/`: TypeORM entities (`Annonce`, `AnnonceCiblage`) model a content announcement with multi-criteria targeting (`CiblageType`: role/user/class/level/function/establishment) and a two-axis state machine — `AnnonceStatut` (draft → active → expired/archived) plus `AnnonceValidation` (draft → pending → approved/rejected). CRUD is exposed through a single controller/service pair.
- `sondages/`: Polls are split into a core service, a PDF export helper (`sondage.pdf.ts`), and a Socket.IO adapter (`sondage.websocket.ts`) that is initialized lazily via an `initialize(io)` setter so the module stays optional when no WebSocket server is running. A `cron-jobs.ts` drives scheduled activation/expiry of polls and recurring poll creation.
- `messagerie/`: The largest sub-system; a monolithic `messagerie.service.ts` is complemented by feature-scoped services (`message-draft`, `message-forward`, `message-mention`, `message-pinned`, `message-reaction`, `message-read`, `template-message`). Realtime is handled by `messagerie-sse.service.ts`, which maintains an in-process `Map` of SSE clients, publishes events on Redis channel `messagerie:events` for multi-instance fan-out, and persists missed events in `messagerie:events:<userId>` lists for Last-Event-ID reconnection. Online presence and typing indicators are tracked via Redis keys with TTL (`messagerie:typing:...`).
- `notifications/`: Pluggable delivery layer built around `INotificationProvider` (`email`, `sms`, `push`, `in-app`) registered through `provider-registry.ts`. Providers expose `envoyer()`, `testerConfiguration()`, optional `getQuota()`, and `initialiser()`. A `notification-provider.controller.ts` exposes admin endpoints to add/configure providers at runtime. Cron jobs schedule payment reminders, daily menu pushes, and processing of queued notifications.

Dependency direction is one-way: controllers → services → TypeORM repositories; realtime layers (SSE/WebSocket) depend only on Redis and the shared logger, never on controllers. Cross-module calls go through named imports like `@modules/cantine/services` or `@database/data-source`.
