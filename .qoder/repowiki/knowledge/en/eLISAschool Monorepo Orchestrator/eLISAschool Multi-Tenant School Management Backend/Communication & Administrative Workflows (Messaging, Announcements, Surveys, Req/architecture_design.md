Each sub-module follows the same vertical slice layout — `entities/`, `dto/`, `services/`, `controllers/` plus a barrel `index.ts` re-exporting them — so they are consumed by the Nest app as independent feature packages. All entities are TypeORM `@Entity` classes using UUID primary keys, `etablissementId` for strict multi-tenancy, and `@Index` annotations on hot query columns; relationships use `ManyToOne`/`OneToMany` with explicit `@JoinColumn` names and `onDelete: 'CASCADE'`. Services are plain classes that fetch repositories via `AppDataSource.getRepository(...)` in their constructor rather than through DI, which keeps each module self-bootstrapping. Cross-cutting concerns are isolated into sibling services: `messagerie-sse.service.ts` implements an in-process SSE client map with Redis pub/sub (`messagerie:events`) for multi-instance broadcast and Last-Event-ID reconnection; `sondage.websocket.ts` is a thin Socket.IO adapter initialized lazily at runtime; `cron-jobs.ts` registers four `node-cron` schedules (activation, expiry, cleanup, recurrence) running on the `Africa/Douala` timezone. The sondage module adds a template layer (`TemplateSondage`) reused to spawn recurring or scheduled `Sondage` instances, while annonces uses a soft-delete pattern via `DeleteDateColumn` and a two-state machine (`statut` + `validation`). Requêtes models a simple typed number-based approval pipeline (`niveauxApprobation` / `niveauActuel` vs `StatutRequete.EN_COURS`).
