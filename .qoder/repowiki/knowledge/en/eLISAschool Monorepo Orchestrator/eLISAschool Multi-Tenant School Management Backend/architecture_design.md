The entry point (`src/index.ts`) bootstraps TypeORM via `AppDataSource`, runs a one-shot backfill for the `postes.fonctionId` migration regression, preloads the permission cache, seeds notification providers, then calls `createApp()` in `src/app.ts`. That function installs global Express middlewares (helmet, CORS, compression, rate-limiting with a stricter auth limiter, request logging) and mounts every business controller under `/api/<module>` using the pattern `authMiddleware → requireModuleActive('<slug>') → filterByEtablissement() → controller`. Module activation is driven by the `configuration` module's `modules_actifs` table; `requireModuleActive` short-circuits disabled features. Multi-tenancy is enforced by `tenantMiddleware` (attaches `etablissementId` from JWT) plus `filterByEtablissement()` which scopes queries to the current establishment, with an explicit `allowSuperAdminOverride` flag on `/api/etablissements`. Cross-module wiring happens only at this top level — modules never import each other directly but share: (1) `@database/data-source` for a single TypeORM connection, (2) `@common/*` utilities (logger, pagination, validation, crypto), (3) the RBAC guard stack from `@modules/auth` (guards + middlewares + `permissionResolverService`), and (4) the pluggable notification provider registry from `@modules/notifications/providers`. Cron jobs are registered centrally (`initNotificationCronJobs`, `initFinanceCronJobs`, `initGamificationCronJobs`, `initScoringPersonnelCronJobs`, `initSondageCronJobs`, `initAuthCronJobs`, `initClassesCronJobs`) and gated by `ENABLE_CRON_JOBS=true` or production. Two parallel migration trees exist — `database/migrations/*.sql` (TypeORM schema migrations) and `src/database/migrations/*.ts` (data/seed migrations) — both executed through scripts in `scripts/` and `src/database/scripts/`.
