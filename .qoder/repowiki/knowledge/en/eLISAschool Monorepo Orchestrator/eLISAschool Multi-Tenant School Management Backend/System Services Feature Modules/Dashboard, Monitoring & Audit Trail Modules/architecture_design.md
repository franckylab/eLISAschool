Each subfolder is an independent Express module mounted under `/api/dashboard`, `/api/monitoring`, `/api/audit` and follows a thin controller → service → TypeORM repository layering:
- `dashboard/`: the most feature-rich. A registry-driven widget model (`utils/widget-registry.ts`) plus `WIDGET_REGISTRY` from `@shared/config/config.registry` drives discovery; `WidgetResolverService` filters widgets by roles + permissions (via `PermissionResolverService`), merges per-user layout persisted in `DashboardLayout` entity, and caches results through `DashboardCacheService`. `DataAggregatorService` / `DashboardDataService` / `DashboardDataloaderService` / `DashboardPrecalcService` are separate data-fetching concerns, while `DashboardSseService` holds open Server-Sent-Events connections keyed by `utilisateurId`. The controller is the only HTTP boundary; all business logic lives in services.
- `monitoring/`: minimal — `MonitoringController` delegates to a single `MonitoringService` that reads OS/process metrics via Node `os`/`process`, probes DB connectivity through `AppDataSource`, and toggles maintenance mode via `getParam`/`getParamBoolean` from `@modules/configuration/utils/config.helper`. No entities of its own.
- `audit/`: read-only query/export API backed by `@modules/auth/services/audit.service` and `AuditLog` entity from `@modules/auth/entities/audit-log.entity`; `ArchivageService` provides batch archive/purge helpers using TypeORM QueryBuilder on `createdAt < cutoffDate`. The controller performs client-side filtering on fields not supported server-side (module, cibleId, estEchec, search).

Dependency direction: controllers depend only on their sibling services and shared auth middlewares (`@modules/auth/middlewares`). Dashboard additionally depends on `@modules/auth/services/permission-resolver.service` and `@database/data-source`. Monitoring and audit have no cross-module dependencies beyond shared config/db/auth primitives. There is no inter-call between the three modules at runtime.
