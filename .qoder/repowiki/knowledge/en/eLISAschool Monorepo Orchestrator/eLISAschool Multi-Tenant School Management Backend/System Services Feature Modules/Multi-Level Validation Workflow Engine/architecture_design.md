Express router (`controllers/validation-workflow.controller.ts`) exposes REST endpoints under `/api/validation-workflows` and delegates to two services: `ValidationWorkflowService` (core lifecycle — create, advance level, cancel, stats) and `ValidationRapportService` (aggregation + CSV export). The single TypeORM entity `WorkflowValidation` in `entities/workflow-validation.entity.ts` is the cross-module persistence layer; it stores a polymorphic reference via `module` + `entiteId`/`entiteType`, a JSON `configRoles` map of `{level: roleName}`, and a JSON `historique` array of per-level decisions. Role enforcement follows a two-tier check: first a dynamic permission code `validation:{module}:level{n}` resolved through `permissionResolverService`, then a fallback against the configured role for that level. Default role maps are duplicated in both the service and the middleware (`middlewares/validation.middleware.ts`), which also provides reusable Express guards `requireValidationLevel(module, niveau)` and `requireActiveWorkflow(module)`. DTOs in `dto/` are Zod schemas consumed by `validateDto(@common/utils)` at the controller boundary. Multi-tenancy is enforced by always scoping queries to `etablissementId`; configuration defaults come from the shared `getParam` config store keyed `${module}.validation_levels` / `${module}.validation_roles`. The module re-exports everything from its barrel `index.ts` so other modules import it as `@modules/validation-workflow`.
