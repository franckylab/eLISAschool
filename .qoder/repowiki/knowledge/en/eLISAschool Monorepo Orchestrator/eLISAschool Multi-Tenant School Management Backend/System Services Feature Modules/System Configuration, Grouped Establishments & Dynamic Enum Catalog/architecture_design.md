Three sibling NestJS-style modules sharing the same internal layout (controllers / dto / entities / services / guards) but with distinct responsibilities:

- `configuration/` — Central key/value configuration (`ParametreSysteme`, `ConfigurationApp`, `ConfigurationModule`) plus a versioned backup subsystem. Backup is built around an abstraction `IBackupStorage` in `services/storage/storage-provider.interface.ts` with a concrete `DatabaseStorageProvider`; `ConfigBackupService` orchestrates snapshot collection, optional differential computation, gzip compression, SHA-256 checksumming, semantic versioning, restore via a TypeORM `QueryRunner` transaction, and inter-establishment cloning with conflict resolution (`skip|overwrite|merge`). A `module-active.middleware.ts` enforces module enable/disable at request time, while `config.guard.ts` + `config-permissions.ts` gate every config endpoint through role-based permissions (SUPER_ADMIN/ADMIN bypass). `ConfigurationListener` seeds defaults and watches runtime changes.
- `groupes-etablissements/` — Models `GroupeEtablissement` and its link table to group establishments; `ConsolidationService` aggregates Eleves/Notes/Finances across all members of a groupe using parallel TypeORM queries and caches results via `dashboardCacheService`. `groupe-access.guard.ts` enforces per-groupe ownership/admin access with a `super_admin:all` bypass.
- `types-enum/` — Stores pluggable enum-like lists (`TypeEnum` with `categorie`, `code`, `libelle`, `estSysteme`, `ordre`, optional `etablissementId`) so frontend dropdowns are data-driven rather than hard-coded enums.

Dependency direction is one-way: `groupes-etablissements` depends on other domain modules (`eleves`, `notes`, `finances`, `auth`) for aggregation; `configuration` depends only on `@modules/etablissement/entities` and shared `@common` utilities; `types-enum` depends only on `@modules/etablissement/entities`. Each module exposes a barrel `index.ts` re-exporting entities/dto/services/controllers/guards/utils/middlewares.
