- **Layered internal structure**: The module follows a clear separation into `controllers/` (Express router with Zod-validated request handling), `services/` (five specialized services: `widget-resolver`, `data-aggregator`, `dashboard-data`, `dashboard-cache`, `dashboard-sse`), `entities/` (TypeORM entity for user layout persistence), `dtos/` (Zod schemas for input validation), `types/` (TypeScript interfaces defining widget contracts), and `utils/` (declarative widget registry).
- **Entry point**: `index.ts` re-exports all public surfaces from sub-packages, making the module consumable as a single import.
- **Dependency direction**: Controllers depend on services; `widget-resolver.service.ts` depends on the auth module's `PermissionResolverService` and the local `WIDGET_REGISTRY`; `data-aggregator.service.ts` lazily loads external module services via dynamic `require()` calls and falls back to `dashboardDataService` for built-in queries; `dashboard-cache.service.ts` is an in-memory cache shared across resolver and aggregator layers.
- **Interface boundaries**: The `WidgetDefinition` interface in `types/dashboard.types.ts` defines the contract between the declarative registry (`utils/widget-registry.ts`) and the runtime resolution/aggregation pipeline. The `DashboardLayout` entity in `entities/dashboard-layout.entity.ts` persists per-user layout preferences via TypeORM.
- **Framework choices**: Express.js router with middleware-based authentication (`authMiddleware`); TypeORM for the `dashboard_layouts` table; Server-Sent Events (SSE) for real-time push notifications managed by `dashboard-sse.service.ts` with heartbeat and stale-client cleanup.
