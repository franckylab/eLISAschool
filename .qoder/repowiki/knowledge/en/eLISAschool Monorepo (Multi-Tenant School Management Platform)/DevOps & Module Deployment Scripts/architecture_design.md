Flat collection of executable scripts with no shared library — each file is a self-contained entry point. Four families coexist:
- Dev lifecycle: `start-dev.sh` / `stop-dev.sh` orchestrate Docker (PostgreSQL + Redis), then launch `npm run dev` in `backend/` and `frontend/`, writing PIDs under `/tmp/`.
- Per-module deployers (`deploy-*.sh`): one script per feature (organisation, messagerie, scoring, recrutement, salaires, etc.). Each follows the same pattern — load `.env`, connect to the PostgreSQL container via `docker exec psql`, run a single numbered migration SQL from `backend/database/migrations/`, verify tables/indexes, then check that the module is wired into `backend/src/modules/index.ts`, `backend/src/app.ts`, `shared/src/enums/modules.enum.ts` and `roles.enum.ts`.
- Database fixers & seeds (`fix-*.sh`, `run-seeds.sh`, `seed-*.sh`, `migrate-*.sh`, `run-migration-082.sh` …): idempotent SQL or Node helpers applied against the live DB; some ship companion `.sql` files (e.g. `fix-super-admin-permissions.sql`) executed via `psql -v user_email=...`.
- Auditors & test harnesses (`check-permissions.js`, `analyse-permissions-manquantes.js`, `test-*.sh`, `verify-*.sh`): Node scans `shared/src/enums/roles.enum.ts` and `frontend/src/**/*.ts(x)` for `hasPermission('module:action')` usage vs enum definitions; shell tests hit `http://localhost:3001/api/...` endpoints after login.

Dependency direction is strictly outward: scripts read source trees (`shared/`, `frontend/`, `backend/`) and drive external services (Docker, `pg_isready`, `curl`, `npx ts-node`). There is no internal package manager or shared JS module — conventions are enforced by naming (`deploy-<feature>.sh`, `test-<feature>.sh`, `verify-<aspect>.sh`) and by the README/GUIDE docs.
