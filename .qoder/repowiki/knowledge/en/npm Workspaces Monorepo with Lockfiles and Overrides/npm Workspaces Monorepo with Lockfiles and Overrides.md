The eLISAschool monorepo manages dependencies through npm workspaces, a single root `package.json`, and per-package lockfiles. There is no vendoring strategy (no `vendor/` or `yarn.lock`), no private registry configuration, and no dedicated dependency-update tooling beyond standard npm commands.

**System / approach**
- **Package manager**: npm (lockfileVersion 3) with the `workspaces` field at the repository root.
- **Workspace layout**: three packages — `backend` (`@elisaschool/backend`), `frontend` (`@elisaschool/frontend`), and `shared` (`@elisaschool/shared`) — all declared under `"workspaces": ["backend", "frontend", "shared"]` in the root `package.json`. The shared package is consumed via the `@elisaschool/shared` scoped name by both backend and frontend.
- **Lockfiles**: each workspace has its own `package-lock.json`; there is also a top-level `package-lock.json` generated by npm workspaces.
- **Engine pinning**: the root `engines` field requires Node ≥ 20 and npm ≥ 10.
- **Dependency overrides**: the root `overrides` section forces `@types/express` to `4.17.21` and `@types/express-serve-static-core` to `4.17.31` across the entire workspace tree to resolve type conflicts.
- **Postinstall hook**: the root `postinstall` script removes a conflicting nested `@types/express-serve-static-core` from `node_modules/@types/express/node_modules/` as a workaround for a transitive type clash.
- **No private registry / vendoring**: no `.npmrc`, no `GOPRIVATE`, no `vendor/` directory; all third-party packages are resolved from the public npm registry.

**Key files**
- `package.json` (root) — workspace declarations, engine constraints, global scripts, `overrides`, `postinstall`
- `backend/package.json` — runtime deps (Express, TypeORM, pg, ioredis, firebase-admin, zod, etc.) and dev deps (ts-node, jest, eslint, typescript)
- `frontend/package.json` — React 19 + Vite + TanStack stack, Tailwind v4, Radix UI, Zustand, i18next, framer-motion, etc.
- `shared/package.json` — minimal runtime dep on `zod`, TypeScript-only build producing `dist/index.js` and `dist/index.d.ts`
- `backend/package-lock.json` (and other lockfiles) — exact resolution snapshots

**Architecture & conventions**
- All three packages are marked `"private": true`, so they are never published to npm; they are only linked locally via workspaces.
- Cross-cutting types/enums/validators live in `shared/src` and are referenced by both `backend` and `frontend` using the `@elisaschool/shared` scope, keeping API contracts in sync without publishing.
- Runtime vs. dev dependencies are cleanly separated in each workspace's `dependencies` / `devDependencies`.
- Docker images (`docker/Dockerfile.backend`, `docker/Dockerfile.frontend`) install dependencies inside containers, relying on the same `package.json` / `package-lock.json` files checked into version control.

**Rules developers should follow**
- Add new third-party packages to the appropriate workspace `package.json` (`backend/`, `frontend/`, or `shared/`); do not edit lockfiles by hand.
- Use `npm run <script> --workspace=<pkg>` (or the root shortcuts like `npm run dev:backend`) instead of running commands directly inside a subdirectory.
- When introducing a new internal package, add it to the root `workspaces` array and reference it via an `@elisaschool/*` scoped name.
- Keep `engines` in the root `package.json` aligned with the CI/container Node/npm versions used in `docker/`.
- If a transitive dependency causes type or runtime conflicts, prefer adding an `overrides` entry in the root `package.json` rather than patching inside a workspace.
